# 示例 13 · 恢复

> **原文**：[`test/examples/13-recovery.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/13-recovery.ts)（在原仓库 `packages/durable` 目录下运行）
>
> ```bash
> node --conditions=source --experimental-strip-types test/examples/13-recovery.ts
> ```

## 本例演示

关闭进程再重新打开，任务如何从中断处继续。示例用一个数到 5 的计数任务，故意在"tick 2 已打印、结果尚未保存"的窗口里关闭 Harness——等价于一次真实崩溃——然后用新的 Harness 重新打开同一个 SQLite 存储，观察任务无缝续跑、且打印不重复。tick 之间的间隔用 v1.4.0 的 `runtime.sleepUntil` 实现为持久化睡眠：睡眠中的任务不持有调用、可挺过重启，到期后在保存的检查点处恢复。这是 pi-durable 持久化能力的招牌演示。

## 逐段解读

### 用 SQLite 文件让存储跨进程存活

```ts
import { mkdtemp, rm } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { createRegistry, defineExtension, defineTask, Harness } from "../../src/index.ts";
import { openNodeSqliteStorage } from "../../src/storage/sqlite/node.ts";

const context = BACKGROUND_CONTEXT;

// Everything a task needs to continue is in storage, so a new Harness over the
// same storage picks up where the last one stopped. This example keeps its
// storage in a SQLite file so it survives closing.
const directory = await mkdtemp(join(tmpdir(), "pi-durable-example-"));
const databasePath = join(directory, "session.sqlite");
```

注释给出了本例的前提：**任务续跑所需的一切都在存储里**，所以基于同一存储打开的新 Harness 能从上一个停下的地方接着跑。为此不能用前面示例的 `MemoryStorage`，而要用 `openNodeSqliteStorage` 把存储落到一个临时目录里的 SQLite 文件，关闭进程后依然存在。

### 定义计数任务：memo 去重 + 检查点推进

```ts
let reachedTick = (_n: number): void => {};
const Ticker = defineTask<{ to: number }, { phase: "tick"; n: number }, string>({
	name: "example.ticker",
	version: 1,
	initial: () => ({ phase: "tick", n: 1 }),
	phases: {
		tick: async (task, runtime, taskContext) => {
			const n = task.state.checkpoint.n;
			// Save the intent before the effect. A memo keeps the first value
			// written under its name, so if the process dies after printing but
			// before the next checkpoint is saved, the rerun sees the memo and
			// does not print the same tick twice.
			if ((await runtime.memo(`printed-${n}`, taskContext)) === undefined) {
				await runtime.memo(`printed-${n}`, true, taskContext);
				console.log(`tick ${n}`);
			}
			reachedTick(n);
			// Save the outcome: the final result, or the next tick after a short
			// sleep. The sleep is stored with the checkpoint, so the task holds no
			// invocation meanwhile, and a Harness opened later continues it once
			// its time has come.
			if (n === task.input.to) {
				await runtime.commit(
					() => ({ status: "terminal", outcome: { status: "completed", result: `counted to ${n}` } }),
					taskContext,
				);
				return;
			}
			await runtime.sleepUntil(runtime.now() + 50, { phase: "tick", n: n + 1 }, taskContext);
		},
	},
	abort: async (_task, runtime, taskContext) => {
		await runtime.commit(() => ({ status: "terminal", outcome: { status: "aborted" } }), taskContext);
	},
});
const registry = createRegistry();
registry.install(defineExtension({ name: "ticker", tasks: [Ticker] }));
const open = async () =>
	Harness.open(await openNodeSqliteStorage(databasePath), { models: createModels(), registry }, context);
```

模块级的 `reachedTick` 是个可供外部替换的钩子，方便示例在恰当时机接管控制流。`tick` 阶段是"先存意图、再产生效果、再存结果"的完整示范：先问 `runtime.memo("printed-N")`——**memo 只保留同名下的第一次写入**，所以先读后写构成一个"这个效果发生过吗"的标记；没写过才写入 memo 并打印。注释解释了为什么这很重要：如果进程在打印之后、下一个检查点保存之前死掉，重跑时 memo 已经在了，同一个 tick 就不会打印两次。接着按是否数到 `to` 分两条路：数到了就 `runtime.commit()` 提交最终结果并 `return`；否则调用 `runtime.sleepUntil(runtime.now() + 50, { phase: "tick", n: n + 1 }, taskContext)` 结束本阶段。这是 v1.4.0 的**持久化睡眠**：约 50 毫秒的等待与下一个检查点（回到 `tick` 阶段、n+1）一起写入存储，`sleepUntil()` 在睡眠被保存时就返回、并不等到时刻来临；从此任务**不持有任何调用**（invocation），睡眠中的任务可挺过任意次进程重启，到期后由之后打开的 Harness 在该检查点处恢复。注意阶段内不存在"内存里干等"这回事：阶段在崩溃或关闭后总是从头重跑，所以等待之后的工作被移进下一个阶段（这里是 `tick` 的下一轮），所需数据由检查点携带。`open()` 辅助函数封装了"基于同一个 SQLite 文件重新打开 Harness"。

### 第一次运行：在崩溃窗口里关闭

```ts
// First run: start counting to 5, and close the Harness right after tick 2 is
// printed, before its next checkpoint is saved. That is the same situation as
// a crash between the effect and saving its outcome.
const firstRun = await open();
const tickerId = await (await firstRun.root(context)).commit(
	(tx) => tx.createTask(Ticker, { to: 5 }, { ownership: { kind: "conversation" } }),
	context,
);
const tickTwo = new Promise<void>((resolve) => {
	reachedTick = (n) => {
		if (n === 2) resolve();
	};
});
firstRun.resume();
await tickTwo;
await firstRun.close(context);
reachedTick = () => {};
```

创建一个数到 5 的任务后调用 `firstRun.resume()` 启动调度。`reachedTick` 钩子在 `commit` **之前**触发，所以当 `tickTwo` 这个 Promise 在 n===2 时 resolve，此刻恰好处于"tick 2 已打印、保存 n=3 的检查点还没执行"的窗口——立即 `close()`，制造出和"在产生效果与保存结果之间崩溃"完全相同的现场。

### 用只读 Harness 查看现场

```ts
// Read the saved record through a Harness that never resumes, so nothing runs.
const reader = await open();
const saved = (await reader.getTask(tickerId, context))!;
await reader.close(context);
console.log("closed; saved checkpoint:", saved.state, "memos:", saved.memos);
```

重新打开一个从不 `resume()` 的 Harness，就能安全地检查持久化的任务记录：`getTask` 返回的 `saved.state` 显示检查点还停在 `tick 2`（存有 n=3 睡眠的那次 `sleepUntil` 还没来得及执行），`saved.memos` 里已经有 `printed-1`、`printed-2`——效果发生过的证据。看完就关掉，它什么都不会运行。

### 第二次运行：等待即恢复

```ts
// Second run: nothing to restart by hand. Waiting for the unfinished task
// enables scheduling and continues it. Tick 2 runs again because its outcome
// was never saved, but its memo says it was already printed.
const secondRun = await open();
const counted = await secondRun.waitForTask(tickerId, context);
console.log("after reopen:", counted.state.outcome);
await secondRun.close(context);
await rm(directory, { recursive: true, force: true });
```

第二次运行**没有任何手动重启步骤**：直接对新 Harness 调用 `waitForTask`，等待未完成任务这个动作本身就启用了调度并让任务继续。tick 2 会再执行一遍（因为它的结果从未保存），但 memo 告诉它已经打印过了，所以输出里不会出现第二次 "tick 2"；任务随后一路数到 5，终态结果是 `counted to 5`。最后删掉临时目录收尾。

## 关键点

- 任务续跑所需的一切都在存储里：换 `MemoryStorage` 就没有跨进程恢复，必须用 SQLite 等文件存储。
- `runtime.memo` 只保留同名第一次写入的值，天然适合做"效果已发生"的幂等标记；先查 memo 再写 memo 再执行效果，重跑就不会重复。
- `runtime.sleepUntil(时刻, 下一检查点, context)` 是 v1.4.0 的持久化睡眠：等待与下一检查点一起存入存储，睡眠中的任务不持有任何调用、可挺过重启，到期后在检查点处恢复。
- 事故现场可以检查：用一个从不 `resume()` 的 Harness 调 `getTask`，能看到保存的 `state` 与 `memos`，且不会触发任何执行。
- 恢复不需要任何手动重启代码：对未完成任务调用 `waitForTask()` 会启用调度并从检查点继续。
- 理解"哪些工作会重做"：结果没保存的那一步会整个重跑，靠 memo 和幂等设计保证重跑无副作用。
