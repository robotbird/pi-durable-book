# 示例 15 · 系统提示

> **原文**：[`test/examples/15-system-prompt.ts`](../../original/packages/durable/test/examples/15-system-prompt.ts)（在 original/packages/durable 目录下运行）
>
> ```bash
> node --conditions=source --experimental-strip-types test/examples/15-system-prompt.ts
> ```

## 本例演示

系统提示不是静态字符串，而是每次请求前由各扩展的 section **现渲染**出来的：存储里没有任何提示状态，只有与模型已见内容的差异会作为 `pi.system` 条目追加。示例还演示了 section 如何读取请求环境（工作目录）、如何被另一个扩展包装、以及子代理如何用 `extensions.remove` 和 `instructions` 获得自己的提示。

## 逐段解读

### 假模型与三份预设回答

```ts
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { fauxAssistantMessage, fauxProvider } from "@earendil-works/pi-ai/providers/faux";
import { NodeExecutionEnv } from "../../src/env/node.ts";
import {
	type Conversation,
	createRegistry,
	defineExtension,
	Harness,
	MemoryStorage,
	SystemEntry,
	section,
	wrapSection,
} from "../../src/index.ts";

const context = BACKGROUND_CONTEXT;
const faux = fauxProvider();
const models = createModels();
models.setProvider(faux.provider);
faux.setResponses([fauxAssistantMessage("Done."), fauxAssistantMessage("Done."), fauxAssistantMessage("Done.")]);
```

faux 供应商注册进模型表；`setResponses` 预置了三份 "Done."——对应后面 root 和子代理各一次提交，加上 root 改 cwd 后的第三次提交。`NodeExecutionEnv` 来自 `src/env/node.ts`，稍后用作执行环境。

### 两个提供 section 的扩展

```ts
// Pico stores no prompt state. Before each model request, the sections of the
// conversation's selected extensions render the desired prompt, and only the
// difference to what the model already saw is appended to the transcript as a
// `pi.system` entry.
const Coding = defineExtension({
	name: "coding",
	sections: [
		// `tag: false` sends the text as is; by default it is wrapped in <key>...</key>.
		section("preamble", () => "You are a coding agent.", { tag: false }),
		// Sections see the environment built for this request, here its working directory.
		section("cwd", (input) => input.env?.cwd),
	],
});
const AgentsMd = defineExtension({
	name: "agents-md",
	sections: [section("agents_md", () => "Run npm run check after changes.")],
});
```

开头注释是本例的题眼：这个框架**不存储提示状态**——每次模型请求之前，对话所选扩展的 sections 渲染出"想要的提示"，然后只把与模型已经见过的内容的**差异**追加到记录里，作为一条 `pi.system` 条目。`Coding` 扩展给出两个 section：`preamble` 用 `tag: false` 让文本原样发送（默认会包成 `<key>...</key>`）；`cwd` 展示 section 可以读取**为本次请求构建的环境**，这里取工作目录。`AgentsMd` 则模拟 AGENTS.md 式的项目指令："改完代码要跑 npm run check"。

### 用 wrapSection 装饰别的 section

```ts
// Another extension decorates a section by key without replacing it.
const Terse = defineExtension({
	name: "terse",
	wraps: [
		wrapSection("preamble", (preamble) => ({
			...preamble,
			render: async (input, renderContext) => `${await preamble.render(input, renderContext)} Be terse.`,
		})),
	],
});
```

与示例 10 的 `wrapTool` 对应，`wrapSection` 按 key 包装某个 section 而不替换它：保留原 section 的其他字段，只包一层 `render`——先调用原渲染，再追加 " Be terse."。注释强调这是"另一个扩展"对既有 section 的装饰，两者保持解耦。

### 组装：环境跟随每个对话的 cwd

```ts
const registry = createRegistry();
registry.install(Coding);
registry.install(AgentsMd);
registry.install(Terse);
// The environment follows each conversation's agent `cwd`.
const env = ({ cwd = "/" }: { readonly cwd?: string }) => new NodeExecutionEnv({ cwd });
const harness = await Harness.open(new MemoryStorage(), { models, registry, env }, context);
const model = { provider: "faux", modelId: "faux-1" };
const root = await harness.root(context, { agent: { model, cwd: "/repo" } });
```

三个扩展都装进注册表。`env` 是一个工厂函数：Harness.open 通过 `env` 选项告诉框架如何为请求构建执行环境，注释说明**环境跟随每个对话 agent 的 `cwd`**——`cwd` 选项没传时默认 `/`。根对话的 agent 指定模型和 `cwd: "/repo"`，所以 `cwd` section 渲染出来就是 `/repo`。

### 子代理：取消选择扩展、追加专属指令

```ts
// A subagent deselects AGENTS.md and gets its own instructions, rendered last
// as the `instructions` section.
const subagent = await harness.createConversation(
	{
		ownership: { kind: "ownerless" },
		agent: {
			model,
			cwd: "/repo",
			extensions: { remove: [AgentsMd] },
			instructions: "Only read; never edit files.",
		},
	},
	context,
);
```

子代理是一个新对话，agent 配置里用 `extensions: { remove: [AgentsMd] }` **取消选择** AGENTS.md 扩展——它就不会收到"跑 npm run check"的指令；同时 `instructions` 提供一段专属指令，注释说明它**最后渲染**、作为 `instructions` section 出现在提示末尾。这就是"同一个代码库、不同角色不同提示"的实现方式。

### 提交两轮并打印各自的系统提示

```ts
async function systemEntries(conversation: Conversation) {
	const page = await conversation.entries({}, 20, undefined, context);
	return [...page.items].reverse().flatMap((entry) => (SystemEntry.is(entry) ? (entry.model ?? []) : []));
}

await (await root.submit({ type: "input", content: "Fix the build." }, context)).wait(context);
await (await subagent.submit({ type: "input", content: "Read the logs." }, context)).wait(context);
console.log("root system prompt:", await systemEntries(root));
console.log("subagent system prompt:", await systemEntries(subagent));
```

辅助函数 `systemEntries` 从对话记录里筛出系统条目（用 `SystemEntry.is()` 识别 `pi.system` 条目），取出它们贡献的 `model` 消息——也就是真正发给模型的系统提示内容。root 和子代理各提交一个输入后打印对比：root 的提示里有无标签的 preamble（已加 "Be terse."）、`/repo` 的 cwd 和 AGENTS.md 指令；子代理的提示里没有 agents_md，末尾多一条 instructions。

### cwd 变了，只追加差异

```ts
// When a section's output changes, the next request appends only the change.
await root.configure({ cwd: "/repo/packages" }, context);
await (await root.submit({ type: "input", content: "Now the package." }, context)).wait(context);
console.log("root system entries after cwd change:", await systemEntries(root));

await harness.close(context);
```

用 `configure` 把根对话的 cwd 改成 `/repo/packages` 再提交一次。由于框架不存提示状态、只追加差异，第三次请求的记录里只会多出一条**只包含变化部分**的 `pi.system` 条目（新的 cwd 值），而不是重发整份提示——注释点明：section 的输出变了，下一次请求只追加变化。

## 关键点

- 系统提示无持久状态：每次请求前由所选扩展的 sections 现渲染，只有与模型已见内容的差异会作为 `pi.system` 条目追加到记录。
- `tag: false` 让 section 文本原样发送；默认会被包进 `<key>...</key>` 标签。
- section 能读到为本次请求构建的环境（`input.env?.cwd`）；`env` 工厂 + agent 的 `cwd` 让环境逐对话生效，用 `configure` 改 cwd 后下一次请求只追加变化。
- `wrapSection` 按 key 装饰别的扩展的 section（如给 preamble 追加一句话），不替换原定义，与扩展选择解耦。
- 子代理配置的两件武器：`extensions: { remove: [...] }` 取消选择某些扩展；`instructions` 提供专属指令且最后渲染为 instructions section。
- 检查系统提示的办法：分页读 `entries()`，用 `SystemEntry.is()` 过滤，再取其 `model` 消息。
