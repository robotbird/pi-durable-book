# 示例 29 · 每对话沙箱

> **原文**：[`test/examples/29-sandbox-per-conversation.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/29-sandbox-per-conversation.ts)（在原仓库 `packages/durable` 目录下运行）
>
> ```bash
> node --conditions=source --experimental-strip-types test/examples/29-sandbox-per-conversation.ts
> ```

## 本例演示

"每个对话一个沙箱"：应用把对话的沙箱位置记在自己的文档（`defineDoc`）里，`env` 环境函数在每次需要时按 `conversationId` 查文档、返回指向该沙箱的 `NodeExecutionEnv`；没有沙箱的对话拿不到环境，工具干净失败。两个用户的对话各写各的 `note.txt`，互不串门。注释也点明：这里用目录模拟沙箱，托管产品里可以返回运行在该对话容器内的 ExecutionEnv。

## 逐段解读

### 沙箱文档与分叉语义

```ts
import { mkdtemp, readFile, rm } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { fauxAssistantMessage, fauxProvider, fauxToolCall } from "@earendil-works/pi-ai/providers/faux";
import { NodeExecutionEnv } from "../../src/env/node.ts";
import { createRegistry, defineDoc, Harness, MemoryStorage } from "../../src/index.ts";
import { CodingTools } from "../../src/tools/index.ts";

const context = BACKGROUND_CONTEXT;

// Which sandbox a conversation runs in. `fork: "initial"`: a fork gets no sandbox until the app assigns one.
const Sandbox = defineDoc<{ path?: string }>({
	kind: "app.sandbox",
	version: 1,
	scope: "conversation",
	history: "latest",
	fork: "initial",
	initial: () => ({}),
});
```

`Sandbox` 文档只有一个字段 `path`。三个声明值得注意：`scope: "conversation"` 每个对话一份；`history: "latest"` 只保留最新值（适合这种"当前指向哪"的配置型数据）；`fork: "initial"` 的语义由注释给出——分叉出的对话拿到的是 `initial()` 的空文档，也就是说**分叉不继承沙箱**，要等应用重新分配。这与 27 例的 `fork: "asOf"` 形成对照。

### 环境函数：从文档查沙箱

```ts
const faux = fauxProvider();
const models = createModels();
models.setProvider(faux.provider);
const note = (text: string) =>
	fauxAssistantMessage(fauxToolCall("write", { path: "note.txt", content: text }), { stopReason: "toolUse" });
faux.setResponses([
	note("from alice"),
	fauxAssistantMessage("Saved."),
	note("from bob"),
	fauxAssistantMessage("Saved."),
]);

const registry = createRegistry();
registry.install(CodingTools);
const harness = await Harness.open(
	new MemoryStorage(),
	{
		models,
		registry,
		// Committed reads only; a conversation without a sandbox gets no environment, so its tools fail cleanly.
		env: async ({ conversationId, read }, envContext) => {
			const sandbox = await read.snapshot(Sandbox, conversationId, envContext);
			return sandbox?.path === undefined ? undefined : new NodeExecutionEnv({ cwd: sandbox.path });
		},
	},
	context,
);
```

模型剧本是两个对话各调一次 `write` 写 note.txt。重点在 `env`：它这次是异步函数，参数里有 `conversationId` 和一个 `read` 句柄，用 `read.snapshot(Sandbox, conversationId)` 查该对话的沙箱。注释强调两点：这是**只读已提交的数据**（沙箱分配必须已经落库才能查到）；查不到 `path` 就返回 `undefined`——没有沙箱的对话**没有执行环境**，工具调用会干净地失败，而不是落到某个默认目录里误操作。查到了就构造一个 `cwd` 指向沙箱目录的环境。对照 26 例：那里的工厂参数是 `cwd`，这里换成了 `conversationId` + `read`，查的是应用自己的文档。

### 创建对话时分配沙箱

```ts
// Each user's conversation gets a fresh sandbox in the creating commit.
const model = { provider: "faux", modelId: "faux-1" };
async function conversationFor(user: string) {
	const path = await mkdtemp(join(tmpdir(), `pi-durable-sandbox-${user}-`));
	const conversation = await harness.createConversation(
		{
			ownership: { kind: "ownerless" },
			agent: { model },
			init: async (tx, id) => {
				(await tx.doc(Sandbox, id)).path = path;
			},
		},
		context,
	);
	return { conversation, path };
}
```

`conversationFor` 为每个用户建一个全新沙箱目录，然后在 `createConversation` 的 `init` 回调里把路径写进该对话的 `Sandbox` 文档（`tx.doc(Sandbox, id)` 按 id 取新对话的文档）。注释点明时序保证：这发生在**创建对话的同一个提交里**——所以第一次工具调用去查文档时，沙箱必然已经落库，env 函数不会读到空。

### 各写各的 note.txt

```ts
const alice = await conversationFor("alice");
const bob = await conversationFor("bob");
await (await alice.conversation.submit({ type: "input", content: "Leave a note." }, context)).wait(context);
await (await bob.conversation.submit({ type: "input", content: "Leave a note." }, context)).wait(context);
console.log("alice's sandbox:", await readFile(join(alice.path, "note.txt"), "utf8"));
console.log("bob's sandbox:", await readFile(join(bob.path, "note.txt"), "utf8"));

await harness.close(context);
await rm(alice.path, { recursive: true, force: true });
await rm(bob.path, { recursive: true, force: true });
```

两个对话发同样的指令"留个便签"，模型各自调用 write 工具——由于执行环境不同，`note.txt` 分别落在 alice 和 bob 自己的沙箱目录里，读出来分别是 "from alice" 和 "from bob"，这就是"每对话一个沙箱"的隔离效果。最后清理两个目录。

## 关键点

- 沙箱归属是应用数据：存在 `scope: "conversation"` 的文档里，env 函数每次按 `conversationId` 查询，而不是在进程里维护映射表。
- `env` 可以返回 `undefined`：没有沙箱的对话没有执行环境，工具干净失败——比落到默认目录更安全。
- `read.snapshot` 只读已提交数据；配合 `init` 回调把写入放进创建对话的同一提交，保证首次使用前必然可见。
- `fork: "initial"`：分叉出的对话不继承沙箱，拿到空文档直到应用重新分配（对照 27 例的 `fork: "asOf"`）。
- `history: "latest"` 只留最新值，适合"当前指向哪"这类配置型文档。
- 本例用目录模拟沙箱；托管产品里可返回运行在该对话容器内的 ExecutionEnv，接口不变。
