# 示例 11 · 扩展状态

> **原文**：[`test/examples/11-extension-state.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/11-extension-state.ts)（在原仓库 `packages/durable` 目录下运行）
>
> ```bash
> node --conditions=source --experimental-strip-types test/examples/11-extension-state.ts
> ```

## 本例演示

扩展如何维护**每个对话一份**的持久化文档（document）：定义一个待办清单文档，用一个 `todo` 工具往里写，用一个 section 在每次模型请求前把清单渲染进系统提示。同时演示用 faux 假模型供应商脚本化一次"调用工具"的完整轮次。

## 逐段解读

### 定义每对话一份的文档

```ts
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { Type } from "@earendil-works/pi-ai";
import { createModels } from "@earendil-works/pi-ai/models";
import { fauxAssistantMessage, fauxProvider, fauxToolCall } from "@earendil-works/pi-ai/providers/faux";
import {
	createRegistry,
	defineDoc,
	defineExtension,
	defineTool,
	Harness,
	MemoryStorage,
	section,
} from "../../src/index.ts";

const context = BACKGROUND_CONTEXT;

// A todo list per conversation. Rewindable with `asOf`, so a fork starts with
// the todos its parent had at the fork entry.
const Todos = defineDoc<{ items: string[] }>({
	kind: "example.todos",
	version: 1,
	scope: "conversation",
	history: "rewindable",
	fork: "asOf",
	initial: () => ({ items: [] }),
});
```

`defineDoc` 定义一份文档类型：`kind` 是全局唯一的文档名，`version` 标记数据结构版本，`scope: "conversation"` 表示每个对话各存一份。关键的两个选项是 `history: "rewindable"`（历史可回放，可以用 `asOf` 取任意时点的快照）和 `fork: "asOf"`——分叉出的新对话自动继承**父对话在分叉点时**的待办清单。`initial` 给出新文档的初始状态。

### 工具负责写，section 负责读

```ts
// The tool writes the document; the section shows it to the model before every
// request. Nothing needs to create it up front: tx.doc() creates it on first
// write, and the section treats a missing document as an empty list.
const Todo = defineExtension({
	name: "todo",
	tools: [
		defineTool({
			name: "todo",
			description: "Add an item to your todo list",
			parameters: Type.Object({ item: Type.String() }),
			execute: async (args, api, callContext) => {
				await api.commit(async (tx) => {
					(await tx.doc(Todos, api.conversationId)).items.push(args.item);
				}, callContext);
				return { content: [{ type: "text", text: `added ${args.item}` }] };
			},
		}),
	],
	sections: [
		section("todos", async (input, renderContext) => {
			const todos = await input.read.snapshot(Todos, input.conversationId, renderContext);
			return todos === undefined || todos.items.length === 0 ? undefined : todos.items.join("\n");
		}),
	],
});
```

注释说明了这套组合拳的分工：工具负责写文档，section 在**每次请求之前**把文档内容展示给模型。而且不需要任何"初始化"步骤——`tx.doc(Todos, api.conversationId)` 在首次写入时自动创建文档，section 遇到不存在的文档就当作空列表处理。工具的 `execute` 拿到三个参数：`args` 是按 TypeBox 模式解析后的入参，`api` 提供 `commit`（在事务里把新条目 push 进文档数组）和 `conversationId`；注意 `callContext` 要透传给 `api.commit`。section 的渲染函数用 `input.read.snapshot()` 读当前对话的文档快照，清单为空或缺文档时返回 `undefined`——该 section 就不会出现在系统提示里。

### 用 faux 假模型搭建环境

```ts
const faux = fauxProvider();
const models = createModels();
models.setProvider(faux.provider);
const registry = createRegistry();
registry.install(Todo);
const harness = await Harness.open(new MemoryStorage(), { models, registry }, context);
const root = await harness.root(context, { agent: { model: { provider: "faux", modelId: "faux-1" } } });
```

`fauxProvider()` 造一个假供应商，注册进模型表，这样示例可以完全离线运行。根对话通过 `harness.root` 的第二个参数把 agent 模型指定为 `faux/faux-1`。

### 第一轮：模型调用 todo 工具

```ts
faux.setResponses([
	fauxAssistantMessage(fauxToolCall("todo", { item: "fix the build" }), { stopReason: "toolUse" }),
	fauxAssistantMessage("Noted."),
	fauxAssistantMessage("Working on it."),
]);
await (await root.submit({ type: "input", content: "Remember to fix the build." }, context)).wait(context);
console.log("todos:", await harness.snapshot(Todos, root.id, context));
```

`setResponses` 预先编排好模型的回复脚本：第一条是带 `todo` 工具调用的助手消息（`stopReason: "toolUse"` 触发工具执行），第二条是工具结果之后的最终回答。`submit()` 提交用户输入，返回的 Submission 用 `wait()` 等到本轮跑完。之后 `harness.snapshot(Todos, root.id, context)` 直接读出根对话的文档快照，验证 "fix the build" 已经写进清单。

### 第二轮：清单进入系统提示

```ts
// The next request's system prompt carries the list. The first system message
// only announced the todo tool; no section had text yet.
await (await root.submit({ type: "input", content: "What is next?" }, context)).wait(context);
const { messages } = await root.context(context);
console.log(
	"system messages:",
	messages.flatMap((message) =>
		message.role === "system"
			? [{ sections: message.sections, toolsAdded: message.toolsAdded?.map((tool) => tool.name) }]
			: [],
	),
);

await harness.close(context);
```

第二次提交后再取上下文，检查发给模型的系统消息。注释点出一个细节：**第一条**系统消息里还没有清单文本（当时文档是空的，todos section 返回 `undefined`），它只是随工具一起宣告了 `todo` 工具的存在（`toolsAdded`）；**第二条**系统消息的 `sections` 里才带上 "fix the build"——section 是在每次请求前现算的，文档一变，下一次请求就能看到。

## 关键点

- `defineDoc` 的选项组合决定文档行为：`scope: "conversation"` 每对话一份，`history: "rewindable"` 支持 `asOf` 回放，`fork: "asOf"` 让分叉对话继承分叉点时的文档状态。
- 文档无需预先创建：`tx.doc()` 首次写入时自动建；读取方（section）把缺失文档当空数据处理。
- 扩展状态的典型模式是"工具写 + section 读"：写入走 `api.commit` 事务持久化，读取在每次请求前渲染进系统提示。
- section 返回 `undefined` 时不会出现在系统提示里——空状态不占提示词。
- faux 供应商是测试利器：`setResponses` 脚本化回复，`fauxToolCall` 模拟工具调用，`stopReason: "toolUse"` 驱动工具执行循环。
- 工具 `execute` 的第三个参数 `callContext` 必须传给 `api.commit`，事务才能挂在正确的执行上下文上。
