# Pico5 实现交接文档

> **本篇译自** [`docs/pico-v5-handoff.md`](../../original/packages/durable/docs/pico-v5-handoff.md)——pi-durable v5（Pico5）的实现计划。

`packages/durable/docs/spec.md` 是规范性（normative）文档。请按顺序实现下述清单。每完成一个包：运行它的测试、运行 `npm run check`，然后停下来等待用户评审。实现当前包时，不要顺手重新设计后面的包。

Pico3 仅作参考素材。要保留的是其中有用的行为，而不是它的能力门面（capability facade）、膜（membrane）、文档路由、视图投影、事件或克隆链。

## 状态

- 过时的 `pico` 与 `pico4` 原型已移除。
- `pico3` 保留。
- 包 1–23 已在 `packages/durable` 中实现；其中包 10 已由 Chord 的规范化结构 diff（structural diff）实现满足。

## 1. 记录、游标与内存表

实现 ID、序列（sequence）、保留的根会话 ID `1`、`ConversationRecord`、`EntryRecord`、严格的输入/写入用 `SubmissionRecord` 取值、活跃/终态（live/terminal）的 `TaskRecord` 取值、文档记录、存储写入、对后端不透明（backend-opaque）的 JSON 游标（cursor），以及分离式（detached）的 `MemoryStorage` 表。`Conversation` 保留给公开的会话对象，`Entry` 保留给类型化的条目（entry）定义，`Task` 保留给 `defineTask()` 返回的类型化可执行定义。

测试：保留根身份及其不可变创建、混合的原子提交（commit）、回滚（rollback）、分离式读写、游标边界、穿过深层祖先上限（ancestor cap）的 fork 感知条目扫描、head 查找、条目到提交（entry-to-commit）的反查、完整任务替换，以及提交替换/按 request-ID 查找。

## 2. 内存文档记录

新增由调用方选定的文档 base/delta（基线/增量）写入、退役（retirement）、转世（reincarnation）、current/as-of 成员关系、按逻辑地址的精确查找、限定作用域的扫描，以及物化（materialized）的时间点读取。存储层把 base/delta 修订保持为私有，返回分离的值及其存储所用定义版本；它直接应用 Chord 的 `Op[]`，不接收定义回调，也不接收未用到的候选值。

测试：Session、会话与任务三种作用域（scope）的文档，半开（half-open）生命周期，创建加退役，已退役文档的历史成员关系，家族（family）查询，仅针对 current 的回收（reclamation），版本边界，分离式所有权，以及绝不扫描无关的文档记录。

## 3. SQLite 后端

用普通数据行加上建索引的文档记录实现完整的存储契约。不要把 Chord 操作翻译成 SQL JSON 补丁。

重开后再运行一遍内存一致性（conformance）测试套件。测试：SQL 事务回滚、近期/久远（recent/ancient）的 as-of 读取、查询计划、latest 回收、WAL 检查点（checkpoint）、已删除页复用，以及有代表性的存储体量。

## 4. JSONL 发布

实现 `main.jsonl` 中的表写入、每个化身（incarnation）一个文档附属文件（sidecar）、每个活跃任务一个 sidecar，以及每次提交一个主标记（main marker）。不要添加独立的 sidecar 协议。

把当前的 `ExecutionEnv`、`FileSystem`、`Shell`、Node 实现及其所需的工具文件，从 `packages/agent/src/harness` 复制（而不是导入）到 `packages/durable/src/env`。只复制与环境相关的部分，不要复制 agent 技能、提示词、遥测或工具定义。为复制过来的文件系统契约补充按精确字节数的文件截断（truncate）与文件冲刷（flush）。JSONL 只依赖 `FileSystem`，不依赖更宽泛的 `ExecutionEnv`。保持可移植的环境与 JSONL 入口不依赖 Node 内置模块；Node 实现只从 `/env/node` 与 `/storage/jsonl/node` 暴露。不要把 Pico3 的实现当作源码素材。

把当前 `MemoryStorage` 的状态机制重构为两阶段的预备变更（prepared mutation）：校验与分离产出一个稍后可以无失败地应用的候选（candidate）。在这一对阶段之上构建 `MemoryStorage.commit()`，并在 JSONL 中复用同一机制。JSONL 必须先追加每条预备好的 sidecar 记录，再追加主标记，最后才应用预备好的内存变更。序列化或准备失败发生在文件 I/O 之前，不会让后端中毒（poison）。保留的索引/物化与写入参数保持分离，读取永不暴露后端持有的缓存对象。

JSONL 创建选项有 `fsync?: boolean`，默认 `false`。为 `false` 时，追加 sidecar 再追加主标记，不做显式 flush。为 `true` 时，先追加所有受影响的 sidecar，逐一 flush 受影响的 sidecar，然后再追加主标记。普通发布不要对 `main.jsonl` 做显式 flush。只有主文件的提交没有 sidecar 需要 flush。任何不确定的发布追加或 flush 失败都会让打开的后端中毒，且不发布任何预备好的内存变更。包 5 将加入发布之后的独立 flush，用于授权回收。

故障测试：撕裂/短缺的 sidecar 写入、sidecar 之间发生的失败、每个标记边界、未确认的尾部、缺失的已确认数据、中毒的写入、按精确字节数的尾部截断、两种 fsync 设置及其调用顺序、分离的保留状态与读取，以及浏览器安全的可移植入口。直接运行并在重开后再次运行完整的存储一致性测试套件。

## 5. JSONL 回收

基于已提交的标记与描述符失效（descriptor invalidation），实现任务文档退役与仅针对 current 的 base 回收。当没有记录残留时直接删除 sidecar；否则采用临时替换加重命名（rename）。`fsync: true` 时，在破坏性回收之前先 flush 一次 `main.jsonl`，确保授权标记不会在清理数据尚存时消失；如果这次 flush 失败，则跳过回收，但不让已发布的提交失败。重命名之前先 flush 非空的临时替换文件。这不是发布 flush，也不是主文件压缩（compaction）。

崩溃测试每一个重写/重命名边界。验证可回溯（rewindable）历史绝不被回收，且默认无 fsync 的行为符合规范。

## 6–7. Tracker 事务核心、定义与类型化访问

**前置条件：** `@earendil-works/chord/delta` 导出规范化的、针对 Astra 不可变结构优化过的 `track`、`Tracker`、`Change` 与 `Prepared`，并且它的 draft 放置（placement）会拒绝非严格 JSON 的值。其他 Delta 目录下的实验性变体不属于 Pico API。

将这两个包作为一个里程碑实现。保持各实现层分离，但不要构建临时性的无类型文档获取接缝。实现这些测试所需的通用 `Tx` 表面：精确表读取、分页的 conversation/entry/task 扫描、`ReadAfterWrite`、创建 ID 的写入，以及完整任务替换。扫描暴露存储层的 cursor 和调用方选择的 limit；它们绝不隐藏无界的全量扫描。语义层面的会话、条目、任务与调度器（scheduler）行为仍属包 13–17。

每个已加载文档保留一个 Astra 不可变 tracker（追踪器）。其受信任的不可变 `value` 就是当前可共享的修订版（revision）。`prepare()` 发出分离的、自包含的操作，并用优化过的不可变应用器计算下一个修订版；操作的 placement 载荷与该修订版可以共享容器，但两者都不可被修改。`adopt()` 校验所有权与修订版，然后只做指针交换（pointer swap）到已算好的值。

实现保持作用域的单例/家族 token 与针对 Session、会话、任务所有者的重载。只有 `tx.doc()` 是 get-or-create：单例 token 提供 `initial()`，而家族调用总是提供 key 与 seed，并且只在实例不存在时使用首个 seed。定义是显式的类型化参数，不是注册式声明；两个冲突的定义声称同一个持久化 kind 属于调用方误用，不受支持。

在首次 `tx.doc()` 访问时，先按逻辑地址对获取 promise 做记忆化（memoize），再去等待它，然后调用 `tracker.beginChange()`。在整个可能异步的 Session 回调期间，重复访问返回同一个覆盖层 draft（草稿）。Session 执行线（line）允许每个 tracker 同时只有一个打开的变更。一个带着未决获取而完结的回调会 reject：封存（seal）`Tx`、中止所有打开的变更、抽干并中止挂起的获取，并观察其失败。回调失败会中止每个变更。回调成功则在存储层准入之前准备好每个变更。

不要为了严格 JSON 而去遍历预备好的操作载荷或选定的 base；它们在构造上就是严格 JSON。Tracker 的品牌标记（branding）与修订版检查负责强制所有权与过期检测。每个暂存的文档写入只求值一次，只把选定的 base 值或操作批次交给存储层。在存储层结算（settlement）期间，保持所有先前的不可变修订版不变。成功时，通过指针交换采纳每个预备好的值，并在释放执行线之前把它的不可变修订版/操作发布排入队列。存储层失败时，中止预备的变更、让 Session 中毒，且什么都不发布。准备失败正常回滚；包 8 补充检查点选择及其失败路径。

初始化器（initializer）、迁移（migration）与替换根在成为受信任的不可变修订版之前，都会经过严格 JSON 检查并复制为内核独占所有权。已加载与 fork 复制的根从存储层分离而来，无需再复制即可被追踪。Chord 会复制并对每次 draft 放置做严格 JSON 检查，在违规赋值处抛错。Astra 空批次会抑制普通写入，而可重放的非空结构无操作（no-op）仍是有效的写入和发布。不需要运行时冻结，也不需要第二次操作载荷复制。

快照（snapshot）、source 与 watch 查找绝不创建，缺席时返回 `undefined`。`snapshot()` 返回可共享的不可变当前修订版；调用方修改前必须先复制。只读迁移可以把它迁移后的不可变 tracker 连同较旧的存储版本标记一起缓存，而不写入；下一次成功的 `tx.doc()` 仍会写入所需的 current 版本 base。事务暂存的创建或迁移只有在其所属的存储层提交成功后才进入共享缓存。所有冷加载都在 Session 执行线上进行；已加载的不可变修订版可以不经复制地读取。

测试：回调失败；回调完结时逃逸 draft 被吊销（revocation）；并发重复获取；带挂起获取的回调失败与成功；封存后的迟到获取；并发初始化只执行一次；初始 base；家族首 seed 胜出；作用域/token 不匹配；非创建读取；共享不可变快照与先前修订版的稳定；空批次抑制与可重放的冗余结构无操作；多文档准备失败；不确定的存储层失败导致中毒；存储层结算期间旧修订版保持稳定；指针交换采纳与替换采纳；受信任不可变契约下的操作/修订版载荷共享；非 JSON 初始化器与 draft 放置的拒绝；赋值复制与重复放置的相互独立；权限（authority）与预备 draft 不可逃逸；终态任务拒绝；由任务派生的会话身份；退役；绑定转世实例的 source；以及卸载/重载。在同一个事务中还要包含：先建任务后建文档、终态之后建文档被拒绝、先建文档后任务终态并结算；内部候选校验不得触发 `ReadAfterWrite`。

## 8. 检查点与迁移

tracker 准备好之后，Session 对普通变更只求值一次 `checkpointWhen(value, ops, { deltasSinceBase })`，并只把选定的 base 或 delta 交给存储层。实现必需的创建/版本 base，以及类型化访问时对所有旧版本的惰性（lazy）迁移；Harness open 不扫描普通文档。

测试：只读的内存迁移、`tx.doc()` 迁移的回滚及其与后续编辑的合并、current/历史读取时的可回溯迁移、即使没有 JSON 变更首次成功的 `tx.doc()` 也写入版本 base、对更新版本的拒绝、迁移后 state/watch 在不写入的情况下水合（hydrate）、对迁移后基线的后续操作、存储版本的 fork 复制、未访问文档与定义不可用文档的保全、谓词失败在存储层准入前回滚，以及不依赖后端启发式的检查点饥饿（starvation）。

## 9. 会话文档 fork

利用固定测试会话（fixture）与条目到提交的映射，实现单例与家族文档的 `asOf`、`current` 与 `initial` 设置。

测试：不依赖定义的不透明存储版本复制、已退役的成员关系、新的子化身、其后的惰性迁移、惰性 `initial` 创建，以及排除任务与 Session 作用域的文档。

## 10. Chord 结构化数组操作

**由 Chord 负责的前置/集成：** 规范化的 Astra 不可变操作生成器必须能编码紧凑且可重放的数组变更；Pico 只负责验证并消费它。

改进规范生成器，使普通的位置变更能把分散的删除（removal）编码起来而不携带被保留元素的载荷。调用方不得手写操作。

测试：头部/尾部/中部/分散/全部/无删除，保留的 256 KiB 与 1 MiB 载荷，追加加删除，其后的嵌套/索引写入，精确重放，先前不可变修订版保持不变，以及 Astra 预备候选与不可变操作重放之间的相等性。一次预备好的文档变更仍然是一次 Session 提交；不采纳也不发布任何中间候选。

## 11. Chord 文档状态

内部使用 Chord 现有的 `ReplicatedStateSource` 附加（attachment）契约，但每次获取暴露一个已附加好的只读 `DocumentState`。它必须从当前不可变修订版出发在 O(1) 内原子地水合，并在其后发布精确的已提交不可变值/操作帧，而无需再建 tracker、复制值或重新 diff。释放（dispose）只注销这一个状态。Pico 仍是唯一的文档修改者。

测试：连续的 Chord 投递序列、原子的水合/订阅、覆盖排队发布而不重复应用的基线、精确的值与操作引用共享、退役为 `null`、绑定化身的重建、独立的状态释放、迁移后的水合、无定义的 fork 复制、tracker 缓存卸载，以及受信任变更的陷阱（footgun）。

## 12. 文档 watch

把非创建的 `watchDoc` 实现为绑定化身的 `WatchHandle`：缺席时返回 `undefined`，并在注册接收后续精确已提交帧的同时，在 O(1) 内原子地捕获当前不可变修订版。在 `start()` 之前，它的 value 保持为获取时的修订版。start 之后，对每个精确的值与操作批次调用一个串行化的异步监听器，并在回调之前立即推进 `watch.value`。保留提交的 Context 值，但不继承生产者的取消。

最多保留 100 个待处理帧（不含正在执行中的回调）。加入第 101 帧时，用一个携带最新精确不可变修订版与 Context 的根替换（root replacement）替换整个未投递后缀。不要估算序列化字节数、不要为了记账调用 `JSON.stringify()`、不要复制值、不要重放操作、也不要重新 diff 修订版。

测试：获取/返回/start 之间发生的更新；精确的值与操作引用；回调不重叠；监听器发起的提交；执行中回调期间到来的提交；start 之前与活跃回调背后的溢出；退役折叠进溢出重置；可重放的冗余结构提交；投递 Context 值的保留；保留的更早修订版保持稳定；受信任变更陷阱；start 之前与活跃期间的退役；重建；幂等的 stop；二次 start 被拒绝；获取期间的取消；回调期间的取消/关闭（不中止也不等待该回调结束）；监听器错误的结算；以及包 14 中由调用方拥有的清理。

包 13–20 是纵向里程碑。每一个都必须让一条真实的公开路径端到端跑通；不要把所有集成推迟到最后一个包。

这些里程碑的横切约束：

- 每种持久化的内置文档 kind 只引入一次，并带上它最终的 schema、历史/fork 策略、迁移、检查点谓词与公开挂载路径。当该 kind 落地时，把这一具体协议记录进规范性说明。不要添加临时内置 kind，也不要事后替换假 schema。
- 让所有可见进展保持持久。测试可以使用假模型（faux model）与假效果，但生产代码必须使用 pi-ai 导出的 `Models` 接口与真实任务链；不要添加 Pico 模型适配器或生产用的假后继。
- 每个已加载的 `ConversationView` 修订版都在存储层准入之前、从完整的候选 Session 提交准备出来。绝不通过订阅已提交的表/文档发布来重建视图。
- 一个里程碑可以留下后续操作未实现，但不得暴露临时公开门面。随着后续行为落地，逐步扩展最终的 §2.2 对象。

## 13. 可打开的 Harness

实现最终 §2.2 表面的第一个可用切片：带注册表的 `Harness.open/close`、`root(context, { init })`、`conversation(id)`、`createConversation({ ownership, init })`，以及通用继承的 Session 文档 API（`Harness extends Session`）。实现公开的 `Entry` 定义 token 与 `Conversation` 句柄，而不是添加中间的能力门面。`Conversation` 提供 `id`、绑定会话的 `commit()`、fork 感知的游标式 `entries()`、`context()`、`fork(at, { ownership, init })`，以及全部配置 getter/setter。

实现 §7.1 的注册表核心：`createRegistry()`、`tools.add`、`tools.wrap` 组合、`batch`、记住位置的键控排序、`Registration` 的 `dispose`、不可变 `snapshot()`，以及列表辅助方法。hook、task 与系统提示（system prompt）注册现在就存储并列出；它们的分发在包 14–16 落地。

把会话与条目语义提升到规范契约的水准：显式所有权、fork 感知的游标分页、head 查找、条目编辑，以及模型上下文推导。上下文削减（context reduction）包括最新编辑胜出、位置性 PR #9548 `SystemMessage` 重放、工具结果排序、fork 后缺失的工具结果、被排除的停止原因，以及相互分开的原始历史/模型上下文结果。

## 14. 持久任务运行时

以下推迟到后续包；不要在包 14 中打桩（stub）：

- 孤儿化会写入终态 `orphaned` 记录并退役任务文档。把输入 submission 标记为未应答以及清除运行控制，在包 15 补充，届时 submission 与运行控制才存在。
- `TaskRuntime.hooks`（hook 运行器）在包 16 随 hook 分发一起加入。包 14 加入 `runtime.registry`（该阶段的注册表快照）与 `runtime.models`。

- idle 等待直接统计活跃的非后台任务（整个 Harness 范围或目标会话内）。遍历所拥有的会话与后台边界将在包 18 取代这一做法。

用一个假的两阶段外部效果来测试真实运行时。验收场景是一个 intent/effect/outcome 任务在 intent 之后被中断、关闭、在同一存储上重开，并安全恢复到持久的终态回执。另外测试：检查点未变化时的故障注入、同阶段内的进展、取消优先级、抛异常的处理器、依赖、结果值与条目 ID、先写者胜出（first-writer-wins）的 memo、终态时移除检查点/memo、任务文档退役、没有 abort 标记或编造结果的 close/reopen、关闭期间不进行新的阶段/abort 分发、watch 清理、被后续注册解锁的阻塞任务、迁移失败时记录保持不变、同名任务替换后的移交、不向缺失或不兼容的定义移交、前后任调用不重叠、中止阻塞任务以 `orphaned` 加完整清理结算、标记之后 run 提交被拒绝，以及直接任务 abort 每个阶段的崩溃。

已实现的设计说明：每个任务转换都由一个在 Session 执行线上串行化的回调决定（预留、abort 标记、运行时提交，以及每个阶段之前的那一步）。`Tx` 没有任务替换；`runtime.commit()` 回调返回类型化的下一状态。`suspend()`、`hold()`、`quiescent()` 与公开的 `markTask()` 已从 §2.2 中移除。

- 所有权：`TaskOptions.ownership` 变为必填（`{ kind: "conversation" }` 或 `{ kind: "task", taskId }`）；`TaskRecord.owner?: TaskId`；子任务驻留在其所有者的会话中；`background` 仅用于会话拥有的任务；新的 task 或 conversation 所有权要求所有者存活（不能是 `completing` 或 `terminal`）。更新每个 `createTask` 调用点，包括工具的 `api.createTask`、示例与测试。存储：持久化 `owner` 与新状态（memory、JSONL、SQLite schema 就地修改；WIP 期间不做迁移），以及一致性用例。不建 owner 索引：调度器从它加载的活跃任务推导边。
- 状态：在 `TaskState` 与每个后端及状态扫描中引入真正的 `waiting { checkpoint, on, policy }` 与 `completing { outcome }` 状态；`NextTaskState` 增加 `waiting`；`runtime.outcomes()`；`inspect()` 报告 `completing`。移除 `after`（记录、选项、调度器依赖处理）。
- 调度器：等待中的任务在 `on` 里的每个任务都终态之前绝不预留（之后在其检查点处直接从 `waiting` 预留为 `running`），除非 abort 标记让它得以进入其 abort 处理器；对不属于它的任务使用 `on` 要求 `allSettled`；`on` 拒绝缺失任务、任务自身以及它的所有者链；failFast 在 reconcile 中，当出现被持有的或终态的非 `completed` 结果时，标记 `on` 中存活的被拥有兄弟任务。带存活普通被拥有工作的终态提交（无论任务写入还是调度器写入）变为 `completing`；当那份工作消失后，后续的调度器提交会将它们定案，并在每次提交与 open 时重新评估；调度器写入的 hold 把它的 Harness 清理（`settleSchedulerOutcome`）推迟到最终提交，任务写入的 hold 在 hold 时即落地其余写入；等待者与任务文档退役发生在最终提交。abort 调用只在普通被拥有工作消失后才开始（自底向上，依据已提交记录判断）。孤儿化只发生在 abort 调用本来就会开始之处，或在没有所拥有的东西存活时直接发生在 `abortTask()` 中，因此孤儿绝不持有。级联（规范 §5.4）：只有存活的所有者才级联（abort 标记或被持有的非 `completed` 结果）；终态所有者绝不级联；普通遍历与 idle 也跟随 task→task 边。`Conversation.abort(context, { background: true })` 的快照语义。
- 内置：generation 拥有它的工具任务，并在一个新的 `tools` 阶段中 `allSettled` 等待，该阶段运行旧 post-tools 的主体（§8.5）；串行轮次从 `pending` 一次创建一个工具；下一次生成由会话拥有；generation 的 abort 处理器为未开始的调用追加 `aborted` 结果。移除 `pi.post-tools`、`PostToolsTask`、`PostToolsHooks`（`afterTools` 移入 `GenerationHooks`）。拥有会话的工具任务在其结果条目之后持有 `completing`。事件：generation 的结果被提交时发出 `turn_end`（hold 或终态，以先到者为准）。
- 文档：撰写规范 §5.5 与 §12 的陷阱；更新 README（任务所有权、等待、`completing`、abort 顺序）、CHANGELOG，以及示例 12/22/23 和新的 `test/examples/24-child-tasks.ts`（带四笔支付的结账流程：failFast、`abortTask(checkout)`、崩溃与重开，各自打印结果）。

穷尽测试（新增 `test/harness-structured.test.ts` 并更新既有测试）：所有权校验（缺失所有权、跨会话子任务、后台子任务、所有者 completing/terminal）；allSettled 与 failFast 下的等待（failed、aborted、faulted、orphaned 的子任务；被持有的失败在失败子任务排干之前触发 failFast）；对已终态任务与非拥有任务的 `on`（仅限 `allSettled`）；按顺序等待子集；只生成不等待；任务写入与调度器写入结果的 `completing`（包括 hold 期间创建的工作、open 时的定案、对 completing 任务的 `abortTask()`、被持有的失败向下中止、等待者与文档退役只发生在最终提交）；跨三层的自底向上 abort 顺序（子任务终态记录先于父任务 abort 处理器启动），包括被中止的等待父任务；`on` 校验（缺失、自身、所有者链、空 `on`）；可以恢复时定义缺失的等待任务（被阻塞，被中止时孤儿化）；在收尾提交中创建被拥有工作（task 所有权被拒绝，被拥有会话中的任务则持有）；经由 task→task 与 task→conversation→task 边的级联；后台边界与 `{ background: true }` 中止；终态所有者绝不级联（讯问一个已完成或被 Esc 的子代理正常运行）；每个时点的崩溃/重开（create+wait 前后、子任务失败之后兄弟被标记之前、所有子任务终态之后父任务恢复之前、hold 与 abort 处理器期间）；generation 工具轮次的并行与串行，Esc 在工具之前、期间、之后，未开始的串行调用，generation abort 下故障的工具槽位，故障的 generation 保持运行控制直到其工具排干，generation 持有时 `turn_end` 先于后继的 `turn_start`，以及工具在其子代理扩展工作运行期间持有 `completing`。重跑所有既有测试套件；把 post-tools、串行轮次与依赖测试迁移到新形态，且不削弱它们。

## 23. 任务图视图

为 UI 与调试提供 Session 任务图的实时可观察视图，如同 `ConversationView` 之于会话：每个活跃任务连同其所有者边（会话或任务）、状态（`running`、`waiting on …`、`completing`）、后台标志与所拥有的会话，在每次提交之后作为复制状态或 watch 发布。`inspect()` 已经提供活跃任务记录的一次性快照。在最终一致性包之后对它做规定并构建。

规定于 `spec.md` §9.5：`Harness.taskGraph()` 与 `watchTaskGraph()` 按 ID 挂载每个活跃任务，连同其已提交状态（phase、wait、被持有的结果状态）、所有者边、标志与所拥有的会话。派生状态（`blocked`、`ready`、`on` 的存活部分）留在 `inspect()`。实现在 `src/harness/task-graph.ts`，测试在 `harness-task-graph.test.ts` 与生命周期测试中，展示于示例 24。
