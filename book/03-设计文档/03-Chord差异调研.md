# Chord delta 调研发现

> **本篇译自** [`docs/chord-delta-findings.md`](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/chord-delta-findings.md)——针对 Chord 差异的调研发现。

## 决定与范围

独立的按 ID 寻址的图（graph）追踪器实验已被移除。它解决了引用重指派与复制身份的问题，但其内存、导入与水合（hydration）成本对绘图工作负载而言不可接受。这否定的是这个被实测过的实现，而不是一切可能的图表示。

保留现有的树/路径 delta 实现、它的弱引用代理缓存修改，以及 spread 优先的克隆改进。保留弱缓存补丁并不表示其性能令人满意：永久驻留大幅改善，但穷尽式读取仍会分配数 GB 内存，而且变得更慢。

图原型从未有过包导出或 Chord 服务集成。移除它不会改变 State/ReplicatedState，也不会让 Pico 规范采纳图语义。既有 delta 的别名（alias）行为仍是另一个独立的正确性问题；本次调研并没有确立树协议在一般可变图意义上的正确性。

## 工作负载与测量规则

测量环境为 Apple M5 Max、128 GiB 内存、Node v26.0.0。文档包含 20,000 个 stroke（笔画），每个 stroke 带 100 个单独分配的 `{ x, y, pressure }` 点对象：共两百万个点，总计约 204 万个对象/数组。它不是打包的数值缓冲。完整遍历使用扁平的 strokes 数组；变更基准把 stroke 划分到图层中，并包含一个 200 KB 的字符串。

纯文档占用约 **139.5 MiB 的 JavaScript 堆**。它约 66 MB 的序列化表示是另一项测量。

- 使用独立进程，每个配置跑三次试验，并轮换变体顺序。报告中位数。大图/遍历 worker 使用 8 GiB 的 V8 堆上限。
- 把初始导入、快照发布、变更、flush、JSON 编码、解码与副本应用分开测量。夹具（fixture）构建不计入变更计时；导入一个新赋值的对象则计入。
- 分别测量仅生产者与生产者加副本的内存。在驻留堆测量之前，先用独立的调用帧释放原始图输入与已发出的批次；否则临时引用可能把整个额外文档钉住（pin）。
- 就绪/驻留堆在 GC 之后测量，相对于已预热的空进程。采样的堆包含临时分配与未回收垃圾，并不是精确的分配峰值。最大 RSS 包含堆容量与原生/运行时分配，不只是存活的 JavaScript 对象。
- 弱引用回收需要真实的 job/事件循环边界，而不是在循环之后同步调用一次 `global.gc()`。要让出、收集，并让 finalizer 运行。
- 序列化重放的校验在计时之外进行。图正确性必须比较身份/拓扑而不只是值：仅靠深相等会漏掉丢失的别名。
- 裸对象与最小代理两个对照组不做复制。它们是本地的成本下限，不是等价实现。

下文的历史测量除非明确说明，否则都早于最终的 spread 优先克隆改动。它们不是对当前源码的新测量。

## 操作日志与克隆基线的对比

`2c995acf4` 的操作日志（operation log）立即比较整个容器的赋值，并合并已记录的操作。`86bac52f9` 的基线设计标记脏路径，在 flush 时对照保留的副本进行比较，并刷新该副本。

一次图层交换可以说明差异。两个独立分配的图层可以有相同的几何、不同的名字。两种设计最终都只发出两个名字集合，共 **73 字节**，但仍要检查几何才能发现这个结果。基线还要额外刷新它的副本。输出极小并不意味着变更或 flush 就便宜。

为了公平比较克隆成本，只把基线的 `cloneJson` 辅助函数替换为 `2c995acf4` 中那个精确的辅助函数。diff、合并、基线刷新与代理行为都没有改变。这是早期的动态赋值辅助函数，不是后来的 spread 优先版本。

变更加 flush，单位毫秒：

| 工作负载 | 原基线 | 匹配克隆基线 | 操作日志 |
| --- | ---: | ---: | ---: |
| 单个 stroke 交换 | 0.114 | 0.086 | 0.085 |
| 交换 1,000-stroke 图层 | 89.940 | 47.924 | 21.048 |
| 交换 10,000-stroke 图层 | 906.390 | 483.264 | 214.425 |
| flush 前十次 1,000-stroke 交换 | 90.598 | 49.455 | 209.346 |
| flush 前六十次选中 | 0.121 | 0.101 | 2.346 |
| 交换不相似的 100-stroke 图层 | 12.097 | 7.515 | 168.273 |

批处理有利于基线，因为它只对最终脏区域比较一次；操作日志则在每次赋值时反复支付比较成本。十次交换恢复了原始值，三个变体都不发出操作。不相似的情形触发了操作日志的 4,096 元数据阈值，发布约 66 MB 的根替换；两个基线发出约 2 MB 的补丁。这一差异不是克隆辅助函数造成的。

全部 63 个独立进程配置都完成了。小夹具检查与全尺寸序列化重放检查通过；在被检查的情形中，原基线与匹配克隆基线发出完全相同的批次。右值（RHS）引用来自 `tracker.target` 以建模解包。这些基准**不能**确立一般性的别名正确性。

### 语义无法从通过的性能用例中推断

历史探查在别名、被持有的引用、重排索引与摘除/重插（detach/reinsert）附近发现了副本分歧，尽管既有测试全部通过。基线在共享初始对象以及 `unshift` 之后持有元素的情形中同样出现分歧。

例如，按引用选中一个条目随后编辑它，意味着两条生产者路径观察同一个对象。树副本持有两个独立的副本；它需要在两条路径上都有更新。跨数组插入持有引用还意味着后续写入必须跟随对象的新位置，而不是它的旧索引。无论是克隆基线还是在路径上缓存代理，都不能自动解决这些情形。

考虑过的其他方法：

- 赋值时深拷贝会改变别名语义，并增加遍历/分配。较早的克隆测量约为 1,000 个 stroke 7.4 ms、10,000 个 76.6 ms、20,000 个 153.8 ms。加入拷贝使一次大交换从约 213 ms 增至 385 ms。这些数字早于 spread 优先克隆。
- 持久化树共享未变化的结构，避免永久的完整基线副本。它们并不能独立解决存活别名或位置搬移问题。
- 基于路径的线上拷贝操作需要排序屏障：否则既有的操作合并可能在拷贝执行之前改变源。
- 声明式引用字段/应用 ID、更严格的树所有权与显式路径 setter 都会改变契约。没有选定替代 API；普通 JavaScript 变更语法仍是期望的接口。

## 图实验做了什么

每个对象/数组成为带数字 ID 的规范节点（canonical node）。标量内联存储；对象边引用规范节点。一个 map 按 ID 索引节点，一个弱 map 识别被导入的原始对象，惰性生产者代理暴露普通的变更语法。这是规范化的图存储，不是叠在第二份完整文档旁边的反向边索引。

线上引用使用 `["@", id]`，带有分开的对象/数组定义，以及按 ID 寻址的 set、delete、splice、length 与 release 操作。带修订版的快照支持恢复。副本在链接定义之前分配外壳，物化出带别名与环的真实 JavaScript 对象。增量更新保留被持有的副本身份；rebase 会重置身份。

已知对象的赋值变成引用写入。交换两个巨大图层不再需要遍历它们的后代。然而，全新独立重建出的相等对象是新身份，需要完整定义而不是一个小的值 diff。被摘除的节点保持驻留，直到显式收集。

五十个测试覆盖拓扑、环、被持有的引用、数组操作、导入回滚、修订版恢复、收集与确定性的混合变更。完整基准跑完 120 个独立进程，对图交换做值校验与持有身份检查。最初的完整遍历对比又增加了 12 个进程。这些用例上的正确性并没有让实现变便宜。

### 图的变更与发布成本

弱缓存改动之前的历史兄弟 delta（sibling delta）与图的对比，变更加 flush：

| 工作负载 | 树 delta ms | 图 ms | 树字节 | 图字节 |
| --- | ---: | ---: | ---: | ---: |
| 100 处分散编辑 | 0.265 | 0.158 | 5,243 | 2,235 |
| 交换 1,000-stroke 图层 | 21.523 | 0.002334 | 73 | 111 |
| 交换 10,000-stroke 图层 | 221.373 | 0.002584 | 73 | 109 |
| flush 前十次 1,000-stroke 交换 | 211.370 | 0.015083 | 2 | 471 |
| flush 前六十次选中 | 0.768 | 0.046125 | 66 | 102 |
| 追加一条新的 100 点 stroke | 0.011 | 0.095 | 3,357 | 7,567 |
| 全新等几何 1,000-stroke 图层 | 12.311 | 78.716 | 37 | 7,440,956 |
| 向 200 KB 字符串追加十个字符 | 0.010 | 0.000958 | 29 | 200,299 |

图的字节包含其信封（envelope）；树的字节是解码后的操作数组，不是路径字典编码。两种格式提供不同的身份保证。图为被取消的交换保留了有序的引用写入。它缺少字符串追加/截断压缩是原型局限，不是图寻址的固有成本。

把 JSON 编码/解码与副本应用计入后，新图层用例图花费 **165.773 ms**，树 delta 为 **12.017 ms**。10,000-stroke 交换管线为 **0.009958 ms** 对 **214.119 ms**。这些增量数字不包含初始导入与水合。

两万次热嵌套读取：图约 **20.84 ms**、树 delta 约 **9.12 ms**、最小代理约 **6.79 ms**、裸对象约 **0.082 ms**。这个小工作集只触及 1,000 个点，没有覆盖穷尽式读取的分配。

| 就绪时生产者堆 | 139.5 MiB | 430.4 MiB |
| 就绪时生产者加副本 | 279.3 MiB | 719.3 MiB |
| 初始导入 | 0.020 ms | 1,118.907 ms |
| 快照 flush | 169.218 ms | 594.904 ms |
| 快照线上大小 | 66,364,338 字节 | 147,487,101 字节 |
| 快照 JSON 编码 | 176.961 ms | 366.942 ms |
| 快照 JSON 解码 | 159.388 ms | 1,179.166 ms |
| 快照应用 | 0.027 ms | 1,417.161 ms |

快照阶段计时来自单独请求的一次 rebase。树的应用直接采纳已解码的快照；图的应用要校验并物化对象。RSS 包含更早的导入/水合分配，并不是最小存活集要求。

五次全新的 1,000-stroke 图层替换使图生产者堆从 **430.2 增长到 563.9 MiB**。显式收集在 **705.5 ms** 内移除了 510,010 个节点，发出 **7.14 MB** 的 release 批次，留下 **486.3 MiB** 驻留。生产者加副本从 **719.2 到 967.0 MiB**，收集后为 **831.2 MiB**。查找表容量与外部持有的值可能使其无法回落到就绪时的占用。

自动收集、不可变历史快照、有界日志、加固的传输限制与服务集成均未实现。

## 完整遍历暴露了内存问题

通过生产者代理读取每个点，会为几乎每个容器分配包装器。历史驻留堆结果（遍历与 GC 之后）：

| 变体 | 就绪 MiB | 完整读取后 MiB | 冷读取 ms | 热读取 ms |
| --- | ---: | ---: | ---: | ---: |
| 裸文档 | 139.47 | 139.49 | 8.00 | 2.95 |
| 最小缓存只读代理 | 139.47 | 452.50 | 705.10 | 550.35 |
| 弱缓存之前的树 delta | 139.26 | 3,525.93 | 2,720.98 | 470.89 |
| 图原型 | 430.39 | 2,159.75 | 1,437.65 | 388.74 |
| 历史匹配克隆基线 | 294.22 | 2,228.71 | 827.13 | 360.95 |

基线一行来自后来一次使用异步 GC 边界的三进程运行，不是从它的就绪堆外推的。其立即采样堆为 **2,245.37 MiB**，最大 RSS **2,456.30 MiB**。没有 diff 在运行：这是只读遍历。三个历史 tracker 都强缓存了包装器。

### 既有 delta：永久驻留已修复，分配量未修复

一次独立的配对前后运行测量弱缓存补丁：

| 指标 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 就绪时生产者堆 | 139.50 MiB | 139.50 MiB |
| 遍历、job 边界与 GC 之后的驻留 | 3,526.17 MiB | 203.54 MiB |
| 冷读取后立即采样的堆 | 3,531.93 MiB | 2,491.78 MiB |
| 最大 RSS | 3,858.11 MiB | 3,391.06 MiB |
| 冷遍历 | 2,397.40 ms | 6,298.76 ms |
| 同一 job 内热遍历 | 466.43 ms | 844.13 ms |

这些运行与上表相互独立。热时间是每进程收集之后三次遍历的中位数：第一次重建被收集的包装器，后两次复用同一 job 的缓存。

该补丁把公开代理与 entry/placement 元数据分离，使用弱普通缓存与化身安全的 finalizer 清理，并把显式别名元数据单独保存。被持有的后代保留祖先元数据，因此即使祖先公开代理已被收集，数组重排索引仍然有效。被赋值的已知代理会被解包，避免包装器嵌入原始目标。placement 复用防止重排索引或重新附加之后重复发出 splice。共享的处理器、惰性子 map 与 job 本地缓存减少了一些开销。

但一次点读取仍可能分配代理、处理器、追踪 entry、placement 记录、placement 集合、弱引用、缓存条目与 finalization 记录。跨约两百万个容器，这就是数 GB。在一次不间断的同步遍历中新建或解引用的 `WeakRef` 目标必须存活到该 job 结束。临时强缓存也要等到排期的微任务清理才消失。事后的收集无法阻止分配峰值。

收集之后高于裸文档的剩余约 **64 MiB** 是簿记/索引开销；其确切构成需要堆剖析才能确定。每个被访问容器约 **1.2 KB** 的额外立即采样堆是聚合平均值，不是逐分配的归因。

十一个隔离的 GC 回归测试覆盖未用代理回收、tracker 释放、持有身份与后代、数组重新获取/重排索引、别名重包装、摘除/重插、根 rebase、被阻塞的视图，以及重复的宽根读取窗口。对 10,000 对象根数组的十二个窗口保留了约 0.35 MiB 簿记。正常变更的正确性绝不能依赖 finalizer 及时运行。

该补丁没有解决一般性的树协议别名问题。通过 `tracker.target` 的批量只读检查可以避免代理构造，但通过它写入会绕过追踪。这条逃生通道并不能让普通的生产者代理遍历变便宜。

## 克隆布局：一个独立的较小改进

为什么 139.5 MiB 的文档加上一份基线占用了 294.2 MiB 而不是 279 MiB？在该 Node 版本上对 V8 布局的检查显示：

- 字面量 `{ x, y, pressure }` 占 48 字节，带三个对象内槽位。
- 通过动态赋值构建的 `{}` 占 56 字节，带一个未用槽位。
- 两百万个点乘以 8 字节，正好是额外的 **15.26 MiB**。

因此旧克隆占用约 **154.7 MiB**，而不是 139.5 MiB。差异并不是隐藏的代理分配。

浅层对象 spread 加上对对象值子级的递归替换保住了紧凑布局。数组保留其递归数组分支；null 原型对象保留 null 原型。全夹具仅克隆测量，每种方法三个全新进程：

| 克隆构建方式 | 额外驻留堆 | 克隆时间中位数 |
| --- | ---: | ---: |
| 动态属性赋值 | 154.725 MiB | 162.338 ms |
| 先 spread，再递归 | 139.466 MiB | 93.924 ms |

这个辅助函数已被既有 delta 采纳。回归测试覆盖分离的嵌套值、null 原型、继承名冲突、共享输入值的独立展开，以及已发布载荷的隔离。V8 布局/计时是引擎相关的。在布局探测中，`structuredClone()` 仍然产生 56 字节的点布局；JSON 往返产生 48 字节的点，但引入文本编解码与临时文本分配。

使用新辅助函数的基线预计需要约 **279 MiB** 来容纳文档加副本。这是从实测克隆大小得出的推断，不是对完整历史基线的重跑。该改进不解决遍历期间数 GB 的代理簿记。

## 驻留复现与出处

```sh

node --expose-gc packages/chord/test/delta-traversal.bench.ts --out /tmp/delta-traversal.json
```

## 对未来尝试的要求

从穷尽式生产者读取开始，而不是只测小的热工作集与变更/flush 基准。分开测量冷分配、热访问、跨 job 回收、持有身份、别名/重排索引行为、导入、水合与全新对象替换。绝不要把 GC 后驻留堆当作峰值内存来呈现、把微小补丁当作比较便宜的证明、或把成功的值重放当作身份正确性的证明。

本次调研中，没有任何一个被实测的设计能同时做到：低驻留与低瞬态内存、便宜的普通读取、便宜的大引用重指派，以及期望的宽泛可变 JavaScript 语义。
