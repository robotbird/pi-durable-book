# Pico5 规范说明书

Pico5 是一个持久化（durable）、可扩展的 agent harness（代理执行框架）。本文档为规范性（normative）文档。Pico5 按如下方式使用既有包中的类型：

```ts
import type {
  AttachedReplicatedState,
  Context,
  Draft,
  JsonRepresentation,
  JsonValue,
  ReplicatedState,
} from "@earendil-works/chord";
import type { Op } from "@earendil-works/chord/delta";
import type {
  AssistantMessage,
  CacheRetention,
  DeferredHandle,
  Message,
  Models,
  ModelThinkingLevel,
  TextContent,
  Tool,
  ToolCall,
  ToolReference,
  ToolResultMessage,
  Transport,
  UserMessage,
} from "@earendil-works/pi-ai";
import type { ExecutionEnv } from "@earendil-works/pi-durable/env";

type JsonObject = { [key: string]: JsonValue };
type TaskOutcomeError = { message: string; detail?: JsonValue };
```

Pico5 以 pi-ai PR [#9548](https://github.com/earendil-works/pi/pull/9548) 中的 transcript `SystemMessage` 契约为目标。该 PR 合入后，`Message` 将包含这一类型。

核心规则是：

> Session 以原子方式提交不可变的条目（entry）、完整的任务记录，以及由 Chord 追踪的文档。只有已提交的状态才是可观测的。

## 1. 术语与不变量

- **Session** 拥有一条变更线（mutation line），以及若干会话（conversation）、条目（entry）、任务（task）、提交项（submission）与文档（document）。
- **会话（conversation）** 是一个 transcript 作用域。它可以 fork 另一个会话。
- **条目（entry）** 是一条不可变的 transcript 记录。
- **任务（task）** 是附着在某个会话上的持久化状态机。
- **文档（document）** 是可变的 JSON 状态，由 Chord 操作和偶尔出现的完整基线（complete base）表示。
- **定义（definition）** 是描述单个文档或一族文档的类型化令牌（token）。
- **源（source）** 向 Chord 暴露已提交的文档变更，而不暴露任何可变对象。
- **回合（turn）** 是一次助手响应及其发起的工具调用。**运行（run）** 是从一条被受理的输入到最终答案之间的回合序列；回合边界（见第 6 节）位于这些回合之间。运行活跃期间，会话处于忙碌（busy）状态。

必须满足的不变量（invariant）：

1. 一次 Session 提交在所有记录写入与文档写入上是原子的。
2. 文档更新只有在其存储提交成功之后才会发布。
3. 一切可见的进展都是持久的。不存在易失性的发布路径。
4. 外部副作用不会在 Session 变更事务内部运行。
5. 条目与 ID 是不可变的，并且在一次已提交的写入之后绝不会被复用。
6. 文档草稿（draft）在其事务回调结算时被完全撤销：Session 会在那一刻同步地准备（prepare）或中止每一个尚未完成的变更。赋入草稿的值按值复制，且必须是严格 JSON。
7. 变更线会一直被持有，贯穿存储结算（settlement）与已提交状态的采纳。提交/关闭观察者只同步运行以捕获不可变状态；文档状态与 watch 的用户回调则在稍后、脱离变更线运行。
8. 不确定的存储失败对已打开的 Session 是致命的。它不发布任何内容，且必须重新打开。准备与检查点（checkpoint）失败发生在存储受理之前，会正常回滚。

## 2. 核心记录

具体的 JSON 表示可以添加簿记（bookkeeping）字段，但必须保持以下契约。

所引用的 pi-ai 成员是：

```ts
interface SystemMessage {
  role: "system";
  content: string | TextContent[];
  sections?: Record<string, string | null>;
  toolsAdded?: Tool[];
  toolsRemoved?: ToolReference[];
  timestamp: number;
}
```

在 pi-ai 中，`content` 在首条消息上承载基础提示词，在后续消息上承载附加的指令文本。`sections` 是一个有序的具名补丁（patch）：字符串表示添加或替换对应的节（section），`null` 则表示移除。在同一条消息内，`toolsRemoved` 先于 `toolsAdded` 应用。按 transcript 顺序重放全部系统消息，即得到生效的提示词与工具集。

Pico 总是写入 `content: ""`。每一个提示词组成部分——包括前言（preamble）在内——都是一个具名节，由会话的 agent 解析得出（第 7.4 节）。

ID 品牌（brand）仅存在于编译期。ID 与序列号（sequence）在内存、JSON、JSONL 和 SQLite 中都是普通数字。代码只在可信的创建或解码边界处施加品牌。独立的序列号品牌可以防止实体 ID 被用作文档的提交点。

会话的历史父子关系与任务归属（ownership）是彼此独立的：

- `parent` 控制继承的条目与历史文档。
- `owner` 记录任务归属，并为子树中止与空闲遍历串联起各个作用域。它不是访问控制能力（capability）。
- 创建时总是显式提供 `ConversationOwnership`。Session 从所指名的任务推导出持久化 owner 对应的会话；调用者从不自行构造持久化的 owner 对。

即使所属任务已进入终态（terminal），会话的 owner 仍保持记录。

### 2.1 条目与上下文

条目 ID 在整个 Session 内全局唯一且有序。`parent.at` 是父历史中对子会话可见的一个条目。

活动 transcript（active transcript）是从最新生效的 `head` 到尾部之间的原始条目区间。条目上的 head 会改变其后的上下文，但不会把更早的条目从存储中移除。fork 遍历时，先取子会话条目，再取父会话条目，直至每个 `parent.at` 截断点。

上下文推导：

1. 找到截止点（cutoff）处或之前、带有 `head` 的最新可见条目 `H`。
2. 令 `from = H.head`；若 `H` 不存在，则从 transcript 开头开始。
3. 从 `from` 扫描至截止点之间的可见条目。
4. 对每个目标条目，该区间内最新的编辑（edit）生效。`omit` 不贡献任何模型消息；`replace` 贡献其自身的 `messages`，取代目标条目的消息。
5. 若 `H` 存在，上下文条目为 `H` 加上该区间内的非 head 条目；否则上下文条目就是该区间本身。
6. 保留每一条位置式（positional）系统消息及其工具/节变更。
7. 把每个 assistant 消息的工具结果——即位于下一个 assistant 消息之前的那些结果——按工具调用顺序直接移动到该 assistant 消息之后、其间任何 user 或 system 消息之前。提供方协议要求结果必须紧跟其调用。
8. 为每一个没有对应结果的调用合成一个错误结果，例如 fork 截断之后或尾部被打断的情形。丢弃没有前导调用的工具结果。
9. 把无模型的条目，以及停止原因（stop reason）为 `aborted`、`error` 或 `deferred` 的 assistant 消息，排除在后续的提供方请求之外。
10. 把一条前面只有 user 消息的 system 消息移到最前面。一次运行的输入在 generation 渲染系统提示之前就已提交，因此一条记录、或压缩/重置之后的区段，否则会以输入开头。提供方只把位于开头的 system 消息视为初始提示与工具集；没有它，之后的工具变更会重写请求的工具列表，并使整个提示缓存失效。已存储的条目与 `contributions` 仍保持提交顺序。

视图（view）承载的是原始的活动条目。UI 归约与模型上下文归约是两个互不相关的消费者。更早的已存历史可以通过所属 `Conversation` 对象基于游标（cursor）的 `entries()` 扫描获得。

### 2.2 公开的 Harness 外部接口

这是面向宿主（host-facing）的 v1 API。Pico5 尚未实现，但在 package 24 期间，实现必须暴露这一形态，而不是另造一个不同的门面（facade）。

```ts
};
```

这一设计有意保留了 Pico3 中好用的宿主形态。它去掉了 Pico3 固定的 `rewindable()`/`sticky()` 访问器、命名空间路由器、语义视图事件以及手工的 Chord 视图桥接，代之以类型化的 Pico5 文档和结构化的会话 watch。`submit()` 以持久化方式受理（admit）用户输入或被动条目写入，并返回一个追踪其结算过程的 `Submission`。

`Harness.open()` 将 Session 绑定到一个由应用持有的注册表（registry）（第 7.1 节）。`createRegistry()` 始终持有内置任务定义（第 8 节），open 会拒绝快照中缺少其中任何一个的注册表。open 会把幸存的 `running` 任务改为 `pending`，让 `waiting` 任务继续保持等待，并为 `completing` 与 `waiting` 任务重新评估收尾（finalization）与 `failFast`（第 5.5 节）。它绝不因为任务的定义缺失或无法迁移而去迁移该任务或使其进入终态。这样的任务保持 `pending` 或 `waiting` 状态，并处于**被阻塞（blocked）**：调度器跳过它，并在注册表每次变化时重新考虑它（第 5.4 节）。凡被恢复过程触及的内置文档，都经由其普通的类型化访问路径完成迁移。open 不扫描、也不迁移其他文档。open 期间不会有任何处理器被分发。应用应当在 open 之前安装好各自的扩展，让被恢复的工作能立即继续；open 之后再安装也会解除相应的阻塞。

根会话始终保留 ID `ROOT_CONVERSATION_ID`（即 `1`）。`root(context, { agent, init })` 惰性地创建它：当根不存在时，Session 线上的一次提交会创建无主的根会话、运行创建钩子（creation hook，见下文）、通过 `configure()` 应用 `agent`，然后运行 `init(tx, rootId)`。当根已存在时，`agent` 与 `init` 会被忽略，不发生任何写入。重新打开时，按保留 ID 找到同一个根。agent 没有模型的会话会产生一个持久的 `no_model` 生成失败。

`resume()` 在运行期间是幂等的，仅用于启用调度。它不会重复 open 时的对账（reconciliation），并且在 close 之后抛出异常。必须在任何任务运行之前完成的工作，例如安装扩展或播种（seeding），都发生在 `resume()` 之前。请求进展的调用也会启用调度，因此它们绝不会在一个被暂停的 Harness 上等待：`Conversation.submit()`、`Conversation.compact()`、`Conversation.abort()`、`Submission.wait()`、`Harness.waitForTask()`、`Harness.waitForIdle()` 与 `Conversation.waitForIdle()`。被恢复的工作由它们启动。只读的观察者永远不会启用调度：`inspect()`、`getTask()`、`submission()`、`Submission.status()`、`usage()`、文档读取、所有会话读取、状态（state）与 watch，以及任务图。

`createConversation({ ownership, agent, init })` 与 `fork(at, { ownership, agent, init })` 原子地提交以下内容：会话本身、显式选择的归属、创建钩子创建的文档、`agent` 变更，以及 `init` 所做的每一次写入。首个输入是此后一次普通的 `submit()`。请求 ID（request ID）使对同一会话重试的 `submit()` 具有恰好一次（exactly-once）语义；必须在两次调用之间经受住崩溃的宿主，应先重新找到自己的会话，例如通过 `init` 写入的某个键。宿主调用者必须显式选择无主（ownerless）或任务归属；无论是 Harness 还是会话句柄，都不会从调用上下文推断归属。

每一个创建或 fork 会话的 Harness 提交，都会在同一提交内运行内置创建钩子，无论它是通过便捷方法，还是通过原生的 `tx.createConversation()` 与 `tx.forkConversation()`（例如在工具提交内部）。它运行在 `tx.createConversation()` 与 `tx.forkConversation()` 内部、二者返回之前，因此同一回调中稍后的 `configure()` 会覆盖它写入的副本。它创建空的 `pi.live`、`pi.inbox` 与 `pi.usage`，创建带有全新面向供应商 UUIDv7 的 `pi.provider`，并按如下方式处理 `pi.agent`：

- fork 无论其归属如何，都保留父会话 `pi.agent` 的 `asOf` 副本（第 3.7 节）。
- 新的任务归属会话获得 owner 任务所属会话已存 `pi.agent` 的副本，覆盖每个字段，包括 `instructions`。此后对 owner 的更改不会传播到子会话。owner 未设置的字段保持未设置，遵循宿主。
- 新的无主会话获得空的 `pi.agent`，即 `{}`。

如果提供了 `HarnessOptions.conversationCreated`，它随后会在同一提交中、以新记录运行，并覆盖每一条创建路径，这样宿主就能在每个会话里创建其应用所需的文档；记录中的 `parent` 与 `owner` 可用于区分 fork 会话与任务归属会话。在这里，表读取会抛出 `ReadAfterWrite`，与 `init` 中一样；抛出异常会让创建提交失败。随后，各便捷方法应用自己的 `agent` 变更并运行 `init`。扩展没有创建钩子，因此它们的钩子与节把自己文档的缺席视作其默认值。由普通 Session 创建的会话没有任何内置文档。

```ts
// In a tool's commit. The child starts as a copy of this conversation's agent: model, extensions, tools, cwd.
const child = await tx.createConversation({ ownership: { kind: "task", taskId: api.taskId } });
// A cheaper model, only the read tool, and its own worktree; everything else stays as copied.
await configure(tx, child.id, { model: haiku, tools: [readTool], cwd: worktree });
```

`init` 在会话创建之后运行，而会话创建是一次表写入，因此 `init` 内的表读取会抛出 `ReadAfterWrite`（第 4 节）。文档访问仍然可用。

内置 agent 文档定稿于版本 1：

| 字段 | 值 |
|---|---|
| kind | `pi.agent` |
| version | `1`（无迁移） |
| scope/history/fork | conversation、`rewindable`、`asOf` |
| schema | `AgentState` |
| `initial()` | `{}` |
| checkpoint | 每次变更都写完整基线（complete base） |
| view mount | `docs["pi.agent"]` |

它只存储有人为该会话做出的选择：扩展与工具的名称，绝不存储代码；除 `instructions` 之外也不存储任何提示词文本。代码在 agent 解析时按名称来自注册表（第 7.1 节）。`configure(tx, id, change)` 可在任何提交中编辑它，包括创建或 fork 会话的那次提交；`Conversation.configure()` 则在它自己的提交中完成编辑。`Conversation.agent()` 使用当前注册表快照与设置解析该文档，把缺席的文档读作 `{}`；它从不写入。

`configure()` 整体替换字段：给出了哪个字段，就用它替换已存储的那个；`null` 清除它；`undefined` 则保持不变。扩展与工具对象代表其名称，因此某个扩展被重新安装后，它的旧对象仍然能把它选中。

```ts
await root.configure({ tools: { remove: [editTool] } }, context);
await root.configure({ tools: { remove: [bashTool] } }, context); // edit is offered again
await root.configure({ tools: null }, context); // every tool of the selected extensions again
```

因此，UI 开关的做法是：读取当前值，再写入新值。`extensions` 的 `{ add, remove }` 对象编辑的永远是宿主的默认选择（第 7.1 节），而不是某个副本选择——无论那个选择本身是数组还是 `{ add, remove }` 对象；要编辑副本选择，请写一个由解析后 agent 的 `extensions` 计算得出的数组。

没有任何机制检查已存储的扩展名或工具名是否已安装。文档记录的是选择；注册表记录的是本进程此刻能执行什么。因此，一个已存储的名称可能处于未安装状态，例如在扩展重载期间、重启之后尚未安装时，或在缺少某个扩展的进程打开的 fork 中。解析会跳过它；文档绝不会因注册表的变动而被重写；当该名称再次安装后又会重新生效。

变更既不启动生成，也不追加系统条目。稍后的请求准备（request preparation）会把期望的提示词与工具同 transcript 历史进行比较，并追加所需的位置式系统基线或增量（delta）（第 7.4 节）。

内置 provider 文档定稿于版本 1：

| 字段 | 值 |
|---|---|
| kind | `pi.provider` |
| version | `1`（无迁移） |
| scope/history/fork | conversation、`latest`、`initial` |
| schema | `{ sessionId: string }` |
| `initial()` | `{ sessionId: uuidv7() }` |
| checkpoint | 每次变更都写完整基线（complete base） |
| view mount | `docs["pi.provider"]` |

这个 UUID 是面向供应商的会话身份，既不是数值型的 Durable `ConversationId`，也不是外层应用自己的 Session ID。每个新建的会话——无论是普通新建、任务归属、原生创建还是 fork——都在创建它的那次提交中获得自己的 UUID；fork 绝不复制父会话的 UUID。生成请求与压缩总结会把它作为 `options.sessionId` 传给 pi-ai。重置、压缩、更换模型与重新打开都不会改变它。没有该文档的旧对话会在首次生成或压缩的供应商请求之前，在 Session 线上创建并持久化一个；并发的调用者因此只会看到唯一的赢家。供应商自身的行为仍然适用：例如当 `cacheRetention` 为 `"none"` 时，Codex 会抑制缓存/会话身份。

缺少工具实现绝不会让请求失败。请求准备只提供 agent 已解析出的工具。如果重放出的工具状态仍在提供某个已无法解析的工具，追加的系统增量会在 `toolsRemoved` 中列出它；当它再次可解析时，更晚的一个增量会加入其当前声明。当模型调用了其请求未曾提供的工具，或其工具任务运行时实现无法解析（第 7.3 节），会产生一个错误工具结果，附带错误码为 `tool_unavailable` 的错误诊断（第 7.3 节），声明该工具不可用；运行继续进行，让模型能够作出反应（第 8.3 节）。

`HarnessOptions.settings` 保存 Harness 级别的运行策略：默认扩展选择、请求选项、重试、压缩（compaction）阈值、工具执行方式与队列模式。任何东西都不会复制或存储它。每个读取者都把它重新解析成 `Settings`——缺失的字段落到其内置默认值上，对象字段逐键合并——并把解析结果用于某一次决策（第 7.1 节列出了这些读取者）。因此，带 getter 的设置对象无需任何 Session 写入即可跟随用户的偏好。Settings 是同步读取的，因为队列模式要在 Session 线上读取。`stream` 被转发给生成请求；`stream.maxRetries` 是单次请求内部的提供方重试，而 `retry` 管辖持久的生成尝试（第 8.3 节）。设置变更不产生提交，也不发出事件。

```ts
// The user's settings, read live through getters.
class UserSettings implements HarnessSettings {
  readonly manager: SettingsManager;
  constructor(manager: SettingsManager) {
    this.manager = manager;
  }
  get stream() {
    return { timeoutMs: this.manager.get("timeoutMs") };
  }
  get compaction() {
    return { enabled: this.manager.get("autoCompact") };
  }
}
manager.set("autoCompact", false); // no Session write; every conversation follows at its next threshold check
```

`HarnessOptions.env` 依据会话的 ID、其 agent 的 `cwd`，以及一个用于读取已提交文档的 `DocumentReader`，构建该会话的执行环境。Harness 绝不在 Session 线上调用它，而是在每次用到时调用：

- 工具任务在每次执行时调用它，并把结果作为 `api.env` 传入（第 7.3 节）。恢复后的重跑会得到当时的会话环境，包括其当前的 `cwd`。抛出异常会成为该调用的一次普通错误结果。
- 生成的 `prepare` 为各节渲染器调用它一次（`input.env`，第 7.4 节）。抛出的异常会被上报，各节以 `env: undefined` 渲染。
- `runtime.env(context)` 为自定义任务调用它，并以该错误拒绝。

没有 `env` 选项，或它返回 `undefined` 时，就没有执行环境。昂贵的东西由宿主负责缓存，例如每个目录一个环境。扩展读取的是构建好的环境，例如 `env.cwd`，而绝不是某种描述符。若应用需要为每个会话保存超出一个目录的信息，就把它放进自己的文档，并通过 `target.read` 读取：

```ts
// Absent: the conversation runs locally. Only conversations with this document run in a container.
// Subagents do not copy it: their creator writes it too when they should run in the container.
const ContainerDoc = defineDoc<{ image: string }>({
  kind: "app.container", version: 1, scope: "conversation", history: "latest", fork: "current",
  initial: () => ({ image: "node:22" }),
});
const harness = await Harness.open(storage, {
  models,
  registry,
  env: async ({ conversationId, cwd, read }, context) => {
    const container = await read.snapshot(ContainerDoc, conversationId, context);
    return container !== undefined
      ? containers.env(container.image, cwd ?? "/work", context)
      : localEnv(cwd ?? process.cwd()); // cached NodeExecutionEnv per directory
  },
}, context);
```

agent 与设置的变更在其读取者解析它们时生效（第 7.1 节）。生成准备在每个请求中解析 agent 一次，并固定该回合的提示词、提供的工具、模型与请求选项。回合运行期间做出的变更在下次准备时生效。模型已调用的工具在其工具任务运行时解析；若届时其名称已不在 agent 的工具之中——因为过滤器、选择或注册表发生了变化——该调用会产生 `tool_unavailable`（第 7.3 节）。重试策略在生成对某次尝试的结果分类时读取，因为它管辖下一次尝试（第 8.3 节）。

`Conversation.commit()` 是绑定到该会话的 Session 提交。`tx.createTask()` 把 `TaskOptions.conversationId` 默认为被绑定的会话。`Conversation.entries()` 把查询绑定到该会话，并对其感知 fork 的已存历史进行分页；调用者无法换成另一个会话 ID。由于 `Harness extends Session`，Session 范围的通用文档操作仍然可以直接在 `Harness` 上使用。

`fork()` 要求提供一个具体可见的父条目与显式的归属，然后按第 3.7 节处理。`compact()` 在一次提交中受理一个手动压缩任务并返回其 ID，而不是它将来产生的摘要条目。该任务由会话拥有且不是后台任务，因此 `Conversation.abort()` 可以取消它，空闲等待也会把它计算在内。它不取得运行控制权，因此不会让会话变忙：它做摘要的同时会话继续工作，其摘要通过一个写入提交（write submission）放置——空闲时立即放置，否则在下一个边界放置（第 8.7 节）。`reset()` 持久化地受理一个写入提交，写入带 `head: "self"` 的 `pi.reset` 条目（第 8.1 节）；如果给出了交接（handoff）文本，则以 user 消息携带它，随后即返回；忙碌时，其放置遵循第 6 节，可能稍后才发生。可通过会话 watch 观察其放置。空闲等待并不保证排队的被动写入会被放置。

`abortTask()` 先提交 `abortRequested`，然后向活跃运行发信号并等待其加入（join）；随后调度器启动中止调用，并在其下一次对账提交中标记前台拥有的子树（第 5.4 节）。`Conversation.abort()` 撤回排队中的输入提交项，标记由普通归属遍历选中的非后台任务，向它们发信号，并且只有当该范围普通地空闲之后才完成。被动写入与后台子树得以存活。会话空闲意味着不存在从该会话选出的、仍然存活的非后台任务。Harness 空闲则从每个无主会话根出发应用同样的遍历。等待中的、被截止时间（deadline）阻塞的，以及 `completing` 的工作仍然存活，因此不算空闲。取消一次空闲等待只会中止那个等待者本身。

会话句柄是无状态的；请通过 `id` 来比较它们。宿主通过查找与扫描来发现会话。不存在创建监听器；任务图视图（第 9.5 节）、`inspect()` 与各空闲等待负责报告活跃工作。

`submit()` 在持久化受理之后即返回，而不等到结算。输入提交项在放置（placement）时以 Harness 时钟的时间戳创建一条 user 消息——若被立即放置，放置即受理；`whenBusy` 默认为 `followUp`。写入提交项走第 6 节的有序被动路径，且绝不启动生成。`Submission.wait()` 对输入提交项而言，只有在其答案产生或终态失败之后才结算；对写入提交项而言，在条目被放置或该写入永久无法放置时结算。取消 `wait()` 只取消那个等待本身，并不撤回提交项；`Submission.abort()` 才是显式的排队撤回操作。`Harness.submission()` 用于在重新打开后重新获取一个提交项；记录在结算之后仍然可以查询。

`abortTask()` 持久化地请求取消，并在标记被提交、所有活跃运行调用均已加入之后返回 `marked`；或在某个没有存活普通自有工作的被阻塞任务已被按 `orphaned` 结算之后返回（第 5.4 节）。中止调用在任务的普通自有工作不再存活时即启动；`completing` 任务只会被标记，其最终记录保留所持有的结果，并带有 `abortRequested: true`（第 5.5 节）。它不会等待终态结算。`waitForTask()` 观察终态接收。中止一个已是终态的任务返回 `terminal`；未知 ID 则拒绝。显式任务中止同样适用于后台任务。取消任务或取消空闲等待并不会中止工作。

`inspect()` 返回 Session 线上某一时点的活跃工作，供 open 之后的恢复决策、观察者与诊断使用。它不写入任何内容，不启用调度，也不运行任务代码。每个活跃任务携带其在当前注册表下的状态：`running` 表示有活跃调用；`completing` 表示持有结果；`waiting` 带有它仍在等待的活跃任务、其 `on` 中仍然存活的部分，或在标记中止时其存活的普通自有工作（第 5.5 节）；`ready` 表示下一次调度轮会预留它，当其定义较新且带有 `migrate` 时附有 `migrates`；或者为 `blocked`（第 5.4 节）。迁移只有在调度器实际尝试过之后，或较新的定义没有 `migrate` 时，才显示为失败；检查绝不会为了弄清这一点而运行迁移。阻塞原因是推导出来的，从不存储。排队与已放置的提交项补全了这一视图。已完成的任务、已结算的提交项、transcript 以及文档使用各自的 API。

`Conversation.viewState()` 以一个一次性的只读 Chord 状态返回其当前的结构化挂载（mount）。`Conversation.watch()` 原子地捕获该不可变修订，并注册以接收此后精确的完整提交帧。它的 `WatchHandle` 使用与第 9.2 节 `watchDoc()` 相同的串行化异步、有界缓冲契约。两者都不携带语义事件，也不拥有第二个持久化权威。

`close()` 封闭（seal）变更受理与任务预留，向各调用发信号，并在该封闭点终止每一个文档状态、视图状态与 watch：在 close 期间才结算的提交不会向它们发布任何内容，各状态保持其最后一个值。在 Session 线之外，它让已受理的存储提交完成结算，加入任务、工具与钩子调用——包括忽略其信号的代码——然后关闭 Storage。一旦 `close()` 完成，本 Harness 的任何调用代码都不再运行，也没有任何处理器持有 Storage，因此新的 Harness 可以打开同一个 Storage。已在运行的 watch 回调仍归调用者所有，可以独立完成。close 不写入任何任务结果。取消 `close()` 调用只取消那个等待本身；关闭流程继续进行，之后的每一次 `close()` 都在等待同一次关闭。

句柄属于那个打开着的 Harness，重新打开后必须重新获取。close 一旦开始，所有新的 Harness、会话与提交操作都会拒绝，`resume()` 会抛出异常。对于封闭时已排在 Session 线上的操作，提交会正常结算（第 4 节），读取会正常完成。等待、状态与 watch 会拒绝，但有两个不需要后续提交的例外：已结算提交项的 `Submission.wait()` 会正常返回，对缺席文档的获取会返回 `undefined`。其中的 `inspect()` 会报告 `scheduling: "closing"`。
