## 3. 文档

作用域（scope）直接决定文档（document）的归属与生命周期（lifetime）。只有会话文档才会声明历史（history）与 fork（分叉）行为。

```ts
type LatestConversationSemantics = {
  readonly scope: "conversation";
  readonly history: "latest";
  readonly fork: "current" | "initial";
};

type RewindableConversationSemantics = {
  readonly scope: "conversation";
  readonly history: "rewindable";
  readonly fork: "asOf" | "current" | "initial";
};

type DocumentSemantics =
  | { readonly scope: "session" }
  | LatestConversationSemantics
  | RewindableConversationSemantics
  | { readonly scope: "task" };

type CheckpointInfo = {
  /** Deltas already stored after the newest base, excluding this change. */
  readonly deltasSinceBase: number;
};

type CommonDocDefinition<T extends JsonObject> = {
  readonly kind: string;
  readonly version: number;
  initial(): T;
  migrate?(value: JsonObject, fromVersion: number): T;
  checkpointWhen?(value: Readonly<T>, ops: readonly Op[], info: CheckpointInfo): boolean;
};

type DocDefinition<T extends JsonObject> =
  CommonDocDefinition<T> & DocumentSemantics;

type DocFamilyDefinition<T extends JsonObject, I extends JsonValue> =
  Omit<CommonDocDefinition<T>, "initial"> & DocumentSemantics & {
    readonly family: true;
    initial(seed: I): T;
  };

declare const docType: unique symbol;

  readonly definition: D;
  readonly [docType]?: T;
}
interface DocFamilyToken<
  T extends JsonObject,
  I extends JsonValue,
  D extends DocFamilyDefinition<T, I>,
> {
  readonly definition: D;
  readonly [docType]?: T;
}

type SessionDocToken<T extends JsonObject> = DocToken<
  T,
  CommonDocDefinition<T> & { readonly scope: "session" }

type ConversationDocToken<T extends JsonObject> = DocToken<

  I,

  T,
  I,
  DocFamilyDefinition<T, I> & RewindableConversationSemantics
>;

  T,
  I,
  DocFamilyDefinition<T, I> & { readonly scope: "task" }
>;

function defineDoc<T extends JsonObject>(

): SessionDocToken<T>;

  },
```

校验规则：

- 版本号必须是正整数。
- 当令牌（token）的作用域或会话 history/fork 策略与持久化下来的实体（incarnation）不一致时，类型化访问会被拒绝。迁移不得重新解释这些生命周期语义。
- Session 文档只保留当前值（current-only），并且属于 Session 本身。关闭再重新打开 Session 不会使它们退役（retire）。
- 会话文档必须声明 `history` 与 `fork`；`fork: "asOf"` 要求 `history: "rewindable"`。
- 任务文档只保留当前值，永远不会被会话 fork 复制，并会在其所属任务进入终态（terminal）时原子地退役。
- `initial()` 与 `migrate()` 返回 JSON 对象。

`checkpointWhen()` 仅用于选定完整的存储基线（base）以限制重放（replay）长度；它不会改变作用域、生命周期、history 或 fork 语义。

内置文档的具体分组与语义在实现各内置定义时声明。通用文档机制不会为模型、工具、收件箱（inbox）或展示（presentation）状态做任何特殊处理。

### 3.2 记录与生命周期

每个持久化的文档实例都对应一条 `DocumentRecord`：

```ts
type DocumentRecord = {
  readonly id: DocumentId;      // unique incarnation
  readonly kind: string;        // stable definition kind
  readonly key?: string;        // families only
  readonly createdAt: Seq;      // stamped by the committing storage
  readonly retiredAt?: Seq;
} & (
  | { readonly scope: { readonly kind: "session" } }
  | ({ readonly scope: { readonly kind: "conversation"; readonly conversationId: ConversationId } } & (
      | { readonly history: "latest"; readonly fork: "current" | "initial" }
      | {
          readonly history: "rewindable";
          readonly fork: "asOf" | "current" | "initial";
        }
    ))
  | { readonly scope: { readonly kind: "task"; readonly taskId: TaskId } }
);

type DocumentCreate = DocumentRecord extends infer Record
  ? Record extends DocumentRecord
    ? Omit<Record, "createdAt" | "retiredAt">
    : never
  : never;
```

`id` 永不复用。把相同逻辑 kind、作用域与 family key 的文档退役后再重建，会产生一个新的实体（incarnation）。是否属于某个实例由半开区间 `createdAt <= at < retiredAt` 判定；尚未退役的实体没有上界。在同一次提交中创建即退役的实体，其生命周期为空。

单例（singleton）在逻辑上由 kind 与作用域标识；族（family）在逻辑上由 kind、作用域与 `key` 标识。记录会保留作用域与会话 history/fork 语义，这样即使提供定义的扩展代码不可用，已有数据也不会消失。定义版本归属于存储的基线与增量（delta），因为同一个实体里可能同时含有由多个定义版本写入的记录。`DocumentCreate` 并非又一条持久化记录；它是同一作用域联合类型去掉了由存储分配的生命周期字段之后的形态。

会创建 ID 的事务（transaction）方法都是异步的，因为远程存储可能需要持久化地分配全局唯一的数字 ID。创建会话总是要求显式给出归属（ownership）；没有任何事务包装器会自动注入当前执行的任务。对于任务归属，调用方只需提供一个类型化的任务 ID；Session 会从该任务最终的候选记录（candidate record）推导出持久化的归属会话。

归属任务可以在同一事务中更早地提交或暂存。在 Storage 准入（admission）之前，Session 会拒绝新建任务或会话的以下归属者（owner）：缺失的、处于 `completing` 的、已终态的或带有中止标记的——判定依据是事务内归属者最终的候选记录。因此，任务无法在结束自己的那次提交中再创建归属于自己的工作。显式 `conversationId` 与其归属者会话不一致的子任务，以及设置了 `background: true` 的子任务，会以同样的方式被拒绝。已有的归属边在其归属者此后才结束时依然有效。创建会话返回的是一条惰性记录（inert record），绝不是可操作的句柄。`forkConversation()` 还会额外校验一个可见条目，并应用第 3.7 节的规则。只有公开的类型化 `tx.doc()` 具备获取即创建（get-or-create）语义；内部的 fork 复制可以不经定义、直接从存储值创建新实体。`tx.doc()` 接收定义令牌，由令牌提供其静态类型、初始化器（initializer）、迁移与检查点（checkpoint）策略。由令牌保留作用域的重载只要求调用方提供具体的会话/任务 ID；对族而言，还要提供 key 与创建种子（seed）。普通定义无需注册，打开时也不会扫描普通文档。

- 已存在的实例按第 3.6 节惰性地重建并迁移。通过 `tx.doc()` 触发的迁移会暂存在其外层事务中。
- 缺失的单例会调用令牌的 `initial()`；缺失的族成员会调用 `initial(seed)`。创建时会存入一个初始基线。
- 对同一逻辑地址的首次获取会在进入 await 之前完成记忆化；此后同一事务中的再次获取都会返回同一个草稿（draft）。对缺失的族而言，第一次调用传入的独立种子生效，后续种子一律忽略。
- `snapshot()`、`snapshotAsOf()`、`documentState()` 与 `watchDoc()` 从不创建文档，也不持久化迁移。所请求的实体不存在时返回 `undefined`；对重建出的值只在内存中迁移。
- 任务作用域的 `tx.doc()` 依据事务内最新的候选任务记录进行校验，并回退到已提交状态。这一内部校验不算调用方的表读取，不会触发 `ReadAfterWrite`。其会话从任务记录推导得出。
- `retireDoc()` 只解析逻辑地址，不会创建它。若要退役的草稿已被获取过，会先持久化其最终内容再退役。同一事务中随后对该地址的 `tx.doc()` 会创建一个新实体，配备新的草稿与 ID。
- 终态候选会拒绝其后的任务文档访问。终态结算（settlement）会同时退役既有的任务文档与同一事务中较早创建的任务文档。
- `snapshot()` 返回当前可共享的不可变修订（revision）。修改它或任何被保留的后代都不受支持；需要可变所有权的调用方必须先自行复制。
- `documentState()` 返回一个绑定到某一已提交实体的一次性只读 Chord 状态。
- `tx.doc()` 为该事务返回一个可撤销的 Astra 覆盖层 `Draft<T>`。
- 历史读取绝不会在过去创建文档。

`snapshotAsOf()` 仅适用于可回溯（rewindable）的会话文档。它会校验 `at` 在所请求会话的祖先链上可见，选出拥有该条目的祖先会话，然后查找其创建/退役区间覆盖该条目所在提交的逻辑单例/族实体。它绝不从今天的实体出发，也绝不创建实例。这样的实例不存在时返回 `undefined`。

当 `B` 在条目 `E` 处 fork 了 `A` 之后，查询 `B` 在继承来的 `E` 处的状态，读到的是 `A` 的历史实例；`B` 被复制出来的实体创建得更晚。如果实例曾被退役又重建，历史查找会选择在目标提交时仍然存活的那个实体。

### 3.4 变更所有权

Pico 直接采用 Chord Delta 的 Astra 不可变事务形态：

```ts
interface Prepared<T extends object> {
  readonly base: T;
  readonly value: T;
  readonly ops: readonly Op[];
  readonly baseRevision: number;
  abort(): void;
}
interface Change<T extends object> {
  readonly state: Draft<T>;
  prepare(): Prepared<T>;
  abort(): void;
}
interface Tracker<T extends object> {
  readonly value: T;
  readonly revision: number;
  beginChange(): Change<T>;
  prepareReplace(value: T): Prepared<T>;
  adopt(prepared: Prepared<T>): void;
}
```

每个已加载的文档拥有一个追踪器（tracker），其 `value` 就是该文档当前不可变的修订。不可变性是一份受信任的所有权契约，而非运行时冻结：修订及其所有后代在移交给 tracker 之后绝不能再被修改。`prepare()` 撤销草稿，产出与之脱离的自包含操作，并在 Storage 准入之前用经过优化的不可变应用器（applier）计算出 `value`。未发生变化的子树与 `base` 结构共享。操作的放置载荷也可以与 `value` 共享；修改已准备好的操作或不可变修订都是不受支持的。对于被证明为无操作（no-op）的变更，Astra 会保留一个空操作批次；但对非空的结构批次，Pico 不会额外执行整值相等性比较。

`abort()` 是幂等的。`adopt()` 只接受该 tracker 在其当前修订上准备出的结果，随后仅执行一次同步指针交换，指向已经算好的不可变 `value`。它不做任何 diff、应用、分配或回调。Session 线允许每个 tracker 至多存在一个进行中的变更，并确保在准备、Storage 结算与采纳之间没有任何结果过期。

首次 `tx.doc()` 获取会调用 `tracker.beginChange()`，并在整个可能异步的 Session 回调的剩余部分里记住该变更的草稿。

事务行为：

```text
begin transaction
  acquire and memoize document changes by logical address
  mutate revocable Astra overlay drafts
callback settles
  seal Tx; synchronously prepare or abort every open change, revoking every draft
  if any acquisition is pending: abort open changes, reject, then drain and abort it
callback fails with no pending acquisition
  abort every open change; persist and publish nothing
callback succeeds with no pending acquisition
  prepare every open change -> immutable next revision + self-contained Chord Op[]
  Session evaluates each required/ordinary document write exactly once
  Storage.commit persists the atomic batch while the Session line remains held
storage succeeds
  adopt every prepared change by pointer swap and enqueue immutable revision/ops publication
  commit listeners, including conversation view mounts (section 9.3), capture it synchronously
  release the line; invoke listeners later
storage fails
  abort every prepared change, poison Session, and publish nothing
```

在封闭之后才落定的未决获取绝不会暴露草稿；其变更被中止，其 promise 以拒绝告终。Session 会在释放该线之前观察到每一次这样的结算。初始化器、迁移与替换用的根值来自调用方代码：Session 会先把每个值复制为内核独占所有，拒绝任何不是严格 JSON 的值，然后才让它成为不可变的 tracker 修订。已加载的和 fork 复制得到的根值本就是 Storage 给出的、已分离的严格 JSON，无需再次复制即可进入 tracker。Chord 的 `track()` 与 `prepareReplace()` 以 O(1)、无需遍历的方式取得所有权，因此它们收到的每个根值都必须来自上述来源之一。迁移回调绝不会收到活的 tracker 修订。

准备、校验或检查点失败发生在 Storage 准入之前，会正常回滚。Session 不会对准备好的操作或选定的基线做严格 JSON 遍历：根值在入口处检查，每次草稿放置由 Chord 检查，因此每个修订、操作载荷与基线在构造上就保证是严格 JSON。tracker 的品牌标记（branding）与 `baseRevision` 负责强制所有权与过期检查；Session 绝不会用调用方创建的 prepared 值取而代之。准备好的不可变候选值本身就会成为被采纳并发布的值。只有当 Session 选定基线时，Storage 才会收到这个完整值；否则它只收到准备好的操作批次。已存在且处于当前版本的文档，若批次为空，则不写入任何内容，也不发布。若非空结构批次的最终值与基线深度相等，它仍是一次有效的持久变更与发布。创建与必需的版本转换即使准备好的批次为空也仍会写入基线；等值的版本基线不会发出 watch 更新。

赋入草稿的值会被立即按值复制；重复赋值彼此独立。Chord 在复制的同时检查每一次放置；当值不是严格 JSON 时——`undefined` 的数组元素或嵌套对象值、非有限数、函数、symbol、bigint、访问器（accessor）、symbol 键、稀疏数组，或原型既不是 `Object.prototype` 也不是 `null` 的对象——它会在草稿发生任何变化之前、恰好在违规的那次赋值处抛出异常。直接把 `undefined` 赋给对象属性会删除该属性。回调结算之后，草稿的读取与写入以及所有 `Tx` 操作都会以拒绝告终。准备好的不可变值仍可被 Session 自有的检查点逻辑与 Storage 准备阶段读取。

```ts
let escaped: Draft<LiveState> | undefined;
await session.commit(async tx => {
  escaped = await tx.doc(LiveDoc, conversationId);
}, context);
escaped!.generation = undefined; // throws: the draft was revoked
```

在归属回调结算之前就修改草稿的「发射后不管」（fire-and-forget）式工作可能悄然混入该事务，属于不受支持的行为。

### 3.5 基线与检查点

创建时总是存入一个完整基线。

对于普通的后续变更，存储记录是不是基线只由定义决定：

```ts
const useBase = definition.checkpointWhen?.(candidateValue, ops, { deltasSinceBase }) ?? false;
```

Session 会在 tracker 准备完成之后恰好求值该谓词一次。`deltasSinceBase` 统计该实体最新基线之后已存储的增量数量，不含正在求值的这次变更。Storage 在物化（materialize）当前值时报告这个数；Session 在每次被采纳的写入之后递增它，并在每次写入基线之后清零，因此求值过程不需要任何 Storage 读取。创建与版本转换要求基线，不会调用该谓词。随后 Session 只把选定的表示交给 Storage：

```text
required or predicate true -> base with complete value
otherwise                  -> delta with the prepared Chord operation batch
```

Chord 的根替换（root replacement）操作仍算增量，除非定义选中了检查点；它本身并不授权回收（reclamation）。谓词失败会在 Storage 准入之前中止已准备好的事务。Storage 不执行任何定义代码，也绝不会在已选定增量时收到一个被弃用的完整候选值。

- 对 Session 文档、任务文档与 latest 会话文档而言，提交一个基线即允许对更早的记录做物理回收。
- 对可回溯会话文档而言，基线用于限制重放长度，但绝不允许删除可寻址的历史。
- 从不打检查点的定义可能造成无界的重放尾部。这属于定义的 bug，而不是后端启发式处理。
- Storage 不会统计编码后的字节数，不会与 `initial()` 的结果比较，也不会自行发明检查点。

定义可以直接约束重放长度：

```ts
checkpointWhen: (_value, _ops, info) => info.deltasSinceBase >= 31
```

变更频繁的 live 文档可以在自己变空时打检查点：

```ts
checkpointWhen: (value, _ops) =>
  value.generation === undefined &&
  value.tools === undefined
```

### 3.6 版本与迁移

一个迁移回调要处理所有受支持的旧版本。

```text
stored == token -> use value
stored < token  -> call migrate(value, storedVersion)
stored > token  -> reject typed access
no migrate      -> reject older stored version
```

`migrate()` 必须是纯函数，并返回完整的当前版本值。迁移由访问驱动：`tx.doc()`、`snapshot()`、`snapshotAsOf()`、`documentState()` 与 `watchDoc()` 都经由本次调用传入的令牌来重建并迁移。Harness 打开时不会清扫普通文档。

- 只读访问只在内存中迁移，从不写入。它可以把 tracker 连同那份迁移后的不可变修订与旧的存储版本标记一并缓存；下一次成功的 `tx.doc()` 访问仍会写入所需的当前版本基线。缓存的 tracker 只服务于与其值被物化时所用版本相匹配的令牌。以任何其他版本发起的访问——例如来自重新加载的扩展代码的令牌——会丢弃该缓存并重新加载存储值，因此每个令牌要么从存储版本开始迁移，要么拒绝比它更新的版本。迁移总是从一份已分离的存储值开始。`tx.doc()` 把迁移暂存在其外层事务中；回调失败则什么都不持久化，此后的草稿编辑会合并为一次最终的必需基线写入。
- 可回溯的历史不会被改写。当前值与历史重建值都在重放完成之后迁移。
- 任何存储版本迁移之后的第一次 `tx.doc()` 事务都会写入必需的当前版本基线，即使迁移后的 JSON 与原值深度相等。
- fork 从 Storage 取得选定的存储值/版本，而不是取自类型化的已迁移 tracker 缓存。子代复制这份存储值/版本对，并在之后类型化访问时才迁移。
- 未被访问的文档，以及定义不可用的文档，都原样保留其存储实例、版本与字节。

### 3.7 Fork

会话 fork 指向一个具体的可见条目 `E`。

子代 transcript 包含直到 `E`（含）的条目，即使同一次提交还追加了更晚的条目。`E` 处的文档状态就是包含 `E` 的那次提交的最终状态。不同的文档状态需要分开提交。

每个会话文档遵循其 `DocumentRecord` 中持久化的 history/fork 策略：

| 会话文档设置 | 子代取值 |
|---|---|
| `fork: "asOf"` | `E` 所在提交时点的父代值 |
| `fork: "current"` | fork 提交执行时选定的父代已提交值 |
| `fork: "initial"` | 不复制任何实例；首次在子代访问时由初始化器创建 |

`current` 与 `asOf` 会复制逻辑上存在的会话单例与族实例，并原样保留未知定义及其存储版本。复制出的值成为独立的子代实例，拥有新的 ID 与初始基线。`initial` 不复制任何实例；子代中的首次访问会用所提供的定义创建它。任务文档与任务永远不会被复制。Session 文档保持共享，且不可回溯。

fork 复制读取的是已提交的存储值，而不是类型化的 tracker 缓存。因此，如果创建 fork 的事务同时还写入父代的某个 `fork: "current"` 文档，该事务会被拒绝；请先提交父代变更，让 fork 拿到一个无歧义的存储源修订。

fork 会暂存后端侧的 `document.copy` 命令，命令中携带子代的创建记录以及精确的源实体/点位。Storage 会物化每个源，并把其存储值/版本持久化为子代独立的初始基线；远程 Storage 在服务端完成这一步。每次复制读取的都是已提交的、批次之前的源状态，与写数组中的顺序无关。被选中的源不得在同一批次中创建、修改或退役。复制与会话创建、覆盖（override）、注册表写入以及其他变更保持原子性。

未被访问的副本只在 Session 内存中保留一个描述符（descriptor）。创建事务内部的类型化访问会惰性读取已分离的源值，在需要时迁移，并用一个包含最终准备值的普通子代创建来替换该副本。无定义的副本发布的是显式的 `document.copy` 元数据而非值。该元数据只是宣告初始状态由 Storage 支撑，绝不会被解释为文档值。文档状态、watch 与挂载视图（mounted view）按如下方式注水（hydrate）：在 Session 线上原子地捕获基线与订阅——捕获时已存在的更晚提交直接成为基线，注册之后才提交的变更则以推送方式送达。发布与 watch 是收敛（convergence）机制，不是审计流。挂载的聚合体（aggregate）必须在一次 Session 线操作中取得其全部文档基线并完成订阅，这样它绝不会暴露同一次提交内部的混合状态。

## 4. 事务与存储所有权

Session 的提交回调可以是异步的。从回调执行、准备、存储结算、已提交基线的采纳，到发布入队，整个过程都由它持有 Session 变更线。提交观察者在变更线上运行；文档状态与 watch 的用户回调稍后运行。外部的模型、进程、工具、网络与人为影响都在变更线之外发生。`subscribeCommits()` 在采纳之后于变更线上同步观察完整的不可变发布（publication）。`subscribeClose()` 在关闭开始时（变更准入封闭之后）于线上同步观察关闭；Harness 在该点停止 watch 并向任务调用发出信号。两者都返回幂等的释放器（disposer）；它们的监听器不得抛出异常、不得阻塞，也不得调用 Session API。文档状态订阅者与 watch 监听器仍然稍后在线下运行。

```ts
await session.commit(async tx => {
  const conversation = await tx.conversation(conversationId); // table read
  const live = await tx.doc(LiveDoc, conversationId);

  await tx.appendEntry(conversationId, message);     // first table write
  delete live.generation;                            // document mutation remains valid
  await tx.createTask(Follow, {}, { ownership: { kind: "conversation" }, conversationId }); // further table writes are fine
}, context);
```

变更准入发生在提交回调开始之前的 Session 线上。关闭（close）会封闭（seal）变更准入与任务预留。已准入的提交会在存储关闭之前完成结算。提交一旦获准入，调用方的取消既不会打断存储结算，也不会撤销该提交。取消对关闭的等待不会重新打开准入。

表规则：

- 表指的是会话、条目、任务与提交项这四张表。
- 第一次表写入之前允许进行表读取。
- 第一次表写入之后的任何表读取都会抛出 `ReadAfterWrite`。
- 表写入之后，文档访问与读己之写（read-your-writes）依然可用。
- 各创建方法会返回所创建的 ID/记录；调用方无需再把它读回来。

存储所有权（storage ownership）：

- 提交参数在 `Storage.commit()` 结算之前处于借用（borrow）状态。
- 结算之后仍要保留的任何东西都会先被分离（detach）。
- 内存存储会递归复制被保留的 JSON 容器。
- JSONL 与 SQLite 通过序列化与解码后的索引来分离。
- 每次存储读取都返回一份已分离的 JSON 值。
- 不可变字符串可以共享；可变数组与对象则不可以。
