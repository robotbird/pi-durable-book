## 7. 扩展、钩子、工具与系统提示

### 7.1 扩展、注册表与 agent 解析

扩展（extension）代码通过一个由应用持有的扩展注册表（registry）进入 Harness。扩展是一个具名的捆绑包，内含工具（tool）、提示章节（prompt section）、钩子（hook）、工具与章节的包装器（wrapper），以及任务定义。注册表是进程本地的，其存续时间可以长于某个 Harness 实例，且不会被持久化；持久状态只保存在会话（conversation）、条目（entry）、任务与文档中。会话在其 `pi.agent` 文档中按名称选择扩展（见第 2.2 节）。

```ts
type DocumentReader = Pick<Session, "snapshot" | "snapshotAsOf">;

type PromptInput<Tool extends ToolRegistration = ToolRegistration> = {
  readonly conversationId: ConversationId;
  /** The request's resolution; `agent.tools` are the tools offered in this request. */
  readonly agent: Agent<Tool>;
  /** Built by `HarnessOptions.env` for this preparation (section 2.2). */
  readonly env: ExecutionEnv | undefined;
  /** Sections already in effect after replaying the active transcript. */
  readonly shown: Readonly<Record<string, string>>;
  /** Committed document reads. */
  readonly read: DocumentReader;
};

type PromptSection<Tool extends ToolRegistration = ToolRegistration> = {
  readonly key: string;
  render(input: PromptInput<Tool>, context: Context): string | undefined | Promise<string | undefined>;
  /** Default true: wrap the text as `<key>\n...\n</key>`. */
  readonly tag?: boolean;
};

/** Built by `hook()`; matches tasks by name. */
type HookRegistration = { readonly task: string; readonly handlers: object };

/** Built by `wrapTool()` and `wrapSection()`; targets a tool name or a section key. */
type Wrap<Tool extends ToolRegistration = ToolRegistration> =
  | { readonly tool: string; wrap(tool: Tool): Tool }
  | { readonly section: string; wrap(section: PromptSection<Tool>): PromptSection<Tool> };

interface Extension<Tool extends ToolRegistration = ToolRegistration> {
  readonly name: string;
  readonly tools?: readonly Tool[];
  readonly sections?: readonly PromptSection<Tool>[];
  readonly hooks?: readonly HookRegistration[];
  /** Apply where this extension is selected, in order. */
  readonly wraps?: readonly Wrap<Tool>[];
  /** Resolved by name for every task, whichever conversations select this extension. */
  readonly tasks?: readonly AnyTask[];
}

function defineExtension<Tool extends ToolRegistration = ToolRegistration>(extension: Extension<Tool>): Extension<Tool>;
function section<Tool extends ToolRegistration = ToolRegistration>(
  key: string,
  render: PromptSection<Tool>["render"],
  options?: { readonly tag?: boolean },
): PromptSection<Tool>;
function hook<K extends AnyTask>(task: K, handlers: Partial<HooksOf<K>>): HookRegistration;
function wrapTool<Tool extends ToolRegistration>(tool: Tool, wrapper: (tool: Tool) => Tool): Wrap<Tool>;
function wrapSection<Tool extends ToolRegistration = ToolRegistration>(
  key: string,
  wrapper: (section: PromptSection<Tool>) => PromptSection<Tool>,
): Wrap<Tool>;

interface RegistryReader<Tool extends ToolRegistration = ToolRegistration> {
  /** Immutable view of the whole current registry. */
  snapshot(): RegistrySnapshot<Tool>;
  /** Called synchronously after every publication; wakes the scheduler to reconsider blocked tasks. */
  subscribe(listener: () => void): () => void;
}

interface RegistrySnapshot<Tool extends ToolRegistration = ToolRegistration> {
  installed(): readonly Extension<Tool>[];
  extension(name: string): Extension<Tool> | undefined;
  /** Every installed tool with its extension, in install order. Names may repeat across extensions. */
  tools(): readonly { readonly extension: Extension<Tool>; readonly tool: Tool }[];
  sections(): readonly { readonly extension: Extension<Tool>; readonly section: PromptSection<Tool> }[];
  /** Built-in and installed task definitions. */
  tasks(): readonly AnyTask[];
  task(name: string): AnyTask | undefined;
}

interface Registry<Tool extends ToolRegistration = ToolRegistration> extends RegistryReader<Tool> {
  /** Installs `extension`, or replaces the installed extension with its name in place. Publishes at once. */
  install(extension: Extension<Tool>): void;
  /** Removes the installed extension with `extension.name`, whichever object it is. A later install appends. */
  uninstall(extension: Extension): void;
}

function createRegistry<Tool extends ToolRegistration = ToolRegistration>(): Registry<Tool>;
```

`Tool` 类型参数让应用可以把元数据（例如提示片段）附加到自己的工具上，并在其章节渲染器里以类型安全的方式读取。Harness 只依赖 `ToolRegistration`；它自身的对外接口（例如 `runtime.agent()`）使用默认类型。元数据字段必须是可选的：注册表不校验它们，而且安装的也可能是默认类型的扩展。由工具派生出的 pi-ai 声明只保留 pi-ai 的 `Tool` 字段（经 `toToolDeclaration`），因此应用元数据永远不会进入转录记录（transcript）。

```ts
type CodingAgentTool = ToolRegistration & { readonly promptSnippet?: string };
// The renderer sees CodingAgentTool: no cast needed to read promptSnippet.
export const ToolList = defineExtension<CodingAgentTool>({
  name: "tool-list",
  sections: [section("tools", ({ agent }) => agent.tools.map((tool) => `- ${tool.name}: ${tool.promptSnippet ?? tool.description}`).join("\n") || undefined)],
});
const registry = createRegistry<CodingAgentTool>();
```

规则：

- 第 8 章的内建任务始终存在，并且不属于任何扩展：`tasks()` 包含它们，任何东西都不能卸载或替换它们。任何扩展都可以针对它们注册钩子。
- 工具名与章节 key 在单个扩展内必须唯一；跨扩展则可以重名。章节 key 必须匹配 `^[a-z][a-z0-9_-]*$`，且 key `instructions` 保留给 agent 的指令（见下文）。
- 任务名在全部内建任务与所有已安装扩展之间唯一。`install()` 按替换完成之后的注册表状态做校验，包括上述规则；不合法时抛出异常，且不发布任何内容。`defineExtension()` 与 `section()` 不做任何检查。
- 发布是同步的，不调用任何扩展回调，并会通知订阅者。没有批量发布：扩展是重载的单位，重新安装它会在一次发布内、在其安装位置上原位替换它的工具、章节、钩子、包装器与任务。
- 扩展、工具与任务定义都不可变，包装器必须是无副作用的纯函数：包装器返回新对象，绝不修改其输入。
- 作为选择目标或包装目标传入的扩展或工具对象，以它的名字为准：`settings.extensions` 里保存的旧 `Skills` 对象会解析到已安装的 `skills` 扩展。

快照（snapshot）是一个普通的不可变值；没有任何资源释放动作。调度器（scheduler）每次调用阶段处理器时取一个快照，并经运行时向下传递；处理器与钩子读取这个快照，绝不自行另取。在每个正常阶段边界上，调度器都会取一个新的快照，任务定义则按第 5.4 节所述交接。不同阶段可能观察到不同的注册表状态；没有任何机制要求一次运行在其生成与工具任务之间看到同一个注册表状态。

```ts
export const ContextFiles = defineExtension({ name: "context-files", sections: [section("agents-md", renderAgentsMd)] });
export const Skills = defineExtension({ name: "skills", sections: [section("skills", renderSkills)] });
export const Coding = defineExtension({
  name: "coding",
  sections: [
    section("preamble", () => "You are an expert coding assistant.", { tag: false }),
    // The environment the host built for this conversation, in the conversation's directory.
    section("cwd", (input) => input.env && `Working directory: ${input.env.cwd}`),
  ],
});
export const Permissions = defineExtension({
  name: "permissions",
  hooks: [hook(ToolTask, { beforeTool: async (call) => (isDangerous(call) ? { block: "Needs approval" } : undefined) })],
});
// A role and a review loop, for conversations that select it.
export const Reviewer = defineExtension({
  name: "reviewer",
  sections: [section("role", () => "You review diffs. Report problems as a list. Never edit files.")],
  hooks: [hook(GenerationTask, { onYield: requestSecondPass })],
});

const registry = createRegistry();
for (const extension of [CodingTools, Coding, ContextFiles, Skills, Permissions, Reviewer]) registry.install(extension);
const harness = await Harness.open(storage, {
  models,
  registry,
  // Reviewer is installed but not selected by default: only conversations that select it get its role and hooks.
  settings: { extensions: [CodingTools, Coding, ContextFiles, Skills, Permissions] },
  env: ({ cwd }) => localEnv(cwd ?? process.cwd()), // cached NodeExecutionEnv per directory
}, context);
// The conversation remembers its model and directory; a restart elsewhere keeps both.
const root = await harness.root(context, { agent: { model: sonnet, cwd: process.cwd() } });
```

注册表不追踪哪些正在运行的工作仍在使用被替换或已卸载的扩展。已经启动的工作会继续使用它拿到的代码，因此一个在 `uninstall()` 之后立即释放资源的扩展，可能让仍在运行的调用以普通的错误结果失败。需要优雅释放资源的扩展必须自行管理资源的生命周期，例如采用引用计数。

**解析（Resolution）。** 会话的 `Agent` 由三方面解析而来：它存储的 `pi.agent`（缺失时：所有字段未设置）、一个注册表快照，以及解析后的设置：

```text
extensions  base = settings.extensions ?? every installed extension; in that order
            array: exactly these, in array order; { add, remove }: base, then add appended, minus remove
            duplicates keep their first position; names not installed are skipped
tools       the selected extensions' tools in extension order; a later same-name tool replaces an earlier one in place
            then every selected extension's tool wrappers, in extension order, then in each extension's order
            then the filter: an array keeps exactly these names in its order, a repeated name at its first position;
            { remove } drops these names
sections    the selected extensions' sections, same-key replacement in place, then their section wrappers,
            then `instructions` when set
hooks       the selected extensions' hooks for the task's name, in extension order
model       stored, else none: the request fails no_model
thinking    stored, else "off"
cwd         stored, else undefined
```

该块的要点：扩展选择以设置为准——未设置时默认选择全部已安装扩展（顺序即安装顺序），数组表示「恰好这些、按数组顺序」，`{ add, remove }` 在默认基础上追加再剔除；重复者保留首次出现的位置，未安装的名字被跳过。工具与章节按扩展顺序取用，后出现的同名者原位替换，再依次应用包装器，最后由工具过滤器收窄（数组保留指定名字及其顺序，`{ remove }` 剔除指定名字）。钩子按扩展顺序收集。模型未存储时请求以 `no_model` 失败；思考级别（thinking level）默认为 `"off"`；`cwd` 未存储时为 undefined。

抛出异常的包装器，或返回了不同名字工具/章节的包装器，会让它的目标从本次解析中消失：该工具不被提供，对它的调用产生 `tool_unavailable`；失败经 `onReport` 上报。找不到目标的包装器什么都不做，因此下文的 `Timing` 可以在没有 `bash` 的地方被选中。设置 `instructions` 时，`Agent.sections` 以一个带标签的 `instructions` 章节收尾，渲染该文本；包装器不作用于它。

对于同时选择两者的会话，后一个扩展的同名工具会覆盖前一个，而包装器作用于胜出的那个工具：

```ts
export const Timing = defineExtension({
  name: "timing",
  wraps: [wrapTool(bashTool, (tool) => ({
    ...tool,
    execute: async (args, api, context) => {
      const start = Date.now();
      try {
        return await tool.execute(args, api, context);
      } finally {
        metrics.record("bash", Date.now() - start);
      }
    },
  }))],
});
// A bash inside a Python virtualenv for one conversation: it replaces CodingTools' bash in place,
// and Timing, if selected, wraps it.
export const Venv = defineExtension({
  name: "venv",
  tools: [createBashTool({ commandPrefix: "source .venv/bin/activate" })],
});
registry.install(Venv); // installed, but not in the default selection
await conversation.configure({ extensions: { add: [Venv] } }, context);
```

**谁在何时解析什么。** 每个读取方在每个决策点只解析一次：

| 读取方 | 解析内容 | 时机 |
|---|---|---|
| 生成（generation）的 `prepare` | agent（工具、章节、模型、思考级别）、流选项、压缩（compaction）阈值 | 每个请求一次；模型、流选项与提供的工具在请求检查点中固定（第 8.3 节） |
| 每个任务阶段 | 钩子的扩展选择；`runtime.agent()` | 每个阶段处理器至多一次，在其第一次钩子派发或 `agent()` 调用时，基于该阶段的快照与已提交的 `pi.agent`，在 Session 行之外、以本次调用的 context 进行；此后整个阶段固定不变 |
| 工具任务 | 一个被接受调用的实现 | 在 `call` 与 `execute` 时：在阶段 agent 的 `tools` 中（应用工具过滤器后的当前选择）按名字查找；没有该工具——例如准备之后被移除——则为 `tool_unavailable`。重开时的重放（replay）策略使用同一查找（第 7.3 节） |
| 生成，工具轮开始时 | 工具执行模式 | 每轮一次（第 8.3 节） |
| 生成，压缩时 | 重试策略 | 在对每次尝试做分类时 |
| 压缩的 `select` | 模型、思考级别、流选项、压缩阈值 | 一次；摘要请求在其各次重试间保持固定（第 8.7 节） |
| Session 行上的边界与空闲准入（admission） | 队列模式 | 按边界（第 6 章） |
| 工具任务、`prepare`、`runtime.env()` | 环境 | 每次调用一次（第 2.2 节） |

注册表安装与设置变更不产生提交（commit），因此不发出任何事件（第 9.4 节）。使用默认选择的会话会随设置或已安装扩展的变化而变化；它的下一次准备（preparation）会附加系统增量（第 7.4 节）。展示已解析工具或已解析模型的 UI 通过 `Conversation.agent()` 重新解析。

### 7.2 钩子

钩子（hook）是任务在提交一个决策之前提出的、带类型的提问。钩子由任务定义声明，随扩展一起提供，由 `hook(task, handlers)` 构建（第 7.1 节）。任务询问的是其会话所选扩展的钩子。`hook()` 按任务令牌确定类型，但派发按任务名匹配，因此钩子能在其任务重载之后继续存在；跨任务版本保持钩子签名兼容是任务作者的责任。钩子在 Session 行之外按扩展顺序运行；在消费性提交（consuming commit）之前发生崩溃时，钩子可能被重跑。中止（abort）错误始终向上传播。

| 钩子 | 组合方式 | 普通抛出的处理 |
|---|---|---|
| `beforeRequest` | 替换链 | 上报后继续 |
| `afterResponse` | 所有观察者 | 上报后继续 |
| `onYield` | 第一个 `continue` 生效 | 上报后继续 |
| `beforeTool` | 参数替换链；第一个阻断生效 | 用错误文本阻断工具 |
| `afterTool` | 结果替换链 | 上报后继续 |
| `afterTools` | 所有观察者 | 上报后继续 |
| `beforeCompact` | 第一个决策生效 | 上报后继续 |

钩子使用任务备忘录（memo）来实现持久的「先写者胜」决策。没有公开的语义事件通道；当前的 UI 状态就是文档状态。

```ts
type HookResult<T> = T | undefined | Promise<T | undefined>;

/** What a hook may use: committed reads and the asking task's memos. */
interface HookApi extends DocumentReader {
  readonly taskId: TaskId;
  readonly conversationId: ConversationId;
  /** `HarnessOptions.models`. */
  readonly models: Models;
  memo<T extends JsonValue>(name: string, context: Context): Promise<T | undefined>;
  memo<T extends JsonValue>(name: string, candidate: T, context: Context): Promise<T>;
}

interface GenerationHooks {
  /** Before every request attempt, including recovery; the result is used for that request only. */
  beforeRequest(
    request: { readonly messages: readonly Message[] },
    api: HookApi,
    context: Context,
  ): HookResult<{ readonly messages: readonly Message[] }>;
  /** Every terminal provider message, before classification. */
  afterResponse(message: AssistantMessage, api: HookApi, context: Context): void | Promise<void>;
  /** A final answer; `continue` appends a user message and continues the run. */
  onYield(answer: AssistantMessage, api: HookApi, context: Context): HookResult<{ readonly continue: UserInput }>;
  /** After every tool of the round is terminal; `results` are the round's result entries in call order. */
  afterTools(assistant: EntryId, results: readonly EntryId[], api: HookApi, context: Context): void | Promise<void>;
}

interface ToolHooks {
  /** Before intent; replaces the arguments or blocks the call with error text. */
  beforeTool(
    call: ToolCall,
    api: HookApi,
    context: Context,
  ): HookResult<{ readonly arguments?: JsonObject; readonly block?: string }>;
  /** After execution, before the result entry; replaces the result. */
  afterTool(
    call: ToolCall,
    result: ToolExecutionResult,
    api: HookApi,
    context: Context,
  ): HookResult<ToolExecutionResult>;
}

interface CompactionHooks {
  /**
   * After range selection, before summarizing; the first decision wins. `entries` are the active entries the summary
   * replaces, the head marker first, and `messages` their model context, the summarizer's source; `firstKept` is the
   * first entry kept verbatim.
   */
  beforeCompact(
    compaction: {
      readonly reason: CompactionReason;
      readonly entries: readonly EntryRecord[];
      readonly messages: readonly Message[];
      readonly firstKept: EntryId;
      readonly instructions?: string;
    },
    api: HookApi,
    context: Context,
  ): HookResult<{ readonly decline: true } | { readonly summary: string }>;
}
```

`GenerationTask`、`ToolTask` 与 `CompactionTask` 是导出的内建任务令牌，它们的 `H` 参数正是上述接口。`runtime.hooks.each(name, invoke)` 会用阶段已解析钩子中 `name` 名下的每一个处理器来调用 `invoke`：即任务的会话所选扩展的、针对该任务名的钩子，按扩展顺序排列（第 7.1 节）。`invoke` 的普通抛出经 `onReport` 上报，`each` 继续下一个处理器；一旦本次调用（invocation）已被信号通知，错误就向上传播。组合方式不同的任务——例如 `beforeTool` 把抛出变成阻断，或在第一个决策后即停止——在其自己的 `invoke` 内部实现。钩子拿到的 `HookApi` 就是任务的运行时；钩子备忘录与任务自己的备忘录共享一个命名空间，因此钩子作者应为自己的备忘录名加前缀。

选择决定会话拥有哪些行为；扩展自己的文档保存该行为的状态：

```ts
const PlanModeDoc = defineDoc<{ enabled: boolean }>({
  kind: "app.plan-mode", version: 1, scope: "conversation", history: "latest", fork: "current",
  initial: () => ({ enabled: false }),
});
export const PlanMode = defineExtension({
  name: "plan-mode",
  hooks: [hook(ToolTask, {
    // An absent document means plan mode is off.
    beforeTool: async (call, api, context) =>
      (await api.snapshot(PlanModeDoc, api.conversationId, context))?.enabled && writes(call)
        ? { block: "Plan mode: read-only" }
        : undefined,
  })],
});
// PlanMode is in the default selection; /plan toggles this conversation's state.
await root.commit(async (tx) => {
  (await tx.doc(PlanModeDoc, root.id)).enabled = true;
}, context);
```

### 7.3 工具

```ts
type ToolControl = {
  readonly addTools?: readonly string[];
  readonly terminate?: true;
  readonly handoff?: string;
};

/** Remark about a call for the model and the UI; never part of the tool's data. */
type ToolDiagnostic = {
  readonly severity: "info" | "warn" | "error";
  readonly message: string;
  readonly code?: string;
};

type ToolExecutionResult<TDetails extends JsonValue = JsonValue> = {
  readonly content?: ToolResultMessage["content"];
  readonly isError?: boolean;
  readonly details?: TDetails;
  readonly diagnostics?: readonly ToolDiagnostic[];
  /** Spend of the execution itself, such as a model call; stored on the result and in `pi.usage.tools`. */
  readonly usage?: Usage;
  readonly control?: ToolControl;
};

interface ConversationHandle {
  readonly id: ConversationId;
  submit(submission: InputSubmissionDraft, context: Context): Promise<Submission>;
  abort(context: Context): Promise<void>;
  waitForIdle(context: Context): Promise<void>;
}

interface ToolExecutionApi<TDetails extends JsonValue = JsonValue> extends DocumentObserver, DocumentReader {
  readonly taskId: TaskId;
  readonly conversationId: ConversationId;
  readonly callId: string;
  /** The tool task's phase snapshot. */
  readonly registry: RegistrySnapshot;
  /** The calling conversation's agent, as the tool task's phase resolved it. */
  agent(context: Context): Promise<Agent>;
  /** `HarnessOptions.models`: the catalog, credentials, and request transforms generation uses. */
  readonly models: Models;
  /** Built by `HarnessOptions.env` for this call. */
  readonly env: ExecutionEnv | undefined;
  output(chunk: string | Uint8Array): void;
  diagnostic(diagnostic: ToolDiagnostic): void;
  details(value: TDetails, context: Context): Promise<void>;
  commit<T>(change: (tx: Tx) => T | Promise<T>, context: Context): Promise<T>;
  memo<T extends JsonValue>(name: string, context: Context): Promise<T | undefined>;
  memo<T extends JsonValue>(name: string, candidate: T, context: Context): Promise<T>;
  createTask<I, S extends { phase: string }, R, H extends object>(
    task: Task<I, S, R, H>,
    input: I,
    options: Omit<TaskOptions, "conversationId">,
    context: Context,
  ): Promise<TaskId<R>>;
  getTask<R>(id: TaskId<R>, context: Context): Promise<TaskRecord<JsonValue, JsonValue, R> | undefined>;
  waitForTask<R>(id: TaskId<R>, context: Context): Promise<SettledTask<R>>;
  conversation(id: ConversationId, context: Context): Promise<ConversationHandle | undefined>;
}

type ToolRegistration<TParameters extends TSchema = TSchema, TDetails extends JsonValue = JsonValue> =
  Tool<TParameters> & {
  readonly replay?: "safe" | "unsafe";
  readonly executionMode?: ToolExecutionMode;
  /** Pure repair of commonly malformed arguments; runs before validation, which still checks its result. */
  prepareArguments?(args: unknown): Static<TParameters>;
  readonly outputLimits?: {
    readonly maxBytes?: number;
    readonly maxLines?: number;
    readonly retain?: "head" | "tail";
  };
  execute(
    args: Static<TParameters>,
    api: ToolExecutionApi<TDetails>,
    context: Context,
  ): Promise<ToolExecutionResult<TDetails>>;
};

/** Identity function that infers `TParameters` from `parameters` and `TDetails` from the reported details. */
function defineTool<TParameters extends TSchema, TDetails extends JsonValue = JsonValue>(
  tool: ToolRegistration<TParameters, TDetails>,
): ToolRegistration<TParameters, TDetails>;
```

`execute()` 接到的 `args` 按 `parameters` 确定类型：Harness 在运行之前会依据该 schema 校验调用的参数。`defineTool()` 让内联的工具字面量可以推断类型，如 `tools: [defineTool({ ... })]`。`execute` 是方法，因此不同类型的工具能共用同一个 `tools` 数组。

省略 `replay` 视为 `unsafe`。省略 `outputLimits` 时默认 50 KiB、2,000 行、`retain: "head"`。省略 `executionMode` 时遵循设置中的 `toolExecution`；一个 `sequential` 调用会让它所在的整轮都变为顺序执行（第 8.3 节）。

工具只通过 `api.env` 触达文件与进程，绝不通过构建工具时捕获的环境。工具任务在每次调用时用 `HarnessOptions.env` 依据会话 ID 与 `cwd` 构建环境（第 2.2 节），因此会话的目录或沙箱不需要包装器。`env` 抛出异常会成为该调用的一个普通错误结果。恢复后的重跑拿到的是当时的会话环境。`api` 是普通对象，便于包装器对它做展开（spread）。需要环境却未拿到环境的工具会抛出异常，产生一个普通错误结果。

运行中的工具向 UI 报告输出（output）与详情（details），与最终结果的两个部分相互对应，另有诊断（diagnostics，见下文）：

- `output(chunk)` 追加运行中的文本输出，类似 stdout。若 `execute()` 省略 `content`，最终保留的输出成为一个文本内容项；没有输出则成为空内容列表。保留的输出是整个流中完整行的精确切片（`head` 取最前的行，`tail` 取最后的行），含末尾换行符；超过 `maxBytes` 的单行会在字节上限处按字符边界切断。除制表符与换行符之外的控制字符会从保留文本中移除；接收单个分块（chunk）时不做逐块清洗。
- `details(value)` 用一个完整的 JSON 值替换运行中的详情；它不合并键。若 `execute()` 省略 `details`，最后一个值成为最终的 `details`，因此渲染器从第一次更新到最终结果面对的是同一种详情形状。

工具运行期间，这两者都不会发给模型。`output()` 同步地把 UTF-8 输出接收进该次调用（invocation）独有的有界缓冲区，并在调用结束后抛出异常。节流提交在其 `pi.live.tools` 槽位发布保留的输出、被丢弃的字节/行数，以及当前的详情与诊断。节流是自适应的，与环境对 shell 输出的捕获类似：空闲一段时间后的第一个变化立即提交；此后每次提交至少把下一次推迟 `settings.progress.outputIntervalMs`（默认 100 ms），并按其写入大小以 100 KiB/s 的速率额外推迟，因此一次大规模重写会换来成比例的更长停顿。延迟期间发生的变化合并进下一次提交。节流是 Harness 的策略，不属于 `outputLimits`——后者只约束保留什么。结果内容中的显式文本在持久化进转录记录之前受同样的限制；非文本内容按其 pi-ai 类型声明的方式保留。当限界丢弃文本时，Harness 追加一条代码为 `truncated` 的 `warn` 诊断，说明被丢弃的行数与字节数。

诊断是一条通道，不是文本。关于一次调用的备注——例如输出被截断、溢写（spill）路径、修正后的路径、磁盘上的文件已变化、搜索被设上限——经 `api.diagnostic()` 或 `ToolExecutionResult.diagnostics` 传递，绝不进入模型读取的、作为工具数据的内容。Harness 追加它自己掌握的那些，工具只追加只有它自己知道的那些。每条诊断都对模型可见；仅供 UI 使用的信息应放进 `details`。`diagnostic()` 同步地把诊断记录进工具的槽位，随下一次节流提交发布，并在调用结束后抛出异常。结算（settlement）时，结果的诊断依次为：经 `api` 记录的、结果自身携带的、Harness 自有的。只要存在诊断，结果内容就以一个文本项收尾：

```text
<harness>
[warn] output truncated: 51,204 lines, 2,301,112 bytes dropped
</harness>
```

每条诊断对应一行 `[severity] message`，`pi.tool-result` 条目把结构化列表（可能为空）以 `data: { diagnostics }` 的形式存储（第 8.1 节）。存储的消息就是模型看到的内容，而 UI 与代码读取的是那个列表。`warn` 诊断不会置 `isError`。

`output()` 从不把完整输出溢写到文件，因为溢写需要文件系统，而文件系统可能是远程的或不可用的。必须保全完整输出的工具应通过它获得的 `ExecutionEnv` 或 `FileSystem` 来溢写，并在诊断中报告产生的路径；渲染器需要时也写进 details。环境的 shell 流式转发原始输出块，一旦超过字节或行阈值就把完整输出溢写到文件；它自己不保留任何有界视图，因此 `output()` 是唯一对输出做限界、清洗与节流的地方。`bash` 工具把这些块送入 `output()`，以诊断形式报告溢写路径，并在非零退出或超时时抛出异常；错误结果仍携带保留的输出与诊断。

需要经慢速链路（例如位于另一台主机上的环境）搬运输出的环境，不必搬运全部输出。`api.outputWindow` 声明了保留尾部的调用所保留的尾部，以及进度提交的节奏；`bash` 工具把它作为 `ShellExecOptions.window` 传入。环境随后可以省略输出，并在下一个块上以 `info.skipped` 报告省略：被省略的解码字节数、换行数，以及被省略的文本是否以换行结尾。只有当其后随输出超过窗口（至少多出 1 字节或 1 行）时才可省略，且全部后随输出必须在同一个块中送达，因此被省略的文本永远不会属于被保留的尾部，任何进度提交都不会看到缺口。`output(chunk, skipped)` 把省略计入被丢弃的计数，因此保留的尾部、丢弃计数与 `truncated` 诊断，与每个字节都到达时的情形完全相同；不同的只是进度提交采样的时刻。环境的投递不应快于该节奏，因为进度提交的采样不会更快。保留头部的调用没有窗口。替换 `output` 来变换文本的包装器应把 `outputWindow` 置为 `undefined`，以免被省略的文本绕过它的变换。

`exec` 接受字符串或 argv 数组。字符串经环境的 shell 运行；数组不经 shell，直接以其余元素为参数运行第一个元素，因此由数据（例如文件名）构建命令的宿主，永远不需要针对某个特定 shell 做引号转义。每个 `onOutput` 块都标明它来自哪个流；`bash` 工具忽略它，而需要分开 stdout 与 stderr 的宿主可以分别收集、自行限界，并在收集足够时中止调用。`openBinaryReader` 打开一个常规文件做位置读取，宿主因此读取有界区间而不是整个文件，并且即使路径被重命名，每次读取看到的仍是它打开的那个文件；`noFollow` 拒绝把符号链接作为路径的最后一段。它的 `scanLines` 在环境内部对文件做一次遍历，报告换行数、一段行范围的字节区间，以及该段与其首行的解码后大小，调用者因此不必搬运文件就能统计与定位行。`openDirReader` 按文件系统顺序分页遍历一个目录，只为它返回的条目读取元数据，并跳过期间已被删除的条目。所有操作在上下文中止时停止，且只有该调用的工作停止：超时或中止只会杀死该命令自己的进程。`cleanup()` 杀死环境仍在运行的每一个命令，属于其所有者的关闭流程，绝不属于单个请求。`watch` 为需要从环境加载资源（例如指令或技能）的宿主报告文件与目录的变化；Durable 自己从不调用它。目标可以不存在，创建它就是一次变化；递归目标覆盖其子树（排除的条目除外），且不追踪其下的符号链接。`watch` 解析完成时，覆盖已建立，因此先 watch 再加载的宿主不会丢失加载期间发生的变化。一次变化以报告的路径送达（每条路径覆盖其子树；调用可能有误报），或在一段时间内覆盖不确定、必须全部重扫时以 `overflow` 送达，或以最终的 `error` 送达。`native` 监视器在约两秒内报告变化；`polling` 监视器则比较快照——当其文件系统（例如网络或 FUSE 文件系统）不报告别处发生的变化，并且可能漏掉两次快照之间被撤销的变化时，就该使用它。`NodeExecutionEnv` 只把事件用作触发重扫的信号，并报告快照之间的差异，因此无论平台发送什么事件，被替换的文件、被重命名的父目录、连同内容一起创建的目录都会被报告。环境是受信任的，不是隔离（confinement）边界：在打开之前检查规范路径并不能阻止并发的重命名或符号链接交换，因此限制路径的调用者是出于整洁考虑，而不是安全。

`details()` 的 promise 在对应（或被合并）的文档提交完成后解析。正常结算期间，工具任务停止节流并等待在途提交；追加结果条目的终结提交是最后一次刷写（flush），会让任何仍挂起的 `details()` promise 完成。中止与关闭遵循调用级与 Session 级准入门：未提交的缓冲更新可能被丢弃，而已获准入的提交会完成。取消、回调、追踪器（tracker）准备与检查点失败都发生在 Storage 准入之前，不会污染 Session。不确定的 Storage 失败遵循致命 Session 规则。

工具随扩展提供（第 7.1 节），具有名字、描述、JSON schema、重放策略与执行函数。`wrapTool(tool, wrapper)` 装饰工具而不替换它。每次解析都把该名字的胜出工具与所选扩展的包装器组合起来（第 7.1 节）；包装器绝不捕获基座（base），因此重载基座后它的包装器仍然有效。复合体提供声明、参数校验、重放策略与执行。

只有其请求提供过的工具，其调用才会被接受。生成任务对照从已提交模型上下文重放（截至请求 `cutoff`）得到的工具集来检查这一点；`beforeRequest` 的替换不改变它。对未提供工具的调用，它直接以第 2.2 节所述的 `tool_unavailable` 结果作答，不启动工具任务。准备之后的 agent 变更不影响该检查（第 2.2 节）。工具任务在阶段 agent 解析结果的 `tools` 中（应用工具过滤器之后）解析被调用的名字，并使用该实现直到执行结算：一个阶段处理器完成解析、校验、运行 `beforeTool`、记录意图（intent）、执行并提交结果，因此没有任何阶段边界把解析与结算分开。解析不到的名字——例如其扩展已被卸载或取消选择，或工具过滤器在请求准备之后丢弃了它——产生 `tool_unavailable`。实现若定义了 `prepareArguments`，会先修复调用的参数，例如以 JSON 字符串形式发来的 `edits`；存储的调用保留模型发送的原始内容。参数在 `beforeTool` 之前与之后都按解析出的实现的 schema 校验；校验失败或修复抛出异常，产生 `invalid_arguments` 错误结果。

钩子与校验之后，工具任务在执行前把最终参数与解析出的重放策略持久记录下来。恢复不重跑 `beforeTool`，并把同一份存储参数传给 `execute()`。重放安全的工具，只要这种转换是纯函数，就可以从这些参数重建提交。随机值、时间戳、可变的文档/配置读取，以及其他必须保持稳定的派生输入，都应先捕获进持久的备忘录、检查点或任务输入。后台报告任务把最终消息收进它自己的持久输入，因此能独立完成。恢复不允许变更后的注册表声明改变已存储的重放策略。

工具获取的会话句柄（handle）只接受输入提交请求（submission）；工具用普通事务写入来产生被动条目。

工具在持久任务中执行。它可以：

- 向其 `pi.live.tools` 槽位发布有界的运行中输出与详情；
- 提交备忘录；
- 创建并等待任务；
- 经 `commit()` 原子地创建或派生（fork）显式拥有的会话；
- 观察其持有令牌/引用的文档；
- 经 `commit()` 变更已获授权的文档；
- 返回有界的模型内容以及相互独立的诊断详情。

工具操作使用发起任务的准入门与调用生命周期门。任务创建默认属于该任务所在的会话。受信任代码中的文档与会话访问遵循第 3.3 与 9.2 节；没有额外的子树授权层。在受信任代码中，持有 Session 全局的带类型 ID 即已足够。

工具没有创建会话的便捷方法。它们在 `commit()` 内部创建或派生会话，显式声明其所有权，原子地暂存相关的文档/任务写入，并且只拿到惰性的记录（inert record）。该提交完成后，`conversation(id)` 获取一个绑定到调用的操作句柄，用于提交请求、显式中止与等待空闲，且不改变所有权。提交回调不得调用 `conversation()`，也不得使用先前获取的句柄：持有变更行（mutation line）期间禁止嵌套 Session 操作与外部副作用。句柄的操作在调用结束后会拒绝（reject）。其 `submit()` 返回的 `Submission` 同样绑定到调用；这些方法拒绝之后，已获准入的提交请求仍然持久有效。调用拥有的文档监视（watch）在调用结束时停止。

前台子代理（subagent）会话由其工具任务显式拥有。一个事务创建或派生子会话；所有者边（owner edge）就是它的持久记录，因此重放安全的重跑会先用 `scanConversations({ ownerTaskId })` 找到子会话，而不是再建一个。结算之后，工具重新获取子会话，用从其任务 ID 派生的请求 ID 提交（重跑沿用同一 ID），并等待该提交请求的结果。提供商的 call ID 在整个 Session 内不唯一，不得用作请求 ID。中止工具任务或使其异常终结时，级联传播贯穿其拥有的范围。工具在运行详情中报告子会话，例如 `api.details({ conversationId })`，这样看到该调用的 UI 就能附加到子会话的视图或事件。

```ts
export const Subagent = defineExtension({
  name: "subagent",
  tools: [defineTool({
    name: "subagent",
    description: "Delegate a self-contained task to a subagent and get its answer back.",
    parameters: Type.Object({ task: Type.String() }),
    replay: "safe",
    execute: async (args, api, context) => {
      const { task } = args;
      const child = await api.commit(async (tx) => {
        const existing = (await tx.scanConversations({ ownerTaskId: api.taskId }, 1)).items[0];
        if (existing !== undefined) return existing.id;
        // Starts as a copy of this conversation's agent: model, thinking level, cwd, extensions, tools.
        const created = await tx.createConversation({ ownership: { kind: "task", taskId: api.taskId } });
        // Without this extension, the child is not offered this tool.
        await configure(tx, created.id, { extensions: { remove: [Subagent] } });
        return created.id;
      }, context);
      await api.details({ conversationId: child }, context);
      const handle = (await api.conversation(child, context))!;
      const request = { type: "input", content: task, requestId: `subagent:${api.taskId}` } as const;
      const settled = await (await handle.submit(request, context)).wait(context);
      if (settled.status !== "done" || settled.type !== "input") throw new Error(`Subagent failed: ${settled.status}`);
      return { content: [{ type: "text", text: await answerText(api, settled.answer, context) }] };
    },
  })],
});
```

`{ remove: [Subagent] }` 编辑的是宿主的默认选择（第 2.2 节）。这里的主会话未设置自己的选择，因此这也是它的选择。若父会话存储了任何选择——数组或 `{ add, remove }` 对象——则改为在提交之前从 `(await api.agent(context)).extensions` 计算子会话的数组。

持久的后台子代理活得比父会话的回合更久，之后可以被发消息、被引导、被停止、被列出。一个事务在按子代理名称于应用的注册表文档中去重之后，在父会话中创建一个后台的、会话拥有的锚点任务（anchor）`A`、一个由 `A` 拥有的子会话 `C`，以及从名称到 `C` 的注册表映射。`A` 立即完成；只要 `C` 还有普通工作它就保持 `completing`（第 5.5 节），随后保持终结状态。它的记录保留 `background`，因此父会话的普通中止与空闲遍历在它这里停止，而 `Conversation.abort(context, { background: true })` 仍能穿过它触达 `C` 的工作，且 `Harness.waitForIdle()` 不会等待它。`C` 中后续的运行是 `C` 自己的普通工作；已终结的所有者从不级联。

发给子代理的每条消息，都由父会话中一个后台的、会话拥有的报告任务（reporter）投递。它在工具的事务中创建，并以工具任务 ID 为键，因此调用重跑不会重复创建。报告任务用从其自身任务 ID 派生的请求 ID 向 `C` 提交，等待该提交结算，再把答案以 `whenBusy: "followUp"` 的输入投回父会话，使用另一个从其任务 ID 派生的请求 ID。任一准入之前的崩溃会重试它；准入之后的崩溃则返回已存在的 `Submission`，因此子会话只收到一次消息，父会话只收到一次答案。因此报告任务不需要事务级准入；`tx.createSubmission()` 写入不带准入规则的原始记录。应用的名称文档使用 `fork: "initial"`，使父会话的派生不继承它。UI 从该文档列出子代理；子代理在其 `pi.live.run` 被设置期间即在工作。中止与空闲遍历只由所有者边驱动。锚点与报告任务的定义随子代理扩展提供，因此重启后只要宿主重新安装它，待处理的报告任务即可恢复：

```ts
export const SubagentTools = defineExtension({ name: "subagent-tools", tasks: [Anchor, Reporter], tools: [subagentTool] });

// In subagentTool's spawn commit, after the name checks:
const anchor = await tx.createTask(Anchor, null, { ownership: { kind: "conversation" }, background: true });
// Owned by a task of the parent: starts as a copy of the parent's agent.
const child = await tx.createConversation({ ownership: { kind: "task", taskId: anchor } });
await configure(tx, child.id, {
  extensions: { remove: [SubagentTools] },
  instructions: `You are the subagent "${name}". Answer the main agent's requests.`,
});
```

工具结果可以请求 `addTools`、`terminate` 或 `handoff`。生成任务的 `tools` 阶段（第 8.5 节）把指名的工具加入会话存储的工具过滤器；它们在下一次准备时生效。只有当本轮的所有结果都请求 `terminate` 时本轮才终止，与 pi agent 循环一致；此时 `tools` 阶段使用一个最终边界（final boundary）。本轮中任何 `handoff`——若有多个，取调用顺序中的最后一个——以同样方式结束运行：先追加一条带 `head: "self"` 的 `pi.reset` 条目、并把交接文本作为用户消息（第 8.1 节），与 `reset(handoff)` 写入的完全一致。

结果的 `usage` 存储在工具结果消息上，并在结果提交中累加进会话的 `pi.usage.tools[toolName]`（第 8.6 节）。运行所拥有会话的工具不得再次上报该会话的消耗：子会话自己的 `pi.usage` 已经计入它（第 12 章）。

重开时，只有当存储的意图策略与当前声明（按 `call` 时的解析方式）都为 `safe`，工具才重跑。当前的 `unsafe` 声明可以否决已存储的安全重放；当前安全的声明绝不会把存储的不安全升级为安全。不再能解析的工具按 `unsafe` 处理。其余所有孤立效应产生包含持久部分输出的 interrupted 结果。完成、失败与中止的工具终结结果都保留其工具结果条目 ID，供生成任务的 `tools` 阶段使用。

Harness 自行写入的错误结果会置 `isError`，并携带一条 `error` 诊断，其代码为 `tool_unavailable`、`invalid_arguments`、`blocked`、`interrupted`、`aborted` 或 `tool_error`（`execute()` 抛出）之一，消息为错误文本。其内容是持久的部分输出（若有），`details` 是工具最后一次上报的值（若有）。

`@earendil-works/pi-durable/tools` 提供 `read`、`write`、`edit` 与 `bash` 工厂函数（自 agent harness 的工具移植而来），以及包含全部四者的 `CodingTools` 扩展。它们只使用 `api.env`；没有任何机制自动安装它们。`read` 尚不返回图片。它通过 `openBinaryReader` 读取文件：图片检测读取文件头（以及 PNG 的 chunk 头），`scanLines` 统计并定位所选行，只有展示的头部才被读取与解码，因此其开销与传输以输出上限加上环境内对文件的一次遍历为界。其结果与「解码整个文件、按行切分、再截取所选行」的结果完全一致。读取期间文件发生变化的，会再读一次，然后才失败。`edit` 与 `write` 在进程内对同一文件的「读取-修改-写入」做串行化，键为环境的 `FileSystem.id`（相同 ID 在相同路径下看到相同文件）加规范路径，因此针对同一文件系统的两次调用即使使用新环境对象也会排队，而其他文件与文件系统永远不必等待。它不是针对 `bash` 或其他进程的锁。

### 7.4 系统提示与动态工具

Pico 没有持久的系统提示（system prompt）章节。会话解析出的 agent 为每个请求产出期望的章节；转录记录中的 `pi.system` 条目是模型所见内容的唯一持久记录。Pico 把提示与工具变更直接作为 PR #9548 `SystemMessage` 值存储在转录中的相应位置，`content` 始终为空：

```ts
type SystemEntry = EntryRecord & {
  readonly kind: "pi.system";
  readonly model: readonly [SystemMessage];
};

const baseline: SystemMessage = {
  role: "system",
  content: "",
  sections: { preamble: renderedPreamble, cwd: renderedCwd },
  toolsAdded: allEffectiveTools,
  timestamp: now,
};

const delta: SystemMessage = {
  role: "system",
  content: "",
  sections: { cwd: nextRenderedCwd, legacy: null },
  toolsRemoved: [{ name: "read" }],
  toolsAdded: [nextRead],
  timestamp: now,
};
```

生成准备针对其阶段快照执行以下步骤：

1. 解析会话的 agent（第 7.1 节），并把活跃转录中的系统消息重放进已展示的章节与已提供的工具。
2. 期望的工具就是 agent 的 `tools`，按其顺序。
3. 用 `HarnessOptions.env`（第 2.2 节）构建环境，并以 `PromptInput` 按顺序渲染 agent 的 `sections`：包括会话、agent、环境、已展示章节，以及一个读取已提交文档的 `DocumentReader`（即任务运行时）。渲染结果即期望的章节。
4. 将期望的章节与工具声明同重放状态比较，若有差异，追加一个按位置（positional）记录的 `pi.system` 条目。

准备在追加之前不复查转录记录：只有 Harness 会向繁忙的会话写入——通过提交请求、运行任务、边界，以及阻塞式压缩（它只在其生成任务等待它时追加，第 8.7 节）——因此它读到的转录记录仍然是最新的（第 12 章）。

模型与思考级别是请求选项，不是提示状态。

所选扩展的章节与 agent 的 `instructions` 是提示文本的唯一来源；没有单独的构建器。`section(key, render, { tag })` 构建章节，`wrapSection(key, wrapper)` 装饰章节，二者按每次解析组合，方式与工具包装器相同。章节按 agent 的顺序渲染：扩展顺序，后一个扩展的同 key 章节原位替换前一个，`instructions` 最后（第 7.1 节）。`render` 返回 `undefined` 的章节被省略。`tag` 省略或为 true 时，文本被包裹为 `<key>\n...\n</key>`。抛出异常的章节保留其已展示文本（若有）并被上报；请求仍然发出。生成调用被取消之后抛出的错误向上传播；章节自身的 abort 错误（例如其 fetch 超时）是普通失败。没有任何章节时，期望的章节集合为空。

最小的提示就是一个不带标签的章节：

```ts
const Chat = defineExtension({
  name: "chat",
  sections: [section("preamble", () => "You are a helpful assistant.", { tag: false })],
});
registry.install(Chat);
```

会话的提示随其扩展选择、`instructions`、`input.env` 与 `input.read` 而变化。不应看到 skills 的子代理不选择 skills 扩展，cwd 章节渲染 `input.env.cwd`；没有章节会检查自己是否运行在子代理中。对相同输入，渲染器必须具有确定性：渲染文本的任何变化——例如内嵌的时间戳——都会追加系统增量，并使提供商的提示缓存失效。

重放按转录顺序应用消息。非空 `content` 追加指令。章节字符串添加或替换该名字，而不移动已有章节的位置；`null` 移除它，之后的重新添加会把它追加到有序章节映射的末尾。同一条消息内，工具的移除先于添加发生，因此同名替换获得新的声明与位置。

准备同时比较值与顺序。若值可以在不改变顺序的情况下修补，它发出最小补丁。若已展示顺序与期望顺序不同，一次提交追加两个 `pi.system` 条目：第一个用 `null` 移除每个已展示章节，第二个按期望顺序重新添加每个期望章节。这样，纯顺序的变化以及跨请求的删除/重新添加都能精确重放；仅仅重述相等的值是不够的。

PR #9548 `SystemMessage` 始终是补丁，不是重置：它无法仅凭重述当前值来移除先前的 `content` 或恢复章节顺序。因此，当一个 head 移除了上一个请求可见的基线（baseline）——即活跃上下文有 head 标记、且该标记之后没有追加过 `pi.system` 条目（没有 ID 更高者）——新的 `pi.system` 条目会为切割后仍保留的每个更早的 `pi.system` 条目添加 `ContextEdit` 省略项。此时它自己的消息就是一个完整基线，按顺序包含每个期望章节以及每个生效的工具声明。模型上下文重放看到的是新基线，而不是被省略的保留增量。即使只是重述重放得到的值，准备也会写入这个基线，这样之后的每次准备都能在标记之后找到一个 `pi.system` 条目。Head 重设基线优先于普通的顺序/值修补。没有 head 切割时，顺序不匹配采用上面的两条件移除/重加序列；只有当顺序已经一致时，准备才发出最小化的值变更与 `null` 移除。

工具变更单独规划，搭载在最后一个已规划的条目上；章节不变时则用单独一条。声明用 pi-ai 的 `declarationsEqual()` 比较、用 `toToolDeclaration()` 写入，因此应用元数据永远不会进入转录记录。发生变化的声明在同一条消息中先移除再重新添加。重放让保留的工具留在原位并追加新增；当这样做得不到期望顺序时，该消息移除每个已提供工具并按顺序重新添加期望的工具。Head 重设基线时添加每个期望工具。

历史 `SystemMessage.sections` 中存储的渲染字符串始终保持权威，即使当前渲染器已经改变。由 pi-ai 决定是把这些消息按位置发给支持的提供商，还是折叠成开头的一条系统消息；Pico 不会为提供商兼容性改写自己存储的转录记录。

### 7.5 扩展重载

扩展代码通过注册表在进程内重载。宿主以已安装的名称安装新的扩展对象，一次发布即原位替换旧对象。Harness 继续运行；无需关闭或重开。

```ts
registry.install(SkillsV2); // same name: conversations selecting skills render v2 at their next request
registry.uninstall(Skills); // selecting conversations get a system delta removing its section; nothing is rewritten
// Restart: the host installs its extensions again; stored names resolve against them.
```

- 新的阶段调用与工具任务立即使用新扩展；运行中的调用在其下一个阶段边界看到它。
- 已经运行的工作保持其快照，直到其阶段处理器结束；已固定（pinned）的工具保持其实现，直到其执行结算。替换从不向它发信号或中断它。旧代码使用的资源由扩展自己负责（第 7.1 节）。
- 被按名替换的任务定义在其下一个正常阶段边界交接（第 5.4 节）。当持久化输入或检查点状态的含义发生变化时，任务定义必须提升版本号，并迁移受支持的旧状态；迁移失败会阻塞任务，而不是使其终结。
- 被替换的扩展保持其安装位置，因此重载不会使其钩子、工具与章节相对其他扩展移动位置；在扩展内部，以新对象的顺序为准。把任务定义从一个扩展移动到另一个扩展，会在两次安装之间留下一个空档，期间其待处理任务被阻塞。
- 文档定义显式传给带类型的访问，无需注册；变更后的令牌在其下一次访问时生效。

如果旧扩展代码无视取消且永不结束，新工作已经在使用替换后的代码。Harness 关闭仍会等待（join）每一次调用。要安全地强制终止任意不配合的 JavaScript，需要 worker/进程隔离；那样的宿主会终止进程，并从持久状态重开 Session。新旧 Harness 实例绝不能同时拥有同一个 Session：在旧实例的 `close()` 完成之后、其调用代码都不再运行时，再打开新实例（第 2.2 节）。
