## 10. 存储契约

存储契约（storage contract）的约定是：有序扫描基于游标（cursor）进行，精确的身份查找（identity lookup）则按键（keyed）寻址。

```ts
type Page<T, C> = {
  readonly items: readonly T[];
  readonly next?: C;
};

type Cursor = Readonly<Record<string, JsonValue>>;

type ConversationQuery = {
  readonly ownerConversationId?: ConversationId;
  readonly ownerTaskId?: TaskId;
};

type EntryQuery = {
  readonly conversationId: ConversationId;
  readonly minEntryId?: EntryId; // inclusive
  readonly maxEntryId?: EntryId; // inclusive
};

type TaskQuery = {
  readonly conversationId?: ConversationId;
  readonly kind?: string;
  readonly status?: "pending" | "running" | "waiting" | "completing" | "terminal";
  readonly abortRequested?: boolean;
  readonly background?: boolean;
};

type SubmissionQuery = {
  readonly conversationId?: ConversationId;
  readonly status?: SubmissionRecord["status"];
};

type DocumentPoint = Seq | "current";

type DocumentAddress = {
  readonly kind: string;
  readonly scope: DocumentRecord["scope"];
  readonly key?: string;
};

type DocumentQuery = {
  readonly scope: DocumentRecord["scope"];
  readonly at: DocumentPoint;
  readonly kind?: string;
};

type DocumentContent =
  | { readonly version: number; readonly kind: "base"; readonly value: JsonObject }
  | { readonly version: number; readonly kind: "delta"; readonly ops: readonly Op[] };

type StoredDocument = {
  readonly record: DocumentRecord;
  readonly version: number;
  readonly value: JsonObject;
  /** Deltas replayed after the selected base to materialize `value`. */
  readonly deltasSinceBase: number;
};

type StorageWrite =
  | { readonly type: "conversation"; readonly value: ConversationRecord }
  | { readonly type: "entry"; readonly value: EntryRecord }
  | { readonly type: "task"; readonly value: TaskRecord<JsonValue, JsonValue, JsonValue> }
  | { readonly type: "submission"; readonly value: SubmissionRecord }
  | {
      readonly type: "document.create";
      readonly record: DocumentCreate;
      readonly content: Extract<DocumentContent, { kind: "base" }>;
    }
  | {
      readonly type: "document.copy";
      readonly record: DocumentCreate;
      readonly source: { readonly id: DocumentId; readonly at: DocumentPoint };
    }
  | {
      readonly type: "document.change";
      readonly id: DocumentId;
      readonly content: DocumentContent;
    }
  | { readonly type: "document.retire"; readonly id: DocumentId };

/**
 * Trusts the owning Session to supply semantically valid records, references,
 * ancestry, and transitions. Enforces atomicity, global ID ownership, immutable
 * conversation/entry creation, document record consistency, and detached
 * values; Session serializes commits. Sequences strictly increase but may have
 * gaps. Once commit() resolves, later reads through that Storage observe it.
 */
interface Storage {
  commit(writes: readonly StorageWrite[], context: Context): Promise<Seq>;
  /** Allocate from the one global numeric namespace; the generic brand is compile-time only. */
  mintId<I extends Id<string>>(): Promise<I>;

  conversation(id: ConversationId, context: Context): Promise<ConversationRecord | undefined>;
  scanConversations(query: ConversationQuery, limit: number, cursor: Cursor | undefined, context: Context): Promise<Page<ConversationRecord, Cursor>>;

  entry(id: EntryId, context: Context): Promise<{ readonly entry: EntryRecord; readonly commitSeq: Seq } | undefined>;
  entry(conversationId: ConversationId, id: EntryId, context: Context): Promise<{ readonly entry: EntryRecord; readonly commitSeq: Seq } | undefined>;
  findLatestHeadMarker(conversationId: ConversationId, atOrBeforeEntryId: EntryId | undefined, context: Context): Promise<(EntryRecord & { readonly head: EntryId }) | undefined>;
  scanEntries(query: EntryQuery, limit: number, cursor: Cursor | undefined, context: Context): Promise<Page<EntryRecord, Cursor>>;

  task(id: TaskId, context: Context): Promise<TaskRecord<JsonValue, JsonValue, JsonValue> | undefined>;
  scanTasks(query: TaskQuery, limit: number, cursor: Cursor | undefined, context: Context): Promise<Page<TaskRecord<JsonValue, JsonValue, JsonValue>, Cursor>>;

  submission(id: SubmissionId, context: Context): Promise<SubmissionRecord | undefined>;
  scanSubmissions(query: SubmissionQuery, limit: number, cursor: Cursor | undefined, context: Context): Promise<Page<SubmissionRecord, Cursor>>;
  submissionByRequest(conversationId: ConversationId, requestId: string, context: Context): Promise<SubmissionRecord | undefined>;

  findDocument(address: DocumentAddress, at: DocumentPoint, context: Context): Promise<DocumentRecord | undefined>;
  document(id: DocumentId, at: DocumentPoint, context: Context): Promise<StoredDocument | undefined>;
  scanDocuments(query: DocumentQuery, limit: number, cursor: Cursor | undefined, context: Context): Promise<Page<DocumentRecord, Cursor>>;

  close(context: Context): Promise<void>;
}
```

`StorageRejected` 表示某个批次在任何持久化效果发生之前就被拒绝，并且保证尚未提交。Session 会按常规回滚这样的批次；而 Storage 受理之后出现的未知失败仍然是致命的（fatal），因为其提交状态无法确定。只有在保证能够回滚的前提下，后端（backend）才将 `StorageRejected` 用于确定性的 `document.copy` 源错误、重放错误和一致性错误。

`document.copy` 读取的是批次开始前已提交的源状态，与命令顺序无关。源必须是所选时间点上一个仍然存活的会话文档，并且其 kind/key/history/fork 必须与子文档的创建记录一致。Storage 会以源已存储的版本持久化一份独立而完整的子基线（base）。一个批次不得创建、修改或退役（retire）被选为源的文档。此后源发生的任何变更、回收（reclamation）、退役或后端重新打开，都不会影响子文档。

游标是由后端拥有的 JSON 对象。调用方只能把它们原样传回同一存储上的同一扫描；跨存储或跨查询使用不受支持。变更线（mutation line）由 Session 持有，因此存储实现不必再增加第二个面向调用者的提交互斥锁。但每个后端仍须保证单个已受理的批次是原子的。

`findLatestHeadMarker()` 返回带有 `head` 的最新可见条目（entry），其位置不迟于可选的包含性截止点。返回的条目本身就是标记（marker）；它的 `head` 值才是上下文的实际下界。`scanEntries()` 以从新到旧的顺序对包含性 ID 区间分页，同时应用所有会话祖先上限。没有边界时，它会分页输出完整的可见历史。要通过条目 `E` 读取上下文，先找到 `E` 处或之前的标记，然后从 `marker?.head` 扫描到 `E`。读取当前上下文时则省略上界。会话所有者过滤是带索引且合取（conjunctive）的，它们支持在不扫描全部会话的前提下进行所有权遍历；应用自行维护的注册表不能替代这些内核索引。

`entry(id)` 将精确的全局查找与历史文档读取所需的提交序列（commit sequence）一并返回。`entry(conversationId, id)` 只有在该条目通过所请求会话的祖先可见时才返回这一对值。`limit` 始终是最大页大小。
`findDocument()` 在当前或历史成员关系中解析一个精确的逻辑 kind/scope/key 地址。缺省 key 指的是单例（singleton），而不是家族（family）的每一个成员。`scanDocuments()` 只枚举某个精确 scope 在其选定时间点仍然存活的所有化身（incarnation），并且可以限制为单个 family/singleton kind。它按化身 ID 升序排列。常规流程中不存在打开时的全文档扫描。任务查询支持会话、kind、存活/终态（terminal）状态、中止标记和后台状态。

`document(id, at)` 具体化（materialize）一个特定的化身，绝不会跟随同一逻辑地址上的替换。调用方在尚未持有化身 ID 时，应当用 `findDocument()` 解析地址。它选取最新的适用基线，按序应用其 Chord 增量尾部（delta tail），并返回与调用方隔离的具体化值、已存储的定义版本，以及该基线之后重放的增量数量。基线/增量记录是后端私有的。查找绝不会扫描无关文档。未知 ID 返回 `undefined`。在 `"current"` 时间点，已退役的化身返回 `undefined`。对可回退（rewindable）会话化身的数字 ID 查找，在其半开生命周期之外返回 `undefined`，在其内则重建所选的值。对已知仅存在于当前（current-only）的化身进行数字查找会直接拒绝，而不是依赖已被回收的内容。元数据的成员关系在历史维度上仍可查询。缺失必需的基线、增量尾部内出现版本变化，或在可寻址生命周期内无法应用的操作，都判定为存储损坏（corruption），而不是数据不存在。

一个规范化批次中，每个化身最多包含一条 create/change 内容命令，并且还可以退役该化身。Storage 在退役之前应用内容，与写入数组的顺序无关。先创建后退役，会用批次序列同时标记生命周期的两个边界。在同一逻辑地址先退役后创建，会让新化身从该序列起成为当前化身。增量不能跨越已存储的版本边界；版本切换必须落成一个基线。

语义一致性测试套件（conformance suite）覆盖 memory、SQLite 和 JSONL 三种实现。

## 11. 后端

### 11.1 Memory

内存存储是参考语义（reference semantics）。它会复制保留的写入值和所有读取结果。这是有意模拟 SQLite 编解码和 JSONL 序列化自然产生的所有权边界，而不是防御性校验。它保留可回退的记录，并且只在提交了基线或退役之后才回收最新记录。

### 11.2 SQLite

一个 SQL 事务对应一次 Session 提交。SQLite 存储：

- conversation、entry、task 和 submission 记录；
- document 记录；
- 按文档和提交序列建立索引的文档基线/增量。

存活任务的状态迁移通过替换单行完成。终态任务以小记录的形式保留。文档读取使用带索引的「基线+尾部」区间。首个实现直接存储 Chord 记录，不把通用操作翻译成 SQLite JSON 函数。

模式（schema）形状、WAL 检查点节奏和 synchronous 默认值都属于后端实现选择，由一致性测试、重开测试、查询计划测试和存储基准测试来验证。

### 11.3 JSONL

JSONL 依赖的是可移植的 `FileSystem` 能力（capability），而不是更宽泛的 `ExecutionEnv`。它使用可回收的边车文件（sidecar），但不把它们暴露给 harness。仅有持久化并不提供所有权边界：内存中保留的任何已解码索引、具体化值或缓存，都必须与提交参数相互隔离，并且不得通过读取直接暴露。JSONL 后端不能只是在别名共享的内存表外面简单加上文件追加。

```text
main.jsonl       table writes, document records, and one marker per commit
doc-<id>.jsonl   one document incarnation
task-<id>.jsonl  live task replacements
```

发布协议：

1. 向每个受影响的边车文件追加完整的预备记录。
2. 追加一条完整的 main 标记，列出这些记录。
3. 只有在标记写入成功之后，才在内存中发布。

每次提交都使用这一协议；不存在只写边车的快速路径。JSONL 创建时接受一个 `fsync` 选项，默认为 `false`。不启用 `fsync` 时，它只保证普通的进程崩溃一致性，不保证在断电、主机、内核或文件系统故障后存活。`fsync: true` 时，后端先追加所有受影响的边车记录，逐个刷写（flush）受影响的边车，然后才追加 main 标记。普通发布不会显式刷写 `main.jsonl`；因此一个已被确认的尾部提交仍可能消失，但存活下来的标记不应超过其边车数据。仅含 main 的提交没有需要刷写的边车。在 `fsync: true` 的前提下进行破坏性回收之前，后端会把 `main.jsonl` 刷写一次，以确保授权标记不会在替换或删除内容存活时反而消失。如果这次刷写失败，已提交状态保持已发布，回收被推迟。非空的临时替换文件也会在重命名之前刷写。

恢复流程：

- 移除被截断的末尾行。
- 忽略并移除未确认的边车尾部。
- 只应用已确认的记录。
- 缺失必需的已确认数据属于损坏，打开失败。
- 后提交的最新基线或退役可能证明更早的物理记录已无必要。
- 任何结果不确定的追加失败都会毒化（poison）已打开的后端。

回收只有在授权它的基线/退役提交之后才会开始。当边车中不再有任何记录时，直接删除该边车文件。否则，它会写入一个临时替换文件，重命名它，并使缓存的文件描述符失效，使后续追加不会指向已被取消链接的 inode。为授权回收而刷写 `main.jsonl` 并不会压缩它。初始实现不压缩 `main.jsonl`。

## 12. API 陷阱

以下 API 陷阱（footguns）条目都是契约，而不是邀请你添加防御性机制：

- **脱离的草稿操作（detached draft work）：** 草稿读取、草稿写入以及所有 `Tx` 操作在 Session 回调结束之后都会拒绝。在回调结束之前运行的「发射后不管」（fire-and-forget）工作仍然可以修改活动事务，这种用法不受支持。
- **写后读取：** 在第一次表写入之前，先读取所需的每一个表行。此后文档草稿仍然可用；表读取则不然。
- **向繁忙会话写入：** 只有 Harness 会向存在活动运行的会话追加内容。在某次生成准备请求期间，由 `Harness.commit()` 或自定义任务追加的原始条目可能错置其系统提示（system prompt）条目；请使用写入提交（write submission）。
- **运行失败后的排队项：** 失败与任务中止不会动收件箱（inbox）。排队的后续事项（follow-up）会在 `pi.inbox` 中等待，其 `wait()` 不会结束，直到下一次提交的边界安置它们，或宿主将其撤回。压缩摘要就是这样一次提交：当手动或后台压缩在那个空闲会话中完成时，其最终边界会安置这些等待中的后续事项，并启动一次运行。
- **压缩开销：** 每一次手动与后台压缩，每次尝试都要支付一次摘要请求的费用，即便其摘要最终因后续压缩切得更深而过时作废，也同样要付费。
- **压缩期间的头标记与编辑：** 摘要反映的是其压缩选定范围那一刻的上下文。在摘要生成期间放置的应用编辑——例如替换条目 20 的写入——会在摘要切过其目标时丢失：摘要仍描述旧的条目 20，而编辑的目标已经离开范围。在此期间放置的应用头标记（head），例如一个切在 85、用来遗忘条目 10-84 的头标记，会被一个切在 90 的摘要撤销：该摘要仍描述 10-84。请把这类写入放在压缩之前进行。
- **摘要时间戳：** 排队摘要的用户消息携带的是其压缩完成的时间，而不是它被安置的时间。依靠消息时间戳判断用量是否过时的代码——例如对视图消息使用 pi-ai 的 `estimateContextTokens()`——可能误判；Harness 的估算使用条目顺序（8.3 节）。
- **直接把头标记写入过去：** 用 `tx.appendEntry()` 直接写入、指向会话活动范围之前条目的头标记会改变模型上下文；但已挂载的视图只会保留它已经持有的条目，直到挂载被重建为止。请改用写入提交，它的过期检查会拒绝这种写入。
- **子代理开销被重复计算：** 运行一个自有会话的工具，不得在其结果中上报该会话的用量；子会话的 `pi.usage` 已经把它计入，子树求和会把它计算两次。
- **自有工作拖住其所有者：** 拥有存活普通工作的任务会一直停留在 `completing` 状态，直到该工作结束（5.5 节）。扩展在子代理（subagent）会话中启动的前台工作会拖住调用方工具，进而拖住整个运行；在该子代理的工具处于完成过程中时向它提问，会延长这种占用。Esc 或宿主超时可以结束它；不应拖住所有者的工作，应创建为会话自有且 `background` 的任务。
- **钩子创建的工作：** 钩子运行在发起任务（asking task）的调用之内，因此它们创建的、归属该任务的工作会拖住它。必须延迟任务完成的工作，必须在任务提交其结果之前创建；事后响应已发布事件的监听器无法延长它。运行任务的自有工作不得在运行被释放之后再写入转录（transcript）。
- **中止处理器中的补偿：** 中止处理器无法创建自有子任务，因为它所在的任务已被标记中止。补偿应当在产生效果的层级进行：在该任务自己的中止处理器中、或以内联方式、或通过用 `waitForTask()` 等待的后台会话自有任务来完成；非后台的任务会被任何波及其会话的级联中止所中止。
- **钩子备忘名：** 钩子与发起任务以及其他钩子共享该任务的备忘（memo）命名空间。请给备忘名加上前缀。
- **长事务：** 异步提交回调持有 Session 的变更线。绝不要在其中 await 模型、工具、进程、网络调用、人类、嵌套的 Session 提交或 Session 等待者。请使用当前 `Tx` 上的方法。
- **显式创建：** 只有带类型的 `tx.doc()` 才会创建不存在的文档。快照（snapshot）、状态（state）和监听（watch）查找只会返回 `undefined`。
- **家族初始化：** 对不存在的家族地址的首次获取会选定其种子（seed）。已存在的实例与后续调用都会忽略种子；种子既不是身份，也不是更新。
- **检查点饥饿：** 如果 `checkpointWhen()` 从不返回 true，那么在文档存活期间，重放数据与仅当前文档存储都可能无界增长。
- **错误的 fork 设置：** `current`、`initial` 与 `asOf` 是产品语义，不是性能优化。改动其中任何一个都会改变子会话的行为。
- **模式稳定性：** 文档 kind 与可见挂载路径是持久化的公开协议。值迁移不能重命名 kind；更换 kind 需要显式复制并退役。传入声称同一 kind 却互不兼容的定义令牌（token），属于不受支持的调用方误用；Session 并不维护文档定义注册表来检测这种情况。
- **受信任的不可变修订：** `snapshot()` 的结果、状态值、监听值及其后代可能共享由跟踪器（tracker）拥有的容器。绝不要原地修改它们；需要可变所有权时请先复制。运行时不提供冻结（freeze）。
- **监听激活：** 在 `start()` 之前，`watch.value` 一直是获取时的那份不可变修订。请先用它完成消费者初始化。start 之后，该属性会在每次回调执行之前推进到每一个已交付的不可变修订；所有更早的引用都保持稳定。
- **带缓冲的监听：** 缓慢或尚未启动的监听最多保留 100 个精确的已提交帧。发生溢出时，会用一次全值根替换来取代未交付的后缀，因此中间的已提交状态可能被省略。必须审计每一次状态转换的消费者，应当把每个事实持久化到不可变条目或日志（journal）中，并显式扫描这段历史。
- **监听停止：** 监听器可以调用并 await `stop()`；它能阻止未来的回调，但既不会中止已在运行的回调，也不会等它完成。
- **持久化进度的节奏：** 客户端只能看到已提交的进度。崩溃可能丢失当前未提交的节流窗口（throttle window）。
- **大型终态结果：** 终态任务记录仍然可查询。请把大型结果放进条目或寿命更长的文档，并在结果（outcome）中只保留它们的 ID。绝不要引用被同一结果退役的任务域（task-scoped）文档。
- **原始转录：** 视图条目并不是模型上下文。渲染编辑、仅用于显示的条目以及对模型的过滤，都需要相应的 reducer。
- **保留的 `pi.` 名称：** 以 `pi.` 开头的任务名、文档 kind 和条目 kind，按约定属于内建（built-in）。没有任何机制强制这一点；复用它们会与 Harness 行为冲突，例如 `pi.system` 条目会被重放为系统消息。
- **过早释放资源：** 卸载或替换扩展只是停止新的使用。立即释放资源，可能让仍在运行中的调用失败。
- **选择中遗漏的守卫：** 使用数组选择、但遗漏了某个守卫扩展（例如权限钩子）的会话，将在缺少它的情况下运行。扩展只能整体选择；不存在横跨注册表的钩子或包装器。
- **选择的编辑与复制：** `{ add, remove }` 总是编辑宿主默认选择。若把它写入一个从所有者复制过选择（无论是数组还是 `{ add, remove }` 对象）的子会话，它会整体替换那份选择，于是子会话得到的是「施加了编辑的宿主默认选择」，而不是所有者的选择。应当改为从解析后的 agent 计算子会话的数组（7.3 节）。
- **复制只有一次：** 新建的任务自有会话会在创建时复制其所有者的 `pi.agent`；之后所有者的变更不会传导到它。而 fork 保留的则是其在 `asOf` 时点的副本（2.2 节）。
- **恢复时的环境：** 恢复之后的工具重跑会重新构建环境，使用会话当前的 `cwd`，它可能与首次尝试时不同。
- **默认选择的漂移：** 位于默认选择上的会话，只要设置或已安装扩展发生变化就会随之改变；每次变化都会追加 `pi.system` 条目，并且错过提供商（provider）的提示缓存。
- **不稳定的提示文本：** 某个 section 渲染器若在真实内容未变的情况下输出仍然变化（例如嵌入了时间），就会追加系统增量（delta），并使提供商的提示缓存失效。
- **关闭时的不合作代码：** close 会等待（join）每一个调用结束。忽略关闭信号的任务处理器、工具或钩子，会让 `close()` 一直挂起、Storage 一直打开，直到它自己返回；取消对 close 的等待并不能终止它。
- **比 Harness 更长寿的服务：** 关闭 Harness 之前，先撤回 Chord 服务并分离（detach）客户端。被 close 终止的状态会保留最后一个值，并且永远不再更新。
- **致命的存储错误：** 在出现一次结果不明确的存储失败之后，Session 已被毒化。不要捕获错误后继续使用它。
- **JSONL 持久性：** 默认的 JSONL 排序能应对普通的进程崩溃；在不启用持久模式（durable mode）时，它不承诺已确认的提交能在断电或主机故障后存活。

## 13. 非目标

Pico5 初期明确将下列内容列为非目标（non-goals），即不具备：

- 覆盖整个 Session 的 DOM（whole-Session DOM）；
- 可见但不持久的发布（visible-undurable publication）；
- Session 内核的语义事件日志（event journal），或独立维护的事件状态；
- 会话域的可回退文档；
- 自动检查点启发式；
- 自动挂载第三方视图；
- CRDT/离线多写者合并；
- 任意 Chord 操作到 SQL 的翻译；
- JSONL 全局压缩或自动损坏修复；
- 针对已移除 Pico 原型的兼容层；
- 在单进程内强制终止不合作的扩展代码。
