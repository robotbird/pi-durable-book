## 8. 内置任务

初始实现提供以下内置任务（built-in tasks）：

| kind | 职责 |
|---|---|
| `pi.generation` | 准备系统提示词与工具，请求或轮询（poll）模型，重试，对响应进行分类 |
| `pi.tool` | 校验、挂接钩子（hook）、执行，持久化输出与 details，追加结果 |
| `pi.compaction` | 选定转录（transcript）区间，生成摘要（summary），放置带头（head）的摘要条目 |

生成任务（generation task）直接使用 `HarnessOptions.models`，不需要 Pico 专属的模型适配器。它解析 `models.getModel(ref.provider, ref.modelId)`，用准备好的提示词/消息/工具构建 pi-ai 的 `Context`，并以任务调用的 abort 信号、agent 的 thinking level 以及设置中的 stream 选项调用 `models.streamSimple()`。延迟续取（deferred continuation）则用同一个模型和信号调用 `models.fetchDeferred()` 与 `models.cancelDeferred()`。缺失的模型以及 pi-ai 的同步/流式错误会被归类到下文的持久化生成结局（durable generation outcomes）中。

生成与工具进度都是经过节流（throttle）的持久化文档提交。崩溃最多只会丢失未提交的节流窗口。恢复时会把已提交的部分内容（partial）转换为普通的 interrupted/aborted 转录条目，清空展示状态，然后按任务所处阶段决定重试还是终止。对迟到加入者而言，重试期限、尝试次数、压缩（compaction）与工具进度都是当前文档状态；已完成尝试的用量/记账则承载于条目或终态 detail 中。截断（truncation）与溢出转存（spill）路径属于工具诊断（第 7.3 节）。

压缩通过追加一条带头（head）的摘要条目来改变模型上下文。它不会删除转录历史。

### 8.1 内置条目

内置条目类型（kind）不携带 `data`，但有两类例外：`pi.tool-result`，其 token 为 `Entry<{ diagnostics: ToolDiagnostic[] }>`——每条工具结果都携带 `data`，没有诊断（diagnostics）时为空列表（第 7.3 节）；以及 `pi.compaction`，其 token 为 `Entry<{ reason: CompactionReason }>`。每个 kind 都以 `Entry` token 的形式导出。

| kind | `model` | 写入者 |
|---|---|---|
| `pi.user` | `[UserMessage]`，时间戳取自准入（admission）或放置（placement）时的 Harness 时钟 | 提交（submissions）、`onYield` 续接（continuations） |
| `pi.assistant` | `[AssistantMessage]`，停止原因（stop reason）不限 | generation |
| `pi.system` | `[SystemMessage]`，`content: ""`（第 7.4 节） | generation 的准备阶段 |
| `pi.tool-result` | `[ToolResultMessage]` | 工具任务；generation（针对其请求未提供的工具调用） |
| `pi.reset` | 缺省，或带交接（handoff）文本的 `[UserMessage]`；始终 `head: "self"` | `reset()`、generation 的 `tools` 阶段（针对 `handoff`） |
| `pi.compaction` | `[UserMessage]`，内容为包裹后的摘要；`head` 为第一个保留条目 | 压缩任务（第 8.7 节） |

每一次 generation 响应都会成为一条 `pi.assistant` 条目：正常回答、带错误文本与用量的失败尝试，以及以 `aborted` 为停止原因的转换后 partial。上下文推导（第 2.1 节规则 9）会把失败与中止的消息排除在后续请求之外，因此不需要单独的用量或通知条目类型。

### 8.2 实时文档（live document）

```ts
type LiveState = {
  /** Run control (section 6); present exactly while the conversation is busy. */
  run?: { taskId: TaskId; inputs: SubmissionId[] };
  /** Presentation of the current generation attempt. */
  generation?: {
    attempt: number;
    /** Committed throttled partial of the in-flight response. */
    message?: JsonRepresentation<AssistantMessage>;
    /** Durable backoff before the next attempt. */
    retry?: { at: number; error: string };
    /** Provider-side deferred response being polled. */
    deferred?: { pollAt: number };
  };
  /** The current tool round in call order, from the tool-calling answer until the generation's `tools` phase ends it. */
  tools?: {
    callId: string;
    name: string;
    /**
     * Absent for a call not started yet (sequential round, `pending`) and for a call its request did not offer,
     * which starts `done` with the `entry` generation wrote.
     */
    taskId?: TaskId;
    status: "pending" | "running" | "done";
    /** Retained running output and what the bounds dropped. */
    output?: string;
    droppedBytes?: number;
    droppedLines?: number;
    /** Last `details()` value. */
    details?: JsonValue;
    /** Diagnostics recorded through `api.diagnostic()`. */
    diagnostics?: ToolDiagnostic[];
    /** Result entry once done; absent when the tool task faulted or was orphaned. */
    entry?: EntryId;
  }[];
  /** Live compaction tasks in task ID order; absent when none (section 8.7). */
  compactions?: CompactionStatus[];
};

type CompactionStatus = {
  taskId: TaskId<CompactionResult>;
  reason: CompactionReason;
  /** Whether a generation waits for it: a compaction the generation owns. */
  blocking: boolean;
  attempt: number;
  /** Durable backoff before the next summarization attempt. */
  retry?: { at: number; error: string };
};
```

| 字段 | 值 |
|---|---|
| kind | `pi.live` |
| version | `1` |
| scope/history/fork | conversation、`latest`、`initial` |
| `initial()` | `{}` |
| checkpoint | 只要在没有任何东西运行时就写完整基（complete base）：`generation` 缺省且没有处于 `running` 的工具槽位 |
| view mount | `docs["pi.live"]` |
| created | 随每个 Harness 会话（conversation）一起创建（第 2.2 节） |

空闲时、处于最终边界（final boundary）时、generation 向其工具轮次（tool round）交接的那次提交中（此时每个槽位仍是 `pending` 或 `done`）、顺序轮次（sequential round）的各工具之间，以及并行轮次（parallel round）没有任何工具处于 `running` 时，都没有东西在运行。槽位只有在 `running` 时才持有输出，因此每个基（base）都很小；存储的 delta 链至多横跨一次 generation（包括其重试与 deferred 轮询），或一轮工具的重叠执行。保留的头部输出通过 Chord 字符串追加增长。滑动尾部通常表现为一次前端裁剪（front trim）加一次追加；当 Chord 的有界重叠搜索找不到共享部分时——例如输出高度重复，或窗口超过其 64 KiB 扫描范围——提交会把保留窗口整体写成一次 set。无论哪种情况，每次提交至多写一个窗口，节流则限制写入速率。

generation 在追加工具调用回答的那次提交里创建 `tools`，每个调用一个 `pending` 槽位；请求未提供的调用则以 `done` 起始并携带其结果条目。工具任务在其意图提交（intent commit）中把槽位设为 `running`，向其中发布节流后的输出与 details，并在其终态提交中设为 `done`、写入 `entry`，同时移除 `output`、`droppedBytes`、`droppedLines`、`details`、`diagnostics`——这些此时改由结果条目承载（第 7.3 节）。generation 的 `tools` 阶段移除 `tools`。槽位更新仅在存在携带该任务 `taskId` 的槽位时生效；若不存在，持久化的部分输出、details 与 diagnostics 视为空。

压缩任务的状态在创建任务的提交中添加，在决定其结果的提交中移除：即任务自身的结果提交（即使该结果以 `completing` 形式挂起，第 5.5 节），或调度器的清理（第 5.4 节）。状态保持很小：摘要文本存放在任务的放置（placement）中，绝不放在这里。partial 在赋值前会被规范化为严格 JSON。run 任务的每条终态路径都会在结算 run 输入的那次提交中移除 `run`、`generation` 与 `tools`。`tx.settleSubmission()` 在组装（assembly）期间暂存（stage）每个输入的新状态，并解析事务中最新的候选提交记录，若无则回退到已提交状态——与任务文档校验（第 3.3 节）相同——因此它不是调用方的表读取，并且在提交的第一次表写入之后也能正常工作。

### 8.3 生成（Generation）

```ts
type GenerationInput = {};
type GenerationCheckpoint =
  | {
      phase: "prepare";
      attempt: number;
      /** The blocking compaction this generation waited for; it starts no other compaction. */
      compacted?: TaskId<CompactionResult>;
      /** Error text of the overflow that started `compacted`; checked once when `prepare` resumes. */
      overflow?: string;
    }
  | {
      phase: "request";
      attempt: number;
      compacted?: TaskId<CompactionResult>;
      model: ModelRef;
      thinkingLevel: ModelThinkingLevel;
      streamOptions: ConversationStreamOptions;
      /** Newest entry included in the request. */
      cutoff: EntryId;
    }
  | { phase: "retry"; attempt: number; compacted?: TaskId<CompactionResult>; until: number }
  | {
      phase: "poll";
      attempt: number;
      compacted?: TaskId<CompactionResult>;
      model: ModelRef;
      cutoff: EntryId;
      handle: DeferredHandle;
      pollAt: number;
    }
  | {
      /** Waiting on the round's tool tasks; `waiting` holds this checkpoint (section 8.5). */
      phase: "tools";
      assistant: EntryId;
      tools: TaskId<ToolTaskResult>[];
      /** Calls of a sequential round not started yet, in call order. */
      pending: string[];
    };
type GenerationResult = { entryId: EntryId };
```

`pi.generation` 版本为 1，起始检查点为 `{ phase: "prepare", attempt: 1 }`。run 的输入存放在 `pi.live.run` 中，而不是任务输入里。

- `prepare` 按本阶段的 agent 解析方式执行第 7.4 节，并一次性解析设置。当 agent 没有模型、或 `models.getModel()` 不认识该模型时，任务以 `no_model` 失败。当它带着 `overflow` 恢复而其压缩没有以 `entryId` 完成时，run 以 `model_error` 失败，detail 为溢出（overflow）文本。否则，一次提交追加计划好的 `pi.system` 条目，并以新的尾部作为 `cutoff`、agent 的模型与 thinking level、设置的 stream 选项进入 `request` 阶段。这些在本次请求尝试内保持固定；重试（retry）则重新准备。`compacted` 会延续到 `request`、`retry`、`poll` 与下一次 `prepare`。
- 在那次提交之前，当设置的压缩策略启用、模型的 `contextWindow` 为正、且 `compacted` 缺省时，`prepare` 会检查压缩阈值（第 8.7 节）。估算从已提交模型上下文中最新的一条 assistant 消息开始——其条目必须是在头标记（head marker）之后追加的（没有头标记时全部符合），且其 usage 非零——取其 usage 的 pi-ai `calculateContextTokens()`，加上其后每条上下文消息以及计划中的系统消息的 pi-ai `estimateMessageTokens()`。该消息的请求包含标记，因为头只在没有请求在途时放置。若没有这样的消息，则对所有消息进行估算。两个阈值都只在区间选择（range selection）找到切点（cut）时适用。
  - 超过 `contextWindow - reserveTokens`（阻塞阈值）时：不追加，而是一次提交创建一个由 generation 持有（owned）的压缩，原因（reason）为 `threshold`，添加其状态，并以 `allSettled` 与检查点 `{ phase: "prepare", attempt, compacted }` 提交 `waiting`。无论压缩结果如何，`prepare` 之后都会重新运行并发送请求。
  - 超过 `contextWindow - reserveTokens - backgroundTokens` 且 `backgroundTokens > 0`、`pi.live` 中没有压缩状态时：进入 `request` 的那次提交同时创建一个由会话持有的后台压缩，原因 `threshold`，并添加其状态。generation 不等待它。设置中的重试策略在本次尝试的结果被分类时读取，因为它决定下一次尝试（第 7.1 节）。
- `request` 与 `poll` 通过 `models.getModel()` 解析检查点中的模型；未知模型使任务以 `no_model` 失败，同 `prepare`。`request` 在解析模型之前会先转换遗留的 partial（见下）。
- `request` 先把上一次被中断的尝试留在 `pi.live` 中的已提交 partial 转换为一条 `aborted` 的 `pi.assistant` 条目。然后以调用信号、作为 `reasoning` 的 thinking level（`off` 时省略）、对话持久化的供应商 `sessionId`，以及固定的（pinned）`streamOptions`，将截至 `cutoff` 的模型上下文进行流式请求，期间提交节流的 partial。在开始流式之前，`beforeRequest` 链可以替换本次请求的消息（仅对本请求生效）。恢复时以相同的固定模型、thinking level 与 stream 选项重发相同的已提交消息，并重新运行 `beforeRequest`。
- `afterResponse` 在分类之前观察来自 `request` 或 `poll` 的每条终态消息；仍处于 deferred 的结果不算终态。
- 分类之前，处理器停止 partial 节流并等待在途的 partial 提交完成，确保结局（outcome）之后不会落下一个过期 partial。终态消息在一次性提交中完成分类，该提交同时清除 partial：
  - `stop`/`length`：在该提交之前，`onYield` 链先行运行；第一个 `{ continue }` 生效。该提交追加回答并施加最终边界（第 6 节）。若有续接（continuation）且没有选中的用户条目（user item）或重置，则追加一条带续接内容的 `pi.user` 条目，创建后继 generation 并把 `pi.live.run` 交给它，保持输入打开。否则把 run 的输入结算为 `done`，移除 `run` 与 `generation`，并为选中的用户条目（若有）启动后继 run；被丢弃的续接不会重试。两者都以 `{ entryId }` 完成。
  - `toolUse` 且至少有一个工具调用：该提交追加 assistant 条目并启动下文描述的工具轮次，进入 `waiting` 的 `tools` 阶段。没有调用的 `toolUse` 消息按 `stop` 分类。
  - `error` 且被 pi-ai `isContextOverflow()` 识别，同时设置的压缩策略启用、`compacted` 缺省、区间选择找到切点：该提交追加错误条目，移除 `generation`，创建由 generation 持有的、原因为 `overflow` 的压缩，添加其状态，并以 `allSettled` 与检查点 `{ phase: "prepare", attempt, compacted, overflow }` 提交 `waiting`；恢复后的请求不计入重试策略。任何其他溢出（包括第二次溢出）都不重试，而是像下文的不可重试错误那样失败。`stop` 或 `length` 响应永远不会被分类为溢出；静默溢出由下一次阈值检查处理。
  - `error` 且被 `isRetryableAssistantError()` 接受，同时设置中的重试策略允许再试一次（`enabled` 且 `attempt <= maxRetries`，即 `maxRetries` 统计首次尝试之后的重试次数）：追加错误条目，并以 `until = now + retryDelayMs(policy, attempt)` 进入 `retry`。
  - 其他任何 `error`，或没有中止标记的 `aborted`：追加错误条目，把输入结算为 `unanswered`（原因 `model_error`），移除 `run` 与 `generation`，并失败。
  - `deferred`：以 `pollAt = now + (handle.pollAfterMs ?? 5000)` 进入 `poll`。
- `retry` 睡眠至 `until`，然后以下一次尝试回到 `prepare`，因此退避（backoff）期间发生的 agent 与设置变更会生效。
- `poll` 睡眠至 `pollAt` 并调用 `models.fetchDeferred()`。仍为 deferred 的结果把 `pollAt` 严格推后；其他结果按上文分类。
- 中止处理器在 `poll` 中于模型已知时调用 `models.cancelDeferred()`（失败会被上报），转换已提交的 partial，把输入结算为 `unanswered`（原因 `aborted`），移除 `run` 与 `generation`，并以 `aborted` 结束。

工具轮次在追加工具调用回答的那次提交中启动：

1. 通过 pi-ai `getCurrentTools()` 从截至 `cutoff` 的已提交模型上下文中重放（replay）所提供的工具：`request` 已经持有该上下文，`poll` 则重新推导。对未提供工具的调用在此处获得其 `tool_unavailable` 结果条目，不创建任务。
2. 其余每个调用都获得一个由 generation 持有的 `pi.tool` 任务，输入为 `{ assistant, callId }`。当轮次启动时读取的设置项 `toolExecution` 为 `sequential`，或任何被调用工具（按工具任务的方式从本阶段 agent 解析，第 7.3 节）具有 `executionMode: "sequential"` 时，轮次为顺序执行：此时只有第一个调用立即获得任务，其余在 `pending` 中等待。否则所有调用立刻各自获得任务并行执行。检查点的 `tools` 列出迄今创建的任务，并随每个启动的顺序调用增长一，`pending` 相应缩短。
3. generation 以 `allSettled` 与 `tools` 检查点在其工具任务上提交 `waiting`（第 8.5 节）；`pi.live.run` 仍归其所有。
4. `pi.live.tools` 接收本轮的槽位（第 8.2 节），`generation` 被移除。

输入提交以以下原因之一结算为 `unanswered`：`no_model`、`model_error`（detail：提供方错误文本）、`aborted`、`faulted`（detail：错误消息），或某个导致孤儿化（orphaning）的阻塞原因（第 5.4 节）。故障（fault）与孤儿（orphan）结算会像中止处理器一样，把已提交的 partial 转换为 `aborted` 的 `pi.assistant` 条目。

### 8.4 工具（Tool）

```ts
type ToolTaskInput = { assistant: EntryId; callId: string };
type ToolTaskCheckpoint =
  | { phase: "call" }
  | { phase: "execute"; arguments: JsonObject; replay: "safe" | "unsafe" };
type ToolTaskResult = { entryId: EntryId; control?: ToolControl };
```

`pi.tool` 版本为 1，起始检查点为 `{ phase: "call" }`。输入保持很小，因为终态记录会保留它；调用本身从 assistant 条目中读取。

- `call` 用 `runtime.entry()` 读取调用，在本阶段 agent 的 `tools` 中解析工具（第 7.3 节），用 pi-ai `validateToolArguments()` 校验参数，运行 `beforeTool` 链，然后再次校验（第 7.3 节）。随后一次提交记录意图：以最终参数和该工具的重放（replay）策略进入 `execute`，并把槽位设为 `running`。同一个处理器执行工具、运行 `afterTool` 链并提交结果；它在执行前一刻用 `HarnessOptions.env` 构建 `api.env`（第 2.2 节）。工具解析不到、参数无效或被阻塞时，改为提交相应的错误结果，不记录意图。
- `execute` 只有恢复时才会到达。当存储的策略与当前策略（按 `call` 的方式解析）都为 `safe` 时，它用存储的参数再次执行（不运行 `beforeTool`），并像 `call` 一样结算。否则它根据槽位持久化的部分输出、details 与 diagnostics 提交一个 `interrupted` 错误结果，并以 `{ entryId }` 结束 `failed`。
- 结果提交会对内容限界、追加诊断块（第 7.3 节），追加一条 `pi.tool-result` 条目，其 `model` 为 `[{ role: "toolResult", toolCallId, toolName, content, details, isError, timestamp }]`、`data` 为 `{ diagnostics }`，把槽位标记为 `done`，并以 `{ entryId, control }` 完成。`isError` 的结果同样正常完成。
- `execute()` 抛出异常，或 `HarnessOptions.env` 在构建环境时抛出异常，都会产生一个 `tool_error` 结果，任务以 `{ entryId }` 结束 `failed`；一旦调用已被信号通知（signalled），异常则改为向上传播。以 `failed` 结束与 `aborted` 一样会记录取消意图（第 5.4 节），因此该调用拥有的、已无人监督的会话会被中止。返回的 `isError` 结果仍正常完成，其调用拥有的工作得以存活。无论哪种情况，run 都带着结果条目继续。若工具任务在提交结果时其拥有的会话仍有普通工作在进行，它将以 `completing` 挂起，此时结果条目已写入（第 5.5 节）；generation 只在工具任务达到终态后才恢复。
- 中止处理器根据槽位持久化的部分输出、details 与 diagnostics 提交一个 `aborted` 错误结果，并以 `{ entryId }` 结束 `aborted`。

### 8.5 工具轮次（tool rounds）

当其等待的每个工具任务都达到终态后，generation 在 `tools` 阶段恢复。顺序轮次中若 `pending` 还有调用，一次提交创建下一个调用的自有工具任务，并带着更短的 `pending` 再次等待。否则，它用 `runtime.getTask()` 读取工具记录、从 `pi.live.tools` 槽位读取本轮的结果条目，运行 `afterTools` 观察者，然后一次性提交：

- 对每个 `addTools` 名称，它会编辑会话存储的 `pi.agent` `tools`：数组在未包含该名称时追加之，`{ remove }` 则移除该名称。`tools` 未设置时，所有工具本就都被提供，不写任何东西。下次准备在解析到该工具时会将其提供。
- 当本轮所有结果都请求 `terminate`，或任一结果请求 `handoff` 时：追加交接的 `pi.reset` 条目（若有），以工具调用回答把 run 的输入结算为 `done`，移除 `run` 与 `tools`，并施加最终边界。
- 否则移除 `tools` 并施加 `postTools` 边界。若该边界放置了一次重置（reset），run 的输入以 `reset` 结算为 `unanswered`，被选中的用户条目启动后继 run（第 6 节）。否则被选中的 steer ID 加入 `pi.live.run`，它创建下一个由会话持有的 generation 并把 run 交给它。

它以工具调用回答的 `{ entryId }` 完成。其中止处理器只在工具任务都达到终态后运行（第 5.5 节）。对每个仍处于 `pending`、从未启动的调用，它追加一个 `aborted` 错误结果；已启动但其任务故障或被孤儿化的调用保留其无条目的 `done` 槽位（第 8.2 节）。随后它把输入结算为 `unanswered`（原因 `aborted`），移除 `run`、`generation` 与 `tools`，并以 `aborted` 结束。因此对 generation 调用 `abortTask()` 会中止其整个轮次。

### 8.6 用量（Usage）

```ts
type UsageState = {
  /** Assistant entries and compaction summarization attempts, keyed `provider/modelId`. */
  models: Record<string, Usage>;
  /** Tool results, keyed by tool name; their usage has no model identity. */
  tools: Record<string, Usage>;
};
```

| 字段 | 值 |
|---|---|
| kind | `pi.usage` |
| version | `1` |
| scope/history/fork | conversation、`latest`、`initial` |
| `initial()` | `{ models: {}, tools: {} }` |
| checkpoint | 每次变更都写完整基 |
| view mount | `docs["pi.usage"]` |
| created | 随每个 Harness 会话一起创建（第 2.2 节） |

`pi.usage` 是会话自身开销的台账（ledger）。每个写入 `pi.assistant` 条目的内置写入者都会在同一次提交中把该消息的 `usage` 按消息自身的 `provider/model` 加进 `models`；每个写入带 `usage` 的 `pi.tool-result` 条目的写入者都把它加进 `tools`。压缩任务的每次摘要尝试都会在分类它的那次提交中把其响应的 `usage` 加入 `models`（第 8.7 节）；无论摘要是被放置、失败还是最终过期（stale），这笔开销都没有条目。失败与中止的尝试也计入。fork 从零开始，因此不会有开销被重复计算。`Harness.usage()` 把每个会话的文档求和进 Session 总计；其他总计（如所有权子树）是对 `scanConversations()` 的应用层求和。没有任何东西跨会话存储总计。

### 8.7 压缩（Compaction）

```ts
type CompactionReason = "manual" | "threshold" | "overflow";
type CompactionInput = { reason: CompactionReason; instructions?: string };
/** The pinned summarization request. */
type SummaryRequest = {
  attempt: number;
  model: ModelRef;
  thinkingLevel: ModelThinkingLevel;
  streamOptions: ConversationStreamOptions;
  maxTokens: number;
  /** Newest entry of the context the range was selected from. */
  tail: EntryId;
  /** First entry kept verbatim; the summary's `head`. */
  firstKept: EntryId;
};
type CompactionCheckpoint =
  | { phase: "select" }
  | ({ phase: "summarize" } & SummaryRequest)
  | ({ phase: "retry"; until: number } & SummaryRequest);
/**
 * `entryId` of a blocking compaction's summary, or the `submissionId` of a conversation-owned compaction's summary
 * write; both absent when nothing was compacted.
 */
type CompactionResult = { entryId?: EntryId; submissionId?: SubmissionId };
```

`pi.compaction` 版本为 1，起始检查点为 `{ phase: "select" }`。压缩用一条 `head` 为第一个保留条目的摘要条目替换模型上下文的旧前缀（第 2.1 节）。原始历史仍保留在存储中。有三种启动方式；任务本身相同，只是所有权与放置方式不同：

| 启动方式 | 持有者 | 后台 | generation 是否等待 | 放置方式 |
|---|---|---|---|---|
| `Conversation.compact()` | 会话 | 否 | 否 | 写入提交（write submission） |
| generation 超过后台阈值 | 会话 | 是 | 否 | 写入提交 |
| generation 超过阻塞阈值，或发生溢出 | 该 generation | 否 | 是 | 直接追加 |

只有阻塞式压缩（blocking compaction）会在会话的 run 等待它时运行。其余压缩从不取得 run 控制：它们做摘要时，会话继续工作，其摘要像任何被动写入一样被放置。压缩之间互不协调；多个可以同时运行，由第 6 节在它们的摘要之间做裁决。

**区间选择（range selection）** 是一个以 `ContextView` 为输入的纯函数：其 `contributions` 给出每个活跃条目在区间内经过每次编辑之后的模型消息（第 2.1 节规则 4 与 9），包括更早的区间内标记所携带的编辑；外加设置中的 `keepRecentTokens`。

1. 切点候选（cut candidates）是其贡献（contribution）以用户或 assistant 消息开头的非标记条目。工具结果与系统条目永远不是候选，因此被保留的 assistant 消息连带保留其工具结果。当某用户条目之后、下一个 assistant 之前，仍跟有其前面 assistant 某次调用的结果时，该用户条目也不是候选（第 2.1 节规则 7）。
2. 从新到旧遍历非标记条目，累加每条贡献的 pi-ai `estimateMessageTokens()`。在总和首次达到 `keepRecentTokens` 的条目处，切点取转录顺序中该条目或其后第一个候选；若其后没有候选，则取最新的候选。
3. 当总和从未达到 `keepRecentTokens`，或切点之前没有任何非标记条目贡献模型消息时，没有可压缩的内容。

被摘要的条目是头标记（若有），加上切点之前的非标记条目。它们的消息即其贡献，按第 2.1 节规则 7 与 8 的顺序排列，因此较早的摘要会与其后的历史一起被再次摘要。上下文小于 `keepRecentTokens` 时不会有任何压缩，因此在 `contextWindow - reserveTokens` 低于该值的窗口下，溢出可能先于任何阈值压缩发生。

```text
1 user   2 assistant (read)   3 tool result, 30k tokens   4 assistant   5 user   6 assistant
keepRecentTokens 20k: the walk from 6 reaches 20k at 3; the first candidate at or after 3 is 4.
The summary covers 1-3; the model context becomes [summary, 4, 5, 6].
```

译注：`keepRecentTokens` 为 20k 时，从条目 6 向前累加，至条目 3 处达到 20k；条目 3 及其后第一个候选是 4。摘要覆盖条目 1–3；模型上下文变为 [summary, 4, 5, 6]。

各阶段：

- `select` 采用本阶段的 agent 解析，一次性解析设置，并捕获已提交的上下文。当 agent 没有模型、或 `models.getModel()` 不认识该模型时，任务以 `no_model` 失败。没有可压缩内容时以 `{}` 完成。否则 `beforeCompact` 钩子（第 7.2 节）带着被摘要的条目与消息运行；第一个决策生效。`{ decline: true }` 以 `{}` 完成；`{ summary }` 则在同一次提交中按下文放置。没有决策时，一次提交以 attempt 1、agent 的模型与 thinking level、设置的 stream 选项、`maxTokens` = `min(floor(0.8 * reserveTokens), model.maxTokens)`（模型值仅在为正时采用）、捕获的尾部（tail），以及作为 `firstKept` 的切点进入 `summarize`。
- `summarize` 从 `tail` 处的上下文（不可变）再次推导被摘要的消息，并把它们序列化为文本：`[User]: ...`、`[Assistant thinking]: ...`、`[Assistant]: ...`、`[Assistant tool calls]: name(key=json, ...)`，以及截断到 2000 字符的 `[Tool result]: ...`；系统消息被省略。请求没有工具，只有两条消息：一条带内置摘要系统提示词的 system 消息，和一条 user 消息——内容是 `<conversation>` 标签包裹的序列化文本，后接内置摘要提示词，输入带 instructions 时再加 `Additional focus: <instructions>`。它以固定的 thinking level 作为 `reasoning`、对话持久化的供应商 `sessionId`，使用不带 `deferred` 的固定 stream 选项、`cacheRetention: "none"` 与固定的 `maxTokens`。Codex 等供应商在缓存被禁用时可能抑制该身份。恢复时重发相同请求。响应在一次性提交中分类，该提交把其用量加入 `pi.usage`（第 8.6 节）：
  - `stop` 且文本非空、无工具调用：该文本即摘要，按下文放置。
  - `error` 且被 `isRetryableAssistantError()` 接受，同时（在分类时读取的）设置重试策略允许再试：以 `until = now + retryDelayMs(policy, attempt)` 进入 `retry`，并设置状态的 `attempt` 与 `retry`。
  - 其他任何情况（包括导致摘要不完整的 `length` 停止）：以 `model_error` 失败。
- `retry` 睡眠至 `until`，然后以下一次尝试与相同的固定请求回到 `summarize`。

内置提示词采用编码 agent 的结构化检查点（checkpoint）格式。提示词还要求模型在对话开头承接（carry forward）较早的摘要。

**放置（placement）。** 摘要条目为

```ts
{
  kind: "pi.compaction",
  head: firstKept,
  model: [{ role: "user", content: [{ type: "text", text: wrapped }], timestamp: now }],
  data: { reason },
}
```

其中 `wrapped` 是 `"The conversation history before this point was compacted into the following summary:\n\n<summary>\n"`、摘要本身、再加 `"\n</summary>"` 的拼接。放置它的那次提交同时移除任务的状态，并提交任务的 `completed` 结果：

- 阻塞式压缩直接追加条目并以 `{ entryId }` 完成。其 generation 持有 run 并在等待，因此没有其他东西写会话。
- 会话持有的压缩把条目作为一个写入提交准入，请求 ID 为 `compaction:<taskId>`，完全遵循第 6 节：在空闲且收件箱（inbox）为空的会话中，它被立即追加或结算为 `stale`；在空闲但有排队条目的会话中，它排队并运行一次最终边界；在繁忙的会话中，它排队等待下一个边界。它以 `{ submissionId }` 完成，且从不等待排队中的放置；`Harness.submission()` 观察放置情况。

下一个 generation 的准备阶段会发现一个其后没有 `pi.system` 条目的头标记，并写出完整的系统基线（第 7.4 节）。

**取消（cancellation）。** 中止处理器移除任务状态并以 `aborted` 结束；它不写条目。被中止或崩溃打断的尝试没有已提交的响应，因此其用量不计入。手动压缩是其会话的普通工作：`Conversation.abort()` 会中止它。后台压缩会在会话中止中存活，只能通过 `abortTask()` 或 `Conversation.abort(context, { background: true })` 停止。阻塞式压缩随其 generation 一起被中止，且先于 generation 的中止处理器运行（第 5.5 节）。已经排队的摘要是写入提交：会话中止会保留它，`Submission.abort()` 则撤回它。

当阻塞式压缩最终没有 `entryId` 时——因为没有可压缩内容、被拒绝、失败、故障，或被直接中止——阈值触发的 generation 仍会发送其请求，而溢出触发的 generation 以 `model_error` 失败（第 8.3 节）。

## 9. 文档观察与 Chord

### 9.1 文档状态（document state）

Chord 既有的复制状态（replicated-state）层暴露如下源接入（source-adoption）契约：

```ts
interface ReplicatedStateSourceFrame<T> {
  readonly cursor: number;
  readonly value: T;
  readonly ops: readonly Op[];
  readonly context: Context;
}

interface ReplicatedStateSourceAttachment<T> {
  /** Fixed immutable snapshot captured at the atomic attachment boundary. */
  readonly snapshot: { readonly value: T; readonly cursor: number };
  /** Install the sole listener and synchronously drain every buffered frame. */
  activate(listener: (frame: ReplicatedStateSourceFrame<T>) => void): void;
  dispose(): void;
}

interface ReplicatedStateSource<T> {
  /** Atomically capture a snapshot and begin buffering every later commit. */
  attach(): ReplicatedStateSourceAttachment<T>;
}

interface ReplicatedStateSourceOptions {
  readonly onError?: (error: Error) => void;
}

interface AttachedReplicatedState<T> extends ReplicatedState<T> {
  readonly value: T;
  dispose(): void;
}

function replicatedState<T>(
  source: ReplicatedStateSource<T>,
  options?: ReplicatedStateSourceOptions,
): AttachedReplicatedState<T>;

type DocumentState<T extends JsonObject> =
  AttachedReplicatedState<Readonly<T> | null>;

type WatchEnd =
  | { readonly reason: "stopped" | "cancelled" | "session_closed" | "retired" }
  | { readonly reason: "listener_error"; readonly error: Error };

interface WatchHandle<T> {
  /** Acquisition revision before start; latest delivered immutable revision afterward. */
  readonly value: T;
  /** Installs the sole serialized asynchronous listener. */
  start(listener: (value: T, ops: readonly Op[], context: Context) => Promise<void>): void;
  /** Idempotently stops future callbacks and returns this watch's terminal result. */
  stop(): Promise<WatchEnd>;
  /** Settles when the watch terminates; an already-running callback remains caller-owned. */
  readonly closed: Promise<WatchEnd>;
}

type DocumentWatch<T extends JsonObject> = WatchHandle<Readonly<T> | null>;

interface DocumentObserver {
  watchDoc<T extends JsonObject>(token: SessionDocToken<T>, context: Context): Promise<DocumentWatch<T> | undefined>;
  watchDoc<T extends JsonObject>(token: ConversationDocToken<T>, conversationId: ConversationId, context: Context): Promise<DocumentWatch<T> | undefined>;
  watchDoc<T extends JsonObject>(token: TaskDocToken<T>, taskId: TaskId, context: Context): Promise<DocumentWatch<T> | undefined>;
  watchDoc<T extends JsonObject, I extends JsonValue>(token: SessionDocFamilyToken<T, I>, key: string, context: Context): Promise<DocumentWatch<T> | undefined>;
  watchDoc<T extends JsonObject, I extends JsonValue>(token: ConversationDocFamilyToken<T, I>, conversationId: ConversationId, key: string, context: Context): Promise<DocumentWatch<T> | undefined>;
  watchDoc<T extends JsonObject, I extends JsonValue>(token: TaskDocFamilyToken<T, I>, taskId: TaskId, key: string, context: Context): Promise<DocumentWatch<T> | undefined>;
}
```

`documentState()` 在返回之前就把 Pico 的已提交文档流接入（attach）到 Chord。返回的状态已经用精确的、可共享的不可变修订（revision）完成注水（hydration），没有任何变更方法，并且无需额外的 tracker、值拷贝或重新 diff，就能发布之后每个精确的已提交修订与操作批次。释放（dispose）它只注销这一项观察；Pico 仍是文档唯一的变更者。

文档观察（document observation）的状态与观察获取从不创建文档；查找不到返回 `undefined`。成功的获取绑定一个具体的实体（incarnation）。文档退役（retirement）会发布一个 JSON `null` 的根替换（root replacement），并终结该实体的流。若状态仍对外暴露，消费者看到的是 `null`，绝不会是过期状态。之后再创建需要重新获取新的状态或观察。

Session 关闭会在其封存（seal）时终结每个状态：状态保留其最后值，不再接收关闭期间落定的提交所产生的帧（frame）。

每个文档状态分配自己内存中的连续 Chord 投递序列。Pico 不持久化该序列，也不通过 `WatchHandle` 暴露它。状态与观察独立于已加载的 tracker 缓存来保留不可变修订。重新打开会创建新的状态生命周期与注水。

内部实现上，状态接入使用 Chord 同步的原子「快照并注册」边界：快照包含接入之前的每一次提交，之后的每个精确帧都被缓冲直到激活（activation）。这避免了快照与基于更新的、尚未见过的修订的操作配对。

### 9.2 `watchDoc`

任务、钩子与工具可以观察任何其代码持有 token 与 owner/key 的既有文档。在受信任的 Session 代码内部没有额外的子树权限系统。

在 Session 线上，`watchDoc()` 解析一个既有的具体实体，以 O(1) 捕获其当前不可变 tracker 修订，并注册接收之后每个精确的已提交修订与操作批次。文档不存在时返回 `undefined`。在 `start()` 之前，`watch.value` 保持为获取时的修订，后续帧被缓冲。

```ts
const watch = await api.watchDoc(JobOutputDoc, producerTaskId, context);
if (watch === undefined) return;
try {
  await initializeConsumer(watch.value, context);
  watch.start(async (value, ops, deliveryContext) => {
    await consume(value, ops, deliveryContext);
  });
} catch (error) {
  await watch.stop();
  throw error;
}
```

`start()` 安装唯一的监听器并安排投递；它从不内联（inline）调用用户代码。每个回调收到精确的不可变已提交值，以及产生它的精确操作批次。在调用前一刻，`watch.value` 前进到该值。观察会等待监听器完成后才开始下一个回调，但 Session 提交从不等待回调的落定。

一个观察至多保留 100 个待投递（pending）的已提交帧（不含正在投递的那一帧）。第 101 帧到来时，会用一个自包含的根替换 `[["r", newestValue]]` 取代完整的未投递后缀，使用最新的精确不可变修订与该次提交的 Context。之后的精确帧正常跟随该替换。再次溢出则再次替换待投递后缀。没有序列化字节测量、值拷贝、操作重放或重新 diff。这是收敛式观察（convergent observation），不是审计流；需要每个中间状态的消费者必须另行持久化这些事实。

在受信任的不可变性契约下，`watch.value` 与所有先前返回的修订永远保持稳定。消费者不得变更它们或其保留的后代。所选提交 Context 的值被保留，不继承生产者的取消状态。回调拥有自己的异步工作。

观察始终绑定其原始实体。退役会把精确的终态帧 `[["r", null]]` 排入队列，或将其折叠进值为 `null` 的溢出替换。该回调落定后，观察以 `retired` 关闭，绝不跟随替代实体。

`stop()` 幂等。它同步注销、丢弃待投递帧、阻止下一个回调启动，并返回共同的终态 promise。已在运行的回调既不被中止也不被等待（join），仍归调用方所有。获取时的 `Context` 决定观察的生命周期。获取期间被取消则在拒绝前完成清理；之后的取消与 Session 关闭同样停止后续投递。监听器失败会丢弃待处理工作，只关闭该观察，原因记为 `listener_error`。第一个终结原因生效，所有迟到的 rejection 都会被妥善观测。

### 9.3 会话视图（conversation view）

公开视图是会话活跃转录及其内置文档的一个固定结构挂载（mount）：

```ts
type ConversationView = {
  readonly conversation: ConversationRecord;
  /** Raw active entries, as `ContextView.entries` (section 2.1): the head marker, then the non-head entries from its head. */
  readonly entries: readonly EntryRecord[];
  /** `pi.agent`, `pi.live`, `pi.inbox`, `pi.provider`, and `pi.usage`, keyed by kind; absent documents are absent. */
  readonly docs: Readonly<Record<string, JsonObject>>;
};
```

这些 kind 及其字段属于公开协议。第三方文档通过它们自己的 Chord 服务暴露，不会被挂载。

Harness 每个会话至多保留一个挂载。第一次 `viewState()`、`watch()` 或事件接入时，在 Session 线上从已提交的活跃转录与文档构建其修订；最后一个观察者脱离时，挂载被丢弃。挂载像 `watchDoc()` 一样，从 Session 的 `subscribeCommits()` 发布（publication）推导每个后续修订：每个发布都已持久化，因此视图只展示已提交状态。一次触及该会话的发布产生一个 Chord 批次：

```text
document op ["s", ["generation", "message"], value]
-> view op ["s", ["docs", "pi.live", "generation", "message"], value]
```

追加一个无头的条目，是在 `entries` 末尾做拼接（splice）。追加头标记 `H` 则使条目变为 `H` 加上当前在 `H.head` 处或之后的非头条目：保留的条目留下，拼接移除其余条目并把 `H` 插到最前。每个被保留的条目都已在挂载中，因为 Harness 写入者从不会指向当前区间之前的头：重置与交接以自身为头，压缩摘要以当前区间中被保留的条目为目标，而指向更早的头写入是过期（stale）的（第 6 节）。指向更早的裸头写入只显示已挂载的条目（第 12 节）。文档创建与退役会设置和删除 `docs` 键。经由 `parent.at` 的父条目是不可变的，因此子挂载只跟随自己的会话。未触及任何已挂载内容的发布不产生修订；冗余的非空批次仍是真实的发布。在受信任的不可变性契约下，已挂载的文档修订在结构上共享。挂载不做任何语义投影，也不拥有任何持久化。

`Conversation.viewState()` 把挂载暴露为可释放的只读 Chord 状态。`Conversation.watch()` 通过第 9.2 节的序列化精确帧观察暴露同一挂载，具有有界的待投递帧与整值溢出替换。

### 9.4 Agent 事件（实验性）

`watchEvents(harness, conversationId, context): Promise<AgentEventStream>` 从包根导出，是一个实验性适配器，把一个会话的已提交发布翻译成形似编码 agent `AgentSessionEvent` 的 agent 事件。它不拥有 tracker 或持久化，恰好覆盖一个会话（不含其拥有的子树），且只在使事件为真的那次提交之后才发出事件。其协议可能随时变更，恕不另行通知。

```ts
type AgentEvent =
  | {
      type: "snapshot";
      entries: readonly EntryRecord[];
      run?: { inputs: readonly SubmissionId[] };
      /** Current generation attempt: its in-flight partial, retry backoff, or deferred poll. */
      generation?: { attempt: number; message?: AssistantMessage; retry?: { at: number; error: string }; deferred?: { pollAt: number } };
      tools: readonly ToolSlot[];
      /** `pi.live.compactions` (section 8.2). */
      compactions: readonly CompactionStatus[];
      inbox: readonly { id: SubmissionId; mode: InboxItem["mode"] }[];
      /** `pi.agent`; `{}` when absent. */
      agent: AgentState;
      usage: UsageState;
    }
  | { type: "run_start"; inputs: readonly SubmissionId[] }
  | { type: "run_end"; inputs: readonly SubmissionId[] }
  | { type: "turn_start" }
  | { type: "turn_end" }
  | { type: "message_start"; message: Message }
  | { type: "message_update"; usage: Usage; changes: readonly MessageChange[] }
  | { type: "message_end"; entry: EntryRecord }
  | { type: "tool_execution_start"; toolCallId: string; toolName: string; args: JsonObject }
  | {
      type: "tool_execution_update";
      toolCallId: string;
      toolName: string;
      /** A front trim and then an append of the retained window, or its replacement. */
      output?: { trimStart?: number; append?: string } | { set: string };
      details?: JsonValue;
      diagnostics?: readonly ToolDiagnostic[];
    }
  /** `entry` is absent when the tool task faulted or was orphaned. */
  | { type: "tool_execution_end"; toolCallId: string; toolName: string; entry?: EntryRecord }
  | { type: "inbox_update"; items: readonly { id: SubmissionId; mode: InboxItem["mode"] }[] }
  | { type: "submission"; record: SubmissionRecord }
  | { type: "auto_retry_start"; attempt: number; at: number; errorMessage: string }
  | { type: "auto_retry_end"; attempt: number }
  | { type: "deferred_poll"; pollAt: number }
  | { type: "entry_appended"; entry: EntryRecord }
  | { type: "agent_changed"; agent: AgentState }
  | { type: "usage_changed"; usage: UsageState }
  | { type: "task_failed"; taskId: TaskId; kind: string; message: string }
  | { type: "compaction_start"; taskId: TaskId; reason: CompactionReason; blocking: boolean }
  /** The task's receipt tells whether it produced a summary; the summary entry has its own events. */
  | { type: "compaction_end"; taskId: TaskId; reason: CompactionReason };

/** One change to the in-flight assistant message, relative to that message. */
type MessageChange =
  | { type: "text_start" | "thinking_start" | "toolcall_start"; contentIndex: number; block: AssistantMessage["content"][number] }
  | { type: "text_delta" | "thinking_delta"; contentIndex: number; delta: string }
  | { type: "toolcall_delta"; contentIndex: number; path: readonly (string | number)[]; delta: string }
  | { type: "block"; contentIndex: number; block: AssistantMessage["content"][number] }
  | { type: "message"; message: AssistantMessage };

interface AgentEventStream {
  /** The `snapshot` event at attachment. */
  readonly snapshot: Extract<AgentEvent, { type: "snapshot" }>;
  start(listener: (events: readonly AgentEvent[], context: Context) => Promise<void>): void;
  stop(): Promise<WatchEnd>;
  readonly closed: Promise<WatchEnd>;
}
```

每个事件都相对于 `snapshot` 及其之前的事件，而非 Pico 的文档布局。`snapshot` 替换消费者持有的一切；其他事件都叠加在它之上。接入时在 Session 线上原子地捕获快照（snapshot）并注册后续发布。

事件源自已提交的变更：

- `run_start`/`run_end`：`pi.live.run` 出现、被移除，或被首个输入不同的后继 run 替换。加入当前 run 的 steer 与其任务之间的交接不是 run 事件。输入的结果以 `submission` 事件呈现。
- `turn_start`：一个 `pi.generation` 任务被创建。`turn_end`：generation 的结果被提交——在其挂起为 `completing` 或达到终态时，以先到者为准，因此在挂起时创建的后继在其之后才开始。
- `message_start`：一次尝试的首个已提交 partial；对于没有已提交 partial 的消息条目，则是条目本身；凡带 `model` 消息的条目其后都有 `message_end`。generation 只在 partial 有内容后才提交它，而每个清除 partial 的内置路径都会追加其条目，因此每条开始的消息都以自己的条目收尾。没有消息的条目是 `entry_appended`。
- `message_update`：对已提交 partial 的 Chord 操作经翻译而成：向 `content` 的插入启动块（block），向块的 `text` 或 `thinking` 追加是一个 delta，向工具调用 `arguments` 内字符串的追加是路径相对于 `arguments` 的 `toolcall_delta`，块内的其他任何变更发送那个 `block`（其中已包含该批次对它的后续变更），`content` 的其他任何变更发送整个 `message`。每次更新都携带 partial 当前的 `usage`，与编码 agent 的 JSON 模式一样；仅有 `usage` 变化时不发送任何变更。只有 delta 在传输，因此节流的 partial 不会在线路上造成写放大。
- `tool_execution_start`：槽位变为 `running`；`args` 来自同一次提交中工具任务的意图检查点。未经运行就变为 `done` 的槽位（调用未被提供、参数无效、被阻塞、意图之前故障）只得到 `tool_execution_end`。`tool_execution_update`：槽位保留窗口的输出追加、前端裁剪与整体替换，以及变化时的当前 `details` 与 `diagnostics`；被移除时（如安全重放重启工具时）发送 `null` 与 `[]`。`tool_execution_end`：槽位变为 `done`，带上携带 diagnostics 的 `pi.tool-result` 条目，或在故障或孤儿之后不带条目。因 run 结束而消失的未完成槽位，以同一次提交中追加的结果条目收尾（如被中止轮次中未启动的调用那样），位置紧贴其 `message_start` 之前；或没有条目地收尾。
- `inbox_update`、`agent_changed`、`usage_changed`：对应文档发生了变更；已退役的文档按其初始值读取，与快照一致。registry 安装与设置变更不产生提交，也不发出任何事件；显示已解析工具或已解析模型的 UI 应通过 `Conversation.agent()` 重新解析。
- `auto_retry_start`/`auto_retry_end`、`deferred_poll`：`pi.live.generation` 获得或失去 `retry`，或获得 `deferred` 或移动其 `pollAt`。
- `task_failed`：会话的某个任务结算为 `faulted` 或 `orphaned`。
- `compaction_start`/`compaction_end`：`pi.live.compactions` 中出现或消失一个状态。重试退避只体现在快照的 `compactions` 里。排队中的摘要稍后放置时，带有自己的 `message_start`/`message_end` 与 `submission` 事件。

一次提交产生一个批次，顺序如下：先是 `tool_execution_start`、首个 partial 的 `message_start`、`message_update`、`tool_execution_update` 与 retry/deferred 事件；然后按追加顺序排列各条目及其 `message_start`/`message_end` 或 `entry_appended`，其中工具结果的 `tool_execution_end` 紧贴其 `message_start` 之前，与编码 agent 一致；然后是没有条目收尾的工具的 `tool_execution_end`；然后是 `compaction_end`、`task_failed`、`turn_end`、`run_end`；然后是按 ID 顺序的 `submission` 事件；然后是 `inbox_update`、`agent_changed` 与 `usage_changed`；最后是 `compaction_start`、`run_start` 与 `turn_start`。流至多缓冲 100 个未投递批次；再来一批时，用最新已提交状态的一个 `snapshot` 取代所有未投递批次。因此流是收敛的，但不承诺每个中间状态；`Submission.wait()` 报告精确结果。重连的消费者重新接入并从其 `snapshot` 开始；没有任何重放。传输层背压与断连策略属于消费者。

打印模式等待自己的输入 `Submission` 并打印回答。TUI 渲染 `ConversationView`；事件可以驱动瞬态动画。

### 9.5 任务图视图（task graph view）

任务图视图（task graph view）把 Session 的每个活跃任务呈现为一个结构化值，供 UI 与调试使用：什么在运行、什么在等待什么、每个任务拥有哪些会话。它之于 Session 的任务，如同会话视图（第 9.3 节）之于一个会话。

```ts
type TaskGraphState =
  | { readonly status: "pending" | "running"; readonly phase: string }
  | {
      readonly status: "waiting";
      readonly phase: string;
      readonly on: readonly TaskId[];
      readonly policy: JoinPolicy;
    }
  /** Outcome held until its ordinary owned work drains (section 5.5). */
  | { readonly status: "completing"; readonly outcome: TaskOutcome<JsonValue>["status"] };

type TaskGraphNode = {
  readonly id: TaskId;
  readonly kind: string;
  readonly conversationId: ConversationId;
  /** Owner task; absent for a conversation-owned task. */
  readonly owner?: TaskId;
  readonly background: boolean;
  readonly abortRequested: boolean;
  readonly state: TaskGraphState;
  /** Conversations this task owns, in ID order. */
  readonly conversations: readonly ConversationId[];
};

type TaskGraph = {
  /** Every live task, keyed by its decimal ID. */
  readonly tasks: Readonly<Record<string, TaskGraphNode>>;
};

type TaskGraphWatch = WatchHandle<TaskGraph>;

interface Harness {
  taskGraph(context: Context): Promise<AttachedReplicatedState<TaskGraph>>;
  watchTaskGraph(context: Context): Promise<TaskGraphWatch>;
}
```

节点持有已提交的任务记录，但不包含其输入、检查点载荷、结果载荷与备忘（memos）：`phase` 是检查点的阶段，`on` 与 `policy` 是存储的等待，`outcome` 是挂起结果的状态。`running` 是持久化状态：打开状态的变更会让 `running` 任务回到 `pending`（第 5.4 节），因此它们在调度器再次保留（reserve）之前显示为 `pending`，而 `waiting` 与 `completing` 任务保持其状态。某个 pending 任务是否被阻塞、`on` 中的哪些任务仍存活，取决于 registry 与图的其他部分；`inspect()` 推导它们。节点从创建任务的提交开始存在，直到使任务终态的提交为止。所有权边（owner edge）不可变，因此节点存活期间其 `conversations` 只增不减。

图只持有活跃任务。拥有者任务已终态的会话（例如锚点任务结束后的后台子 agent 会话）没有列出它的节点；那里后来的任务就是该会话的顶层节点。要把它置于父级之下的 UI，从 `ConversationRecord.owner` 读取会话的所有权边，`ConversationView.conversation` 也携带该字段。

Harness 至多保留一个图挂载。第一次 `taskGraph()` 或 `watchTaskGraph()` 时，在 Session 线上从已提交的活跃任务及其拥有的会话（每个活跃任务做一次所有权扫描）构建其修订，构建期间持有该线；最后一个观察者脱离时，挂载被丢弃。它像会话视图一样从 `subscribeCommits()` 发布推进：改变节点的发布产生一个 Chord 批次，设置或删除 `tasks[id]`，或设置节点的 `conversations`。不改变任何节点的发布不产生修订。任务与会话记录是不可变值；节点与它们不共享任何东西。

`taskGraph()` 把挂载返回为可释放的只读 Chord 状态。`watchTaskGraph()` 通过第 9.2 节的序列化精确帧观察返回它。两者都是只读：都不启用调度。关闭像其他所有状态与观察一样，在其封存时终结它们（第 2.2 节）。

```ts
const graph = await harness.taskGraph(context);
graph.subscribe((value) => {
  for (const node of Object.values(value.tasks)) {
    const where = node.owner === undefined ? `conversation ${node.conversationId}` : `task ${node.owner}`;
    render(`${node.id} ${node.kind} ${node.state.status} under ${where}`);
  }
});
```
