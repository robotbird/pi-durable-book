# @earendil-works/pi-durable

> **实验性（Experimental）。** API 会在版本之间随时变更，恕不另行通知。

这是一个持久化（durable）的智能体运行框架（harness）。对话（conversation）、模型轮次、工具调用以及你自己的状态，都会先提交（commit）到存储（storage），然后才会对外呈现。如果进程在某个轮次中途消亡，重新打开存储就能从中断处接着运行。

它构建在 `@earendil-works/pi-ai` 之上以访问模型，并使用 `@earendil-works/chord` 管理文档（document）状态。

## 快速上手

```typescript
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { openaiProvider } from "@earendil-works/pi-ai/providers/openai";
import { AssistantEntry, createRegistry, Harness, MemoryStorage } from "@earendil-works/pi-durable";

const context = BACKGROUND_CONTEXT;

const models = createModels();
models.setProvider(openaiProvider()); // reads OPENAI_API_KEY

const harness = await Harness.open(new MemoryStorage(), { models, registry: createRegistry() }, context);
const root = await harness.root(context, { agent: { model: { provider: "openai", modelId: "gpt-6-sol" } } });

const submission = await root.submit({ type: "input", content: "What is the capital of France?" }, context);
const settled = await submission.wait(context);
if (settled.status === "done" && settled.type === "input") {
	const answer = await root.commit((tx) => tx.entry(AssistantEntry, settled.answer), context);
	console.log(answer?.model?.[0]);
}
await harness.close(context);
```

上面发生了什么：

- `Harness.open()` 在一个存储后端之上打开会话（Session）。`MemoryStorage` 把一切保存在内存里。
- `root()` 返回根对话，首次使用时会按给定的智能体选项创建它。对话是一份由不可变条目（entry）组成的记录（transcript）。
- `submit()` 以持久化的方式受理你的输入，并返回一个提交项（Submission）。内置的生成任务会调用模型并追加回答。
- `wait()` 在输入得到回答（`done`）或失败（`unanswered`，附带原因）后完成。

每个异步调用都接收一个 Chord `Context`，取消信号与当前的 `TelemetrySpan`（遥测 span）都由它携带。`BACKGROUND_CONTEXT` 永不取消，并使用 NOOP span。根适配器（root adapter）由运行框架持有；适配器从不存入 `Context`。取消一次等待只会取消这次等待本身，绝不会取消正在进行的工作。

`HarnessOptions.identity` 设置模型请求如何向供应商表明应用的身份（一个 pi-ai `ClientIdentity`），它在 `DEFAULT_HARNESS_IDENTITY`（`{ attribution: PI_ATTRIBUTION }`：OpenRouter、NVIDIA NIM 与 OpenCode 的 attribution 头会署名 pi）之上合并。它作用于生成、压缩、钩子与工具，覆盖宿主 `Models` 创建时所采用的身份。请传入你应用的署名，例如 `{ attribution: { name: "my-app", url: "https://my-app.example" } }`，或传 `{ attribution: null }` 表示不发送任何署名。

`HarnessOptions.telemetry` 接收一个由宿主持有的 `TelemetryContext`（来自 `@earendil-works/pi-telemetry`），可带可选的 `propagation` 与 `metrics` 能力；不传则等价于空操作。从包根导出的 `DURABLE_TELEMETRY_SCHEMA` 记录了它的类型化 span、事件与指标。属性中只含 ID 与控制元数据，绝不含消息、参数或结果；ID 指向记录（transcript）。

- `pi.durable.submit` 覆盖公开的 submit 调用及其提交。每个输入都会开启一条新的根 trace，并附带一个指向其调用方当前 span 的链接；写入则是其调用方的子 span。重复的 `requestId` 会保留原有的提交项与载体（carrier）。内部受理——例如压缩写入——在其阶段 span 上发出事件，没有 submit span。
- `pi.durable.phase` 覆盖每个任务的一次运行或中止阶段，包括其决策提交；绝不涵盖下一个阶段、一次持久化等待或一次重启。其属性标识任务、阶段、尝试次数（若存在）、`resumed` 与结果。工具阶段还会标识工具与调用。嵌套任务与后台压缩继承创建它们的阶段；模型请求会接收到该阶段上下文。钩子不添加任何 span。
- 失败阶段的结果会以一个固定类别（`task_faulted`、`task_failed` 或 `task_orphaned`）设置错误状态，并附带该结果的诊断消息，截断至 500 字符（即孤儿任务的原因）。诊断可能包含调用方的内容；不会记录错误细节或异常名称。`aborted` 结果保持状态 `ok`，被关闭或取消中断时也是如此。
- 每份 `onReport` 报告还会在其当前 span 上发出一个 `pi.durable.report` 事件。没有 span 时，NOOP span 会丢弃该事件，也不会创建根报告 span。只记录 `type`、可选的固定 `reason`、`extension` 与 `task.id`；不包含错误负载。`pi.durable.reports` 只按 `type` 统计所有报告，包括没有 span 的那些。时钟故障的报告不带阶段上下文。`onReport` 回调本身保持不变。
- 已提交的条目与已落定的提交项会发出 `pi.durable.entry` 与 `pi.durable.submission`。已提交的运行中阶段变化发出 `pi.durable.checkpoint`；凭存储结果得到应答的嵌套调用发出 `pi.durable.replay`。
- 传播（propagation）把可选的不透明 `trace` 载体存入提交项与任务的 JSON，无需存储迁移。阶段 span 会提取其任务所存储的载体；缺失或未知时，则从适配器根开始。`TaskOptions.trace` 缺省时继承创建者的载体，也可显式传入覆盖载体，或用 `"root"` 从适配器根开始且不存储载体。一次运行为多个排队输入启动时，取第一个输入的 trace；其首次调用的阶段 span 通过不可变的任务 `links` 链接到其余输入。转向留在运行中的 trace 内，其 submit span 链接到该运行存储的载体。重新打开的任务，其首次调用在同一条 trace 中带有 `resumed: true`。
- 指标记录 `pi.durable.phase.duration`（毫秒；任务、阶段、结果）与 `pi.durable.tasks.active`（存活任务；任务名），不含记录 ID。关闭运行框架会释放其活跃计数。

## 核心概念

- **运行框架（Harness）**：一个已打开的存储，加上在其上运行智能体的整套机制。所有变更都经过同一条原子提交流水线；任何内容在其提交被存储之前，都不会对外呈现。
- **对话（Conversation）**：一份记录（transcript）。`root()` 在首次使用时创建根对话；你还可以创建更多对话，并对它们分叉（fork）。`Conversation` 句柄本身不持有状态；比较句柄请用 `id`。
- **条目（Entry）**：记录中的一条不可变条目，例如用户消息（`pi.user`）、模型响应（`pi.assistant`）、工具结果（`pi.tool-result`）、系统提示变更（`pi.system`）、重置（`pi.reset`），或你自定义的类型。模型只能看到最近一次重置之后的条目。
- **提交（Commit）**：一次原子写入。`conversation.commit((tx) => ...)` 可以在一次调用中同时追加条目、编辑文档并创建任务；要么全部写入存储，要么什么都不写。
- **文档（Document）**：与记录存放在一起、可在提交中修改的类型化 JSON 状态。内置文档保存每个对话的智能体选项（`pi.agent`）、面向供应商的会话身份（`pi.provider`）、正在运行的生成与工具（`pi.live`）、排队的提交项（`pi.inbox`）以及开销（`pi.usage`）。
- **任务（Task）**：一种持久化状态机，每一步都会保存检查点（checkpoint），进程重启后从上一个检查点继续。每个任务都有归属者（owner）：它所属的对话，或另一个任务。运行框架把「回答输入」作为内置任务来执行：`pi.generation` 调用模型，持有其工具调用对应的 `pi.tool` 任务，等待它们完成后，把运行交给下一个生成任务。
- **提交项（Submission）**：你递交给对话的内容，可以是用户输入，也可以是要写入的条目；你可以等待它完成。
- **轮次与运行**：轮次（turn）是一次模型响应及其工具调用；运行（run）是从某个输入到其最终答案之间的所有轮次。运行进行期间，对话处于忙碌状态。
- **扩展（Extension）**：一组具名的捆绑内容，包含工具、系统提示段落（section）、钩子（hook）、包装器（wrapper）与任务。
- **注册表（Registry）**：本进程安装的扩展集合。它可以在运行框架运行期间变化；新工作会使用新状态。
- **智能体（Agent）**：对话运行所依赖的一组设定：模型、思考级别（thinking level）、所选扩展、工具、指令（instructions）与工作目录。它以名字的形式按对话存储在 `pi.agent` 中，每次使用时对照注册表解析。

一次被回答的输入，对应的条目与任务：

```text
submit(input) → pi.user
  pi.generation → pi.system (only if the prompt or tools changed), pi.assistant (tool calls)
    pi.tool × n → pi.tool-result × n   (owned by the generation, which waits for them)
  pi.generation → pi.assistant (answer) → submission done
```

## 持久化与恢复

使用 SQLite 或 JSONL 存储，可以让对话在重启后依然保留：

```typescript
import { openNodeSqliteStorage } from "@earendil-works/pi-durable/storage/sqlite/node";

const harness = await Harness.open(await openNodeSqliteStorage("./session.sqlite"), { models, registry }, context);
const root = await harness.root(context); // the same root as last time
harness.resume(); // continue any run the last process left unfinished
```

因崩溃或关闭而中断的工作会保持待处理状态。`resume()` 启动任务调度器；提交或等待操作同样会启动它。每个对话都在 `pi.provider` 中持久化了自己的 UUIDv7，并作为 `sessionId` 转发给 pi-ai，用于供应商侧的提示缓存（prompt cache）与会话亲和（session affinity）。重新打开、重试、重置、压缩与更换模型都不会改变它；子对话或分叉则会获得全新的身份。没有该文档的旧对话会在首次生成或压缩请求之前创建并持久化一个。

携带相同 `requestId` 重试的提交会返回已有的提交项，而不会重复提交：

```typescript
const submission = await root.submit({ type: "input", content: "Hello", requestId: "greeting-1" }, context);
// After a restart: the same request ID finds the same submission.
const again = await root.submit({ type: "input", content: "Hello", requestId: "greeting-1" }, context);
// again.id === submission.id
```

`harness.submission(id)` 按 ID 重新获取一个提交项，例如在重启之后继续等待它。

### 睡眠与唤醒

任务通过结束当前阶段、进入睡眠（sleep）来等待一段时间。这份睡眠会被存储，因此任务在此期间不持有调用（invocation），能够挺过重启，并在运行框架的时钟到达 `until` 时从检查点恢复：

```typescript
const Reminder = defineTask<{ text: string; at: number }, { phase: "wait" } | { phase: "deliver" }, null>({
	name: "app.reminder",
	version: 1,
	initial: () => ({ phase: "wait" }),
	phases: {
		// Resolves once the sleep is stored; the phase ends there.
		wait: (task, runtime, context) => runtime.sleepUntil(task.input.at, { phase: "deliver" }, context),
		deliver: async (task, runtime, context) => {
			await notify(task.input.text);
			await runtime.commit(() => ({ status: "terminal", outcome: { status: "completed", result: null } }), context);
		},
	},
	abort: (_task, runtime, context) =>
		runtime.commit(() => ({ status: "terminal", outcome: { status: "aborted" } }), context),
});
```

阶段中间不存在睡眠：重启之后，阶段会从头重新运行，因此等待之后的工作要放进下一个阶段，它所需的东西则放进检查点。从 `runtime.commit()` 返回 `{ status: "sleeping", until, checkpoint }` 是同一份睡眠，它与其他写入一起提交。内置任务的重试退避（retry backoff）与延迟响应轮询（deferred-response poll）也以同样的方式睡眠。

会话（Session）、调度器及其任务的定时器都经由 `setTimer`（默认 `setTimeout`），它们的时间读数则经由 `now`（默认 `Date.now`）；把两者都传入，就能让运行框架跑在一个假时钟（fake clock）上。Node.js 环境、文件监视器（file watcher）与图片 worker 保留各自独立的定时器。睡眠的截止时间按 `now` 存储，因此打开同一个存储的每个进程都必须使用同一个时钟。调度运行期间，定时器会在睡眠任务到期时恢复它们，并在此期间让 Node.js 进程保持存活。

进程可能被逐出（evict）的宿主——例如 Cloudflare Durable Object——要由它自己来唤醒运行框架。传入 `onWake` 后，运行框架不再为睡眠布设定时器；每当 `harness.wake()` 的结果发生变化，它就把变化告知宿主：只要有任务现在就能运行或正在运行，`active` 即为真；`at` 则是最早的一次睡眠。宿主让自己的闹钟（alarm）保持布设状态，并在其触发时调用 `resume()`：

```typescript
export class Session extends DurableObject<Env> {
	#harness!: Harness;

	constructor(ctx: DurableObjectState, env: Env) {
		super(ctx, env);
		void ctx.blockConcurrencyWhile(async () => {
			// A fallback before anything can throw: an object whose open or recovery fails is started again.
			const fallback = Date.now() + 60_000;
			const current = await ctx.storage.getAlarm();
			if (current === null || current > fallback) await ctx.storage.setAlarm(fallback);
			const storage = await openDurableObjectSqliteStorage(ctx.storage);
			const onWake = (wake: Wake) =>
				// A failed alarm write resets the object; it arms again when it next starts.
				void this.#arm(wake).catch(() => ctx.abort("Alarm write failed"));
			this.#harness = await Harness.open(storage, { models, registry, onWake }, context);
			// Armed before `resume()` runs anything, as for any call that can start work.
			await this.#arm(this.#harness.wake());
			this.#harness.resume(); // work a lost instance left, and due sleeps
		});
	}

	override async alarm(): Promise<void> {
		await this.#arm({ ...this.#harness.wake(), active: true });
		this.#harness.resume(); // due sleeps and work a lost instance left
	}

	// Arm before any call that can start work (submit, compact, abortTask, abort, a registry change): `onWake` runs
	// after the commit. An early alarm is harmless, a missing one strands the work.
	async submit(conversation: Conversation, input: string, requestId: string): Promise<void> {
		await this.#arm({ ...this.#harness.wake(), active: true });
		await conversation.submit({ type: "input", content: input, requestId }, context);
	}

	async #arm(wake: Wake): Promise<void> {
		// A recovery heartbeat while work runs, never later than the earliest sleep.
		const heartbeat = wake.active ? Date.now() + 60_000 : undefined;
		const at = heartbeat === undefined || wake.at === undefined ? (heartbeat ?? wake.at) : Math.min(heartbeat, wake.at);
		if (at === undefined) await this.ctx.storage.deleteAlarm();
		else await this.ctx.storage.setAlarm(at);
	}
}
```

默认的 `setTimer` 会拒绝那些在 Workers 里只为释放内存而设的定时器，因此不会有挂起的定时器妨碍对象休眠（hibernate）或被逐出；内存随后会在之后的提交中被释放。

### 失败与恢复

**崩溃循环（crash loop）。** 若一项工作在抵达下一个检查点之前就确定性地耗尽内存或 CPU、令进程崩溃，那么它本来会被重新运行、然后再次崩溃，如此永远循环。打开（open）会为每个因崩溃、逐出或重置而被打断的任务计数；关闭不计入，任务提交一个新状态也会让计数归零。计数达到 `settings.restartLimit`（默认 5；`Infinity` 表示永不驻停）时，任务被驻停（parked）：`inspect()` 与任务图都把它显示为因 `restart_limit` 而被阻塞，`wake()` 不把它算作活跃，`onReport` 以 `task_parked` 收到它一次。进程死亡时正在运行的每个任务都会被计数，因此请把被驻停的任务展示出来，并提供 `harness.retryTask(id)`——它会让任务再次运行。`abortTask()` 仍会运行任务的中止处理器；中止处理器被打断达到同样次数时，任务以 `faulted` 告终。

**报告。** `onReport(error, info)` 在 `info.type` 中说明发生了什么：`session_failed` 对应使运行框架失败的那个错误（存储错误，通常是平台重置）；`task_faulted`、`task_parked`、`migration_failed`、`task_outdated` 或 `task_error` 对应某个任务，附带 `info.task`（其 `id`、`kind` 与 `conversationId`），安装它的扩展则放在 `info.extension`；`extension_error` 对应钩子、段落、包装器与工具，附带该扩展的名字；`host_error` 对应某个宿主回调，名字在 `info.callback`；还有 `listener_error`。宿主可以把同一类别的 `task_faulted` 报告接进自己的熔断器（breaker）。

**运行失败后的排队输入。** 因模型错误而失败的运行，会让排在其后的输入留在队列里等待，直到下一个输入到来。`settings.afterFailedRun` 可以改变这一行为：`continue` 用它们启动下一次运行，如同回答之后那样；`withdraw` 则把它们落定为 `unanswered`，原因为 `run_failed`。

**被阻塞的任务。** 因定义缺失或无法迁移而被阻塞的任务，也会在任务图中显示其原因；一次解除阻塞的注册表变更会让 `onWake` 把会话报告为活跃，宿主因此无需轮询它们。

## 扩展

运行框架运行的代码中，除内置任务之外，都以具名扩展的形式提供，安装在你的进程自己持有的注册表里：

```typescript
import { createRegistry, defineExtension, defineTool, hook, section, ToolTask } from "@earendil-works/pi-durable";
import { CodingTools } from "@earendil-works/pi-durable/tools";

const Coding = defineExtension({
	name: "coding",
	sections: [section("preamble", () => "You are a concise coding assistant.", { tag: false })],
	hooks: [hook(ToolTask, { beforeTool: (call) => (isDangerous(call) ? { block: "Needs approval" } : undefined) })],
});

const registry = createRegistry();
registry.install(CodingTools);
registry.install(Coding);
```

一个扩展可以携带 `tools`、`sections`、`hooks`、`wraps`（按名字装饰某个工具或段落的装饰器）与 `tasks`。默认情况下，每个对话都会按安装顺序选中所有已安装的扩展。注册表中的内容不会被存储；对话存储的只是扩展的名字。

## 工具

`@earendil-works/pi-durable/tools` 提供 `read`、`write`、`edit` 与 `bash` 四个工具，以及囊括四者的 `CodingTools` 扩展。它们只通过调用所处的环境（environment）接触文件与进程（见下文「环境」一节）。

`read` 会把图片文件作为一个图片块（image block）返回，以编程方式调用它的程序会拿到一个 `ImageContent`。上限取模型的 `inputLimits.images.resize`，默认 2000x2000 像素、base64 编码后 4.5 MB。未配置图片处理器（image processor）时，`read` 会原样发送尺寸在上限之内（尺寸直接从文件头读取）的 PNG、JPEG、GIF 与 WebP 文件，不做解码；超限文件与其他格式一律拒绝。配置了处理器时，它会对每张图片解码、按 EXIF 朝向摆正、把 BMP 转为 PNG，并缩放到上限以内。基于 Photon 的处理器运行在 WebAssembly 上，只有在你导入它时才会加载：

```typescript
import { createNodePhotonImages } from "@earendil-works/pi-durable/images/node"; // or /images/cloudflare, or createPhotonImages(wasm) from /images
import { createCodingTools } from "@earendil-works/pi-durable/tools";

registry.install(createCodingTools({ images: await createNodePhotonImages() }));
```

不支持图片输入的模型会看到占位符（placeholder）而不是图片，`read` 也会在诊断（diagnostic）中说明这一点。`/images/node` 在工作线程（worker thread）里准备图片，因此一张大照片（一两秒的工作量）绝不会阻塞事件循环；worker 连续 30 秒没有图片任务就会退出，释放 Photon 的 WebAssembly 内存（`createNodePhotonImages({ worker: false, idleMs })`）。在其他环境里，`createPhotonImages()` 与 `/images/cloudflare` 在调用线程上工作，解码占用的 WebAssembly 内存相当于图片的完整尺寸，且之后不会归还；在 Cloudflare Workers 这类内存受限的宿主上，如果图片都不大，干脆不要配置处理器。

用 TypeBox schema 定义自己的工具。`defineTool()` 依据 `parameters` 推导 `args` 的类型，运行框架会在 `execute()` 之前校验参数。`api.output()` 以流式输出运行中的输出；当 `execute()` 未返回 `output` 时，这些输出就成为结果：

```typescript
import { Type } from "@earendil-works/pi-ai";

const count = defineTool({
	name: "count",
	description: "Count from 1 to n",
	parameters: Type.Object({ n: Type.Number() }),
	execute: async (args, api) => {
		for (let i = 1; i <= args.n; i++) api.output(`${i}\n`);
		return {};
	},
});
registry.install(defineExtension({ name: "count", tools: [count] }));
```

每次工具调用都作为独立的持久化任务运行，其意图会在 `execute()` 执行前先行提交。如果进程在调用中途消亡，只有声明为 `replay: "safe"` 的工具才会在重新打开后重跑；否则模型会收到 `interrupted` 错误结果，附带截至中断前已提交的输出。从 `execute()` 抛出异常会向模型返回错误结果。结果还可以返回 `usage`，它会计入对话的用量。结果也可以返回 `control: { terminate: true }`：当一轮的所有结果都提出这一要求时，运行就此结束，不再发起下一次模型请求。

结果有三个通道：给模型的 `output`、给调用工具的程序的结构化输出（structured output）`structuredOutput`（见下文「工具调用工具」一节），以及给界面的 `details`。声明了 `structuredOutputSchema` 的工具会返回与之匹配的 `structuredOutput`，由运行框架校验。程序调用未声明 schema 的工具时，拿到的是该工具有界的输出（bounded output）：单个文本项转为字符串，单个图片转为它的 `ImageContent`，空转为 `""`，其余转为内容列表，错误结果亦然。`structuredOutput` 始终是工具自己给出的值：声明了 schema 的工具，其错误结果仍保留它返回的值；未声明 schema 的工具，其错误文本则进入 `tool_error` 诊断，抛出异常的错误消息也是如此。记录中只存储 `output` 与 `details`：

```typescript
const lines = defineTool({
	name: "lines",
	description: "Count the lines of a file",
	parameters: Type.Object({ path: Type.String() }),
	structuredOutputSchema: Type.Object({ lines: Type.Number() }),
	execute: async (args, api, context) => {
		const text = await readText(api, args.path, context);
		const count = text.split("\n").length;
		return { output: [{ type: "text", text: `${count} lines` }], structuredOutput: { lines: count } };
	},
});
```

缺失、未声明或无效的 `structuredOutput` 会把嵌套调用（nested call）的结果变成错误结果，并附带 `invalid_structured_output` 诊断；对模型发起的调用而言，模型根本看不到这个通道，因此该值被丢弃，并通过 `onReport` 上报。错误结果可以省略它，此时程序可在 `tool_error` 诊断中找到错误文本；运行框架自己写下的错误结果（阻止、无效、中断、中止）则一律不带，出错缘由写在其 `diagnostics` 里。某个 `afterTool` 钩子若抹除了声明 schema 工具的 `output`，也必须一并抹除其 `structuredOutput`。内置的 `bash` 返回 `{ output, truncated, fullOutputPath?, exitCode }`，其中 `output` 是模型看到的那段保留尾部，可用 `api.retainedOutput()` 读取；非零退出码会以错误结果应答，但结果中仍携带该值。

当两个扩展都被选中且工具同名时，后安装的会取代先安装的；`wrapTool()` 则装饰最终胜出的那个工具：

```typescript
const Venv = defineExtension({ name: "venv", tools: [createBashTool({ commandPrefix: "source .venv/bin/activate" })] });
const Timing = defineExtension({
	name: "timing",
	wraps: [wrapTool(createBashTool(), (bash) => ({ ...bash, execute: (args, api, ctx) => timed(() => bash.execute(args, api, ctx)) }))],
});
```

### 工具调用工具

工具通过 `api.executeTool()` 调用另一个工具，代码模式（code mode）脚本与 MCP 桥接器就是这样做的。嵌套调用是一个独立的工具任务，归属于发起调用的那个工具：它同样经过参数校验、执行 `ToolTask` 钩子，维持自己的输出限制与重放策略，并把结果返回给调用方，而不是写入记录：

```typescript
const testsPass = defineTool({
	name: "tests_pass",
	description: "Run the test suite and say whether it passed",
	parameters: Type.Object({}),
	execute: async (_args, api, context) => {
		const run = await api.executeTool("bash", { command: "npm test" }, context, { progress: false });
		// Absent when bash did not finish, for example on a timeout.
		const exitCode = (run.structuredOutput as { exitCode: number } | undefined)?.exitCode;
		return { output: [{ type: "text", text: exitCode === 0 ? "passed" : "failed" }] };
	},
});
```

- 调用方拿到的是嵌套调用的 `taskId`、`structuredOutput`、`details`、`diagnostics`、`usage` 与 `isError`，而不是给模型看的 `output`。被阻止、无效、失败或中止的嵌套调用会返回 `isError` 结果。`executeTool()` 本身在以下情况会拒绝：`execute()` 已经返回之后、调用方被中止时，以及运行框架关闭时；取消它的 `context` 只会取消这次等待。
- 钩子能看到嵌套调用的 `call.parent`，因此守卫钩子可以区别对待来自脚本的调用。
- 调用方运行期间，它的嵌套调用会显示在 `docs["pi.live"].nestedTools` 中，附带运行所用的参数，完成后还会有一份 `summary`（错误、耗时、用量）；它们也会以工具事件的形式出现，带 `parentToolCallId` 与 `parentTaskId`。`progress: false` 可以让嵌套调用的运行中输出不进入 `pi.live`。在调用方落定（settle）之前，它遗留的、仍在运行的嵌套调用会被中止，早前一次尝试发起的也不例外。调用方的结果消息不罗列它的嵌套调用；它们保留在各自的任务记录里。
- 每个嵌套调用都有一个键（key），默认是它在调用方各嵌套调用中的序号，调用方也可以传入 `{ key }` 自行指定。重放安全的调用方在崩溃后重跑时，只要按相同顺序调用、或传入相同的键，拿回的就是它已经发起过的嵌套调用，无论已完成还是仍在运行，而不会重新启动它们。若崩溃在结果提交之前打断了某个嵌套调用，该调用会遵循它自己的 `replay` 策略，因此带外部副作用的重放安全工具仍需自行保证幂等（idempotency）。不满足重放安全的调用方绝不会重跑，所以重启之后，它未完成的嵌套调用会连同其名下的一切先被弃置（abandon），然后才可能重新运行。
- 嵌套调用的 `usage` 记在它自己的工具名下；若在调用方的结果里再传递一次，就会被统计两遍。
- 嵌套调用的结果不会被保留：它们只存放在调用方的任务文档中（`NestedCallDoc`，每个嵌套调用一份，以键为索引，内容为 `{ taskId, result? }`），调用方一旦落定就会随之清除。嵌套调用的任务记录里只留一张小小的回执。存储下来的结果与 `executeTool()` 返回的内容完全一致，不含给模型的 `output`，因此一张图片或一段 `bash` 尾部输出只会存一份。
- 嵌套调用的深度没有任何上限；默认 `callers` 设置下的工具甚至可以调用它自己。在意这一点的地方，请用 `callers` 加以限制（见下文）。

### 谁可以调用工具

工具上的 `callers` 声明谁可以调用它：模型、经 `executeTool()` 调用它的其他工具，或两者皆可（默认）。对话的 `modelTools` 可以收窄向模型提供的工具范围，但不会把它们从工具侧收回：

```typescript
const codemode = defineTool({ name: "codemode", callers: ["model"], ... }); // scripts cannot start scripts
const search = defineTool({ name: "mcp__github__search", callers: ["tools"], ... }); // never offered to the model

// The model is offered only codemode; its scripts call read, bash, and the MCP tools.
await root.configure({ modelTools: [codemode] }, context);
// The model is offered everything but bash, which scripts may still call.
await root.configure({ modelTools: { remove: [bash] } }, context);
```

`conversation.agent()` 会解析出这两张名单：提供给模型的 `tools`，以及供嵌套调用解析的 `callable`。工具整体上启用与否仍由 `tools` 决定；`modelTools` 不能往里添加。

声明 `deferred: true` 的延迟工具（deferred tool）在加载之前不会提供给模型，但其他工具随时可以调用它。`@earendil-works/pi-durable/tool-search` 提供的 `tool_search` 工具（`createToolSearchExtension()`）让模型搜索这些延迟工具，并用 `control.addTools` 加载匹配项，加载结果会记录进 `modelTools`；已加载的工具在该分支上保持可用，压缩之后也是如此，而 `codemode` 段落则不包含延迟工具。庞大的工具集（例如某个 MCP 服务器的）适合用它。

### 重启后弃置的任务

只在内存中被创建者等待、创建者重启后也不会再恢复的任务，可以用 `abandonOnRestart: true` 创建。当后来的运行框架开始调度、发现它仍然存活时，会在其中任何部分重新运行之前，以 `abortReason: "restart"` 将它连同其名下的一切一并中止。不满足重放安全的工具，其嵌套调用自动获得这一行为；这类工具用 `api.createTask()` 创建的子任务也一样。如此弃置的任务若定义缺失，会等到其扩展安装之后才被中止，从而让其中止处理器仍能完成清理。它的调用方与所属对话会陪着它一起等待；`harness.inspect()` 把它显示为被阻塞。那时再中止它，会使它沦为孤儿，与其他任何中止行为一样。

## 代码模式

`@earendil-works/pi-durable/codemode` 添加了一个 `codemode` 工具：模型编写 JavaScript，以 `await tools.<name>(args)` 的形式调用对话的工具，运行在 QuickJS 沙箱（`@earendil-works/pi-codemode`）中。每次调用都是一次嵌套工具调用，只有脚本的输出会到达模型。脚本能挺过重启：它从原来的位置继续，不会重复执行已完成的调用。

```typescript
import { CodemodeSandbox } from "@earendil-works/pi-codemode";
import { createCodemodeExtension } from "@earendil-works/pi-durable/codemode";

registry.install(createCodemodeExtension({ sandbox: new CodemodeSandbox({ memoryLimitBytes: 256 * 1024 * 1024 }) }));
```

该扩展还会添加一个 `codemode` 提示段落，以 TypeScript 声明的形式、在 token 预算之内列出脚本可调用的工具；其余工具由脚本用 `searchTools()`、`describeTool()` 与 `describeNamespace()` 自行查找。用 `namespaces: [{ name, description, prefix }]` 可以按名字前缀为工具分组，例如 MCP 服务器的 `mcp__github__`。结果的形态与编码智能体的输出一致：一个标题、脚本的输出，失败时还会附上已经发起的调用；超出 `max_output_tokens` 的文本会被截断，完整文本放进临时文件。脚本还能使用 `models.*`：模型目录、`models.classify()` 与 `models.generateImages()`，它们作为内部工具的嵌套调用运行（`models: false` 可将其关闭）。在 Cloudflare 上，请改传 `RemoteCodemodeSandbox`。脚本运行途中关闭沙箱（例如停机时）不算一种结局：脚本会带着下一个进程的沙箱继续运行。失败的嵌套调用会在脚本内以其错误文本拒绝，除非该工具声明了 schema、并在出错时连同错误返回了自己的值：`tools.bash` 即使非零退出也会以 `{ output, exitCode, ... }` 兑现，因此脚本应检查 `exitCode`。`store(key, value)` 与 `load(key)` 按对话保存 JSON 值；分叉看到的值是它进入时的样子。

它如何挺过重启：沙箱确定性地运行脚本（虚拟时钟、定种子的随机数、UTC 时区），工具在把每个结果交给脚本之前，先把结果写入日志（journal）。重启之后，工具重新运行脚本，按相同的顺序把日志中的结果递还给它，于是脚本以相同的参数发出相同的调用；这些调用按键重新挂回各自的嵌套调用，随后脚本继续执行。如果脚本走了与此前不同的路径、沙箱指纹（fingerprint）或代码模式版本发生了变化、或者 `timeout_ms` 已在期间流逝，重跑就会改为以错误结束这次调用。重启那一刻仍在运行的嵌套调用，遵循它自己的重放策略。

## 系统提示

系统提示由所选扩展的段落拼装而成，在每次请求前按顺序渲染。段落可以看到解析后的智能体、为该请求构建的环境，以及已提交的文档：

```typescript
section("cwd", (input) => input.env?.cwd); // rendered as <cwd>\n...\n</cwd>; undefined omits it
```

对话的 `instructions` 最后渲染，对应名为 `instructions` 的段落。段落与工具的变更会以位置式系统条目的形式存入记录。只有发生变化的部分才会重新发送，这让服务商的提示缓存保持热度。若某个段落每次返回的内容都不同（例如当前时间），这一机制就会失效。

## 每对话智能体

每个对话都把运行时设定存在自己的 `pi.agent` 文档中。`configure()` 用一次提交完成修改；未设置的字段沿用宿主（host）的值：

```typescript
await root.configure(
	{
		model: { provider: "openai", modelId: "gpt-6-sol" },
		thinkingLevel: "high",
		extensions: { remove: [Coding] }, // edits the host default; an array selects exactly these, in order
		tools: [readTool, bashTool], // an array enables exactly these; { remove: [...] } drops some
		modelTools: [readTool], // of those, offer the model only read; tools may still call bash
		instructions: "Only read; never edit files.",
		cwd: "/work/repo",
	},
	context,
);
await root.configure({ tools: null }, context); // null clears a field back to the host default
const agent = await root.agent(context); // resolved: model, extensions, tools, sections, cwd
```

扩展和工具以对象传入、按名字存储，因此存下来的名字可以比代码活得更久：某个扩展被卸载后，选中它的对话就暂时拿不到它，直到它被重新安装。`createConversation()`、`fork()` 与 `root()` 接受与 `agent` 相同的修改项。由任务持有的对话（例如子代理的对话）以一份其归属者对话智能体的副本开始；分叉出的对话则以父对话在分叉条目处的智能体起步。一次请求的模型、提示与可用工具在请求准备时就已确定；修改从下一次请求开始生效。工具调用与钩子使用其任务阶段解析到的智能体，而环境在每次使用时都按当前 `cwd` 构建，因此 `cwd` 或扩展的修改可以影响到模型已经发出的调用。

## 设置

所有对话共享的运行策略通过 `settings` 传入。它每次使用时都会被读取、从不存储，因此可以用 getter 让它保持动态，例如背后接一个设置文件：

```typescript
const harness = await Harness.open(storage, {
	models,
	registry,
	settings: {
		extensions: [CodingTools, Coding], // default selection; absent: every installed extension
		stream: { timeoutMs: 120_000 },
		retry: { maxRetries: 3 },
		compaction: { reserveTokens: 16384 },
		progress: { partialIntervalMs: 100, outputIntervalMs: 100 },
		toolExecution: "parallel",
		contextRetentionMs: 600_000, // idle conversations keep their context in memory this long (checked lazily where background timers are declined, as in Workers)
		documentRetentionMs: 600_000, // loaded documents nothing observes stay in memory this long after their last use; observed ones always
		get followUpMode() {
			return userSettings.followUpMode;
		},
	},
}, context);
```

## 环境

`env` 为每次工具调用、段落渲染与 `runtime.env()` 构建执行环境。它会收到对话 ID、智能体的 `cwd` 以及已提交的读取操作，因此同一个函数就能支撑「每对话一个目录」或「每对话一个容器」：

```typescript
import { NodeExecutionEnv } from "@earendil-works/pi-durable/env/node";

const harness = await Harness.open(storage, {
	models,
	registry,
	env: ({ cwd }) => new NodeExecutionEnv({ cwd: cwd ?? process.cwd() }),
}, context);
```

`env` 抛出的异常会成为该调用的错误结果。没有环境时，内置工具会以错误结果失败。每次调用都新建一个环境对象也没问题：`edit` 与 `write` 会按环境的 `id` 和路径，把对同一文件的修改串行化。自定义 `ExecutionEnv` 应设置好 `id`，让相同 id 在相同路径下看到相同文件，例如每个容器一个 id。

宿主也可以直接使用环境，例如展示项目的文件。`openBinaryReader()` 读取一个已打开文件的字节区间，`openDirReader()` 分页遍历一个目录，argv 数组形式的 `exec()` 不经 shell 直接运行程序，并报告每个输出块来自哪个流：

```typescript
const status = { stdout: "", stderr: "" };
await env.exec(["git", "status", "--porcelain=v2", "-z"], {
	onOutput: (text, _context, { stream }) => {
		status[stream] += text;
	},
}, context);
```

中止上下文即可停止单次调用；`cleanup()` 用于关闭整个环境。自定义环境可以用 `@earendil-works/pi-durable/testing` 中的 `registerEnvConformance()` 自检，就像下文的存储一样。

一些环境还实现了可选的 `listFiles()`：列出一个目录之下任意深度的文件与目录，如同 `fd` 所列，跳过 git 忽略的内容，到达上限时以 `truncated` 收尾。`NodeExecutionEnv` 没有实现它；pi-env 的 `RemoteExecutionEnv` 与 `LocalExecutionEnv` 实现了。方法缺失或以 `not_supported` 失败时，调用方会退回自己遍历：

```typescript
const listing = await env.listFiles?.(".", { exclude: ["node_modules"], maxEntries: 50_000 }, context);
```

## 重载

安装一个与已装扩展同名的扩展，会一步完成原地替换：

```typescript
registry.install(await loadCodingExtension()); // same name "coding": replaces the installed one
```

`registry.uninstall(extension)` 按名字移除已安装的扩展，无论它对应哪个对象。

已经开始的工作会继续使用它拿到的代码：正在进行的工具调用以旧实现跑完；每个任务阶段只在阶段开始时从注册表解析一次钩子与智能体。下一个阶段、请求或调用才会使用新代码。进程重启后，请重新安装相同的扩展；扩展 `tasks` 中待处理的任务会在它装好之后恢复运行。

## 监听对话

界面需要的一切都是已提交的状态。`viewState()` 以只读 Chord 状态的形式返回对话的结构化视图（view），每次触及它的提交之后都会更新：

```typescript
const view = await root.viewState(context);
view.subscribe((value) => {
	// value.entries: the active transcript
	// value.docs["pi.live"]: the running generation (streamed partial, retry, deferred) and tool calls (output, details)
	// value.docs["pi.inbox"], value.docs["pi.usage"], value.docs["pi.agent"], value.docs["pi.provider"]
	render(value);
});
// later: view.dispose();
```

`watch()` 递送同一个视图，并附带每次提交确切的 Chord 操作，逐批回调：

```typescript
const watch = await root.watch(context);
render(watch.value); // the state at attachment
watch.start(async (value, ops) => {
	await send(ops); // for example to a remote client that applies them
});
// later: await watch.stop();
```

消费太慢的监听最多保留 100 帧未送达的数据。超过之后，积压的帧会被替换为一帧包含最新完整视图的数据。较晚加入或重连的客户端从当前视图开始，不会重放任何历史。

部分回答与工具输出默认最多每 100 ms 提交一次，因此崩溃最多丢失这个时间窗口内的数据。`settings.progress` 可以调整提交间隔；存储在远端的宿主可以降低提交频率，例如 `{ partialIntervalMs: 500, outputIntervalMs: 500 }`。

## 忙碌的对话

运行正在处理某个输入时，对话处于忙碌状态。向忙碌的对话提交内容时，提交项会排入对话的收件箱（inbox），即视图中的 `docs["pi.inbox"]`：

```typescript
await root.submit({ type: "input", content: "Also run the tests" }, context); // follow-up (default)
await root.submit({ type: "input", content: "Use pnpm, not npm", whenBusy: "steer" }, context);
await root.submit({ type: "input", content: "Only if idle", whenBusy: "reject" }, context); // throws ConversationBusy
await root.submit({ type: "write", entry: { kind: "app.note", data: "user opened a file" } }, context);
```

- **转向（Steer）** 在当前工具轮之后放置，加入正在进行的运行。
- **追问（Follow-up）** 在运行给出回答后放置，并启动下一次运行。
- **写入（Write）** 只追加条目，不向模型提问。只含 `kind` 与 `data` 的写入不会改变模型可见的任何内容，因此会被立即追加，即使在运行途中也一样，而且从不排队：一条聊天消息一经发出就出现在记录里。因此它可能出现在更早提交、却仍在排队的条目之前；例外是当它排在一个排队中的重置之后时，它会等待，以免被重置掩盖。带 `model`、`head` 或 `edits` 的写入则像转向一样等待下一个边界。
- `await submission.abort(context)` 撤回一个仍在排队的提交项。
- 设置中的 `steeringMode: "all"` 与 `followUpMode: "all"` 会一次性放置全部排队项，而不是每轮只放一个。

如果一次运行失败，排队项会留在收件箱里，直到下一次输入或排队写入放置它们，先到先放。

输入放置后会成为一条 `pi.user` 条目。想让它以别的面目呈现，可以给它一个 `entry`，写上你的 kind 与数据；模型看到的 `content` 仍然是用户消息：

```typescript
await root.submit(
	{
		type: "input",
		content: "ann: can you check the build?",
		entry: { kind: "chat.mention", data: { author: "ann", text: "can you check the build?" } },
	},
	context,
);
// placed as { kind: "chat.mention", data: { author: "ann", ... }, model: [{ role: "user", content: "ann: can you check the build?" }] }
```

它的行为与其他任何输入一样：启动一次运行、转向、追问或被拒绝，并且会得到回答。排队期间，它的收件箱条目会携带这个 `entry`。kind 不得以 `pi.` 开头。

## 重置与交接

`reset()` 开启一段新上下文。模型不再看到更早的条目，但它们仍保留在存储中：

```typescript
await root.reset(undefined, context);                                  // start from nothing
await root.reset("We were fixing the flaky login test. Continue.", context); // start from a handoff note
```

忙碌期间，重置会像写入一样排队。如果它在某个工具轮中被放置，当前运行随即结束。工具也可以通过 `control: { handoff: "..." }` 请求同样的行为。

## 压缩

压缩（compaction）缩减模型可见的内容：它总结较早的条目，并追加一条 `pi.compaction` 条目——该条目保存摘要，并置于其保留的第一条条目之前。更早的条目仍留在存储中。

```typescript
const id = await root.compact("Keep the failing test names", context); // manual, with optional instructions
const { outcome } = (await harness.waitForTask(id, context)).state;
if (outcome.status === "completed" && outcome.result.submissionId !== undefined) {
	const placed = await (await harness.submission(outcome.result.submissionId, context))!.wait(context);
	console.log(placed.status); // "done", or "unanswered" with reason "stale"
}
```

生成摘要期间对话照常工作。对话空闲时摘要立即放置，否则放到下一个轮次边界。Esc（`abort()`）可取消手动压缩。

生成任务也会自行压缩，由设置控制：

```typescript
settings: {
	compaction: {
		enabled: true, // automatic compaction; manual compact() always works
		reserveTokens: 16384, // above contextWindow - reserveTokens, the next request waits for a compaction
		keepRecentTokens: 20000, // roughly how much recent context stays verbatim
		backgroundTokens: 32768, // this far below that, a compaction starts in the background; 0 disables it
		modelOverrides: {
			// exact "provider/modelId"; each field set here replaces the one above for that model
			"local/small-32k": { reserveTokens: 4096, keepRecentTokens: 8000, backgroundTokens: 4096 },
		},
	},
}
```

固定的 token 数很少能同时适合 32k 与 1M 两种上下文窗口；`modelOverrides` 让一个运行框架可以同时服务两者。对话当前使用的模型会在阈值检查时、上下文溢出之后、以及压缩挑选总结内容时，选取对应的条目。

当服务商以上下文过长为由拒绝请求时，生成任务会压缩并重试一次。如果一个摘要在放置时会切到当前上下文的起点之前，它会以 `stale` 告终；因此当多个摘要同时在途时，切得最深的那个保持生效。总结所花费的开销计入 `pi.usage`。`CompactionTask` 上的 `beforeCompact` 钩子可以拒绝压缩，或自行提供摘要。

当生成任务在阻塞阈值处等待的压缩失败时，生成任务也随之失败，而且不会发出请求：其输入以 `unanswered` 告终，原因为 `model_error`，细节是 `Compaction failed: <error>`。找不到可压缩内容或被钩子拒绝的压缩，则会放行请求。

正在进行的压缩会连同原因、尝试次数与重试退避一起列在 `docs["pi.live"].compactions` 中。最近一次失败会留在 `docs["pi.live"].compactionFailure`（任务、原因、错误）里，直到某次压缩产出摘要。智能体事件增加了 `compaction_start` 与 `compaction_end`（压缩失败时附带 `error`），快照中也增加了 `compactions` 与 `compactionFailure` 字段。

## 智能体事件（实验性）

如果消费者想要编码智能体风格的事件（`message_start`、`message_update`、`tool_execution_start`……）而非结构化状态：

```typescript
import { watchEvents } from "@earendil-works/pi-durable";

const stream = await watchEvents(harness, root.id, context);
initialize(stream.snapshot); // entries, run, in-flight generation, tools, compactions, inbox, agent, usage
stream.start(async (events) => {
	for (const event of events) console.log(JSON.stringify(event));
});
```

事件从提交派生而来，每次提交对应一批，并在快照之上应用。消息与工具更新携带增量（delta）：文本与思考内容的追加、工具调用参数文本的追加，以及输出的截断与追加。当消费者落后超过 100 批时，会改为收到一个全新的 `snapshot` 事件。一次运行的完整事件流参见 `test/examples/19-json.ts`。

## 钩子

钩子（hook）让扩展能在选中它们的对话中观察或调整内置任务：

```typescript
import { GenerationTask, hook, ToolTask } from "@earendil-works/pi-durable";

const Guard = defineExtension({
	name: "guard",
	hooks: [
		hook(ToolTask, { beforeTool: (call) => (call.name === "bash" ? { block: "bash is disabled here" } : undefined) }),
		hook(GenerationTask, { onYield: (answer) => (needsMoreWork(answer) ? { continue: "Keep going." } : undefined) }),
	],
});
```

- **生成（Generation）**：`beforeRequest`（替换某次请求的消息）、`afterResponse`、`onYield`（追加一条用户消息以继续运行）与 `afterTools`（在一轮工具全部完成后运行）。
- **工具（Tools）**：`beforeTool`（阻止调用或改写参数）与 `afterTool`（替换结果）。

要把某个钩子限制在部分对话中生效，只需让那些对话才选中它所属的扩展，例如 `configure({ extensions: { add: [Guard] } })`。

## 更多对话与分叉

```typescript
const other = await harness.createConversation({ ownership: { kind: "ownerless" } }, context);
const fork = await root.fork(entryId, { ownership: { kind: "ownerless" } }, context);
```

分叉能看到父对话截至 `entryId` 的条目，此后独立延续。它保留父对话在该条目时刻的智能体设定，但会获得一个全新的供应商会话身份。两者都接受 `agent` 与 `init`，并在创建它们的那次提交中生效。

## 中止与子代理

`await root.abort(context)` 停止一个对话：排队的输入被撤回（排队的写入保留），其当前工作涉及的每个任务都被中止，调用在对话恢复空闲后完成。

对话可以**归属于**某个任务。子代理（subagent）工具在 `api.commit()` 内以 `ownership: { kind: "task", taskId: api.taskId }` 创建子对话，然后通过 `api.conversation(id)` 驱动它：

```typescript
const Subagent: Extension = defineExtension({
	name: "subagent",
	tools: [
		defineTool({
			name: "subagent",
			description: "Delegate a self-contained task to a subagent and get its answer back.",
			parameters: Type.Object({ task: Type.String() }),
			replay: "safe", // a rerun after a crash finds the same child and submission
			execute: async (args, api, context) => {
				const child = await api.commit(async (tx) => {
					// The ownership index remembers the child, so a rerun reuses it.
					const existing = (await tx.scanConversations({ ownerTaskId: api.taskId }, 1)).items[0];
					if (existing !== undefined) return existing.id;
					// Starts as a copy of this conversation's agent: model, extensions, tools, cwd.
					const created = await tx.createConversation({ ownership: { kind: "task", taskId: api.taskId } });
					// A cheaper model, and no subagents of its own.
					await configure(tx, created.id, { model: haiku, extensions: { remove: [Subagent] } });
					return created.id;
				}, context);
				await api.details({ conversationId: child }, context); // lets a UI attach to the child
				const request = { type: "input", content: args.task, requestId: `subagent:${api.taskId}` } as const;
				const settled = await (await (await api.conversation(child, context))!.submit(request, context)).wait(context);
				return { output: [{ type: "text", text: settled.status }] };
			},
		}),
	],
});
```

归属于任务的工作也属于它的归属者：

- 中止这次调用会中止子对话。调用失败亦然：`execute()` 抛出异常，或崩溃打断了一个不满足重放安全（replay-safe）的调用。
- 只有子对话空闲，父对话才算空闲。
- 以 `{ background: true }` 创建的任务是一道边界：它名下的工作会在父对话中止后继续存活，也不会让父对话保持忙碌。`root.abort(context, { background: true })` 则会把它一并中止。

示例以产品级代码展示了这两种模式：

- [`22-subagent-foreground.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/22-subagent-foreground.ts)：即上文那个工具，返回子对话的回答。界面通过调用的 `details` 找到子对话，并把子对话的事件缩进打印在该调用之下。
- [`23-subagent-background.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts)：用一个 `subagent` 工具承载持久子代理，可以生成、发消息（转向或追问）、等待、停止与列举。每个子对话都归属于一个后台锚点任务，因此父对话的 Esc 与空闲等待都不会波及它。每条消息由一个后台报告者任务投递，回答一到就以追问输入的形式回传给父对话；请求 ID 确保重启后不会重复发送消息或报告。

## 子任务

任务可以持有子任务（用 `ownership: { kind: "task", taskId }` 创建），并通过提交一个 `waiting` 状态来等待它们：

```typescript
pay: async (task, runtime, context) => {
	await runtime.commit(async (tx) => {
		const payments = [];
		for (const card of task.input.cards) {
			payments.push(await tx.createTask(Payment, { card }, { ownership: { kind: "task", taskId: task.id } }));
		}
		// Resume in `decide` once every payment is done; the first failure aborts the rest.
		return { status: "waiting", checkpoint: { phase: "decide", payments }, on: payments, policy: "failFast" };
	}, context);
},
decide: async (task, runtime, context) => {
	const outcomes = await runtime.outcomes(task.state.checkpoint.payments, context);
	// ...commit the checkout's own outcome
},
```

- **等待（Waiting）**：任务在等待期间不执行任何代码。用 `allSettled` 时，`on` 中的每个任务都完成后它才恢复；用 `failFast` 时，第一个失败的子任务会把其余的一并中止。配合 `allSettled`，`on` 也可以指名其他任务。
- **收尾（Finishing）**：任务在名下工作仍在运行时宣告完成，会进入 `completing`：其结果已经决定，但要等那些工作做完，它才转为终态，`waitForTask()` 也才返回。若结果是失败或中止，会先中止那些工作。
- **中止（Aborting）**：中止自底向上进行。中止一个任务会先中止它名下的工作；等那些工作完成后，它自己的中止处理器才启动，这样每个任务都能撤销自己的副作用。

[`24-child-tasks.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/24-child-tasks.ts) 演示一场四笔支付的结账：一张被拒的卡、一次被取消的结账，以及支付进行中的一次重启。

## 任务图

`harness.taskGraph(context)` 把会话中所有存活的任务以一个 Chord 状态呈现，适合做任务面板或调试。每个节点带有归属边（`owner` 任务；若任务由其对话持有则为空）、状态、是否为 `background` 或已被标记中止，以及它持有的对话。`harness.watchTaskGraph(context)` 以监听的形式递送同样的值，就像对话的 `watch()` 一样。

```typescript
const graph = await harness.taskGraph(context);
graph.subscribe((value) => {
	for (const node of Object.values(value.tasks)) {
		const status = node.state.status === "waiting" ? `waiting on ${node.state.on.join(", ")}` : node.state.status;
		console.log(`${node.id} ${node.kind} ${status}`, node.owner ?? `conversation ${node.conversationId}`);
	}
});
```

任务随创建它的提交出现，随使其终结的提交消失。状态就是已提交的那些：`pending`、`running`、`waiting`（附带 `on` 与 `policy`）以及 `completing`（附带暂存结果的状态）。重启之后，原本 `running` 的任务会显示为 `pending`，直到再次运行。某个待处理任务是否因缺少定义而被阻塞，不在任务图的呈现范围内；`harness.inspect()` 会报告这一点。任务图只列出存活任务：一旦子代理的归属任务终结，其对话中之后的任务就会成为顶层节点，对话的 `ConversationRecord.owner`（也出现在其视图的 `conversation` 中）会把它与父对话关联起来。[`24-child-tasks.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/24-child-tasks.ts) 会在支付运行期间打印结账的任务树。

## 自有状态

文档是与条目一起提交的类型化 JSON 对象。定义一个文档，然后在提交中编辑它：

```typescript
import { defineDoc } from "@earendil-works/pi-durable";

const Todos = defineDoc<{ items: string[] }>({
	kind: "app.todos",
	version: 1,
	scope: "conversation",
	history: "latest", // or "rewindable" to read old values with snapshotAsOf()
	fork: "initial", // what a fork starts with: "initial", "current", or "asOf"
	initial: () => ({ items: [] }),
	checkpointWhen: () => false, // required: true stores this change as a complete base, bounding replay
});

await root.commit(async (tx) => {
	(await tx.doc(Todos, root.id)).items.push("write docs");
}, context);
console.log(await harness.snapshot(Todos, root.id, context));
```

`harness.watchDoc()` 与 `harness.documentState()` 像上面的视图一样观察单个文档。`HarnessOptions.conversationCreated(tx, conversation)` 在每个创建或分叉对话的提交中运行，包括工具直接调用的 `tx.createConversation()`，因此每个对话都会拥有你的文档；`createConversation()`、`fork()` 与 `root()` 中的 `init` 则在同一次提交里写入每次调用的专属数据。扩展的工具、段落与钩子通过 `api` 或 `input.read` 读取自己的文档，文档不存在时按默认值处理（[`11-extension-state.ts`](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/11-extension-state.ts)）。

## 存储

| 后端 | 引入方式 | 说明 |
|---|---|---|
| 内存 | 包根目录导出的 `MemoryStorage` | 不持久化任何内容。 |
| IndexedDB | `@earendil-works/pi-durable/storage/indexeddb` 中的 `IndexedDbStorage.open(name)` | 仅浏览器可用的存储，存于单个 IndexedDB 数据库中。 |
| SQLite | `@earendil-works/pi-durable/storage/sqlite/node` 中的 `openNodeSqliteStorage(file)` | 单个数据库文件。WAL 模式且 `synchronous = NORMAL`：提交能在进程崩溃后幸存；断电或宿主机故障时，最新一次提交可能丢失。 |
| JSONL | `@earendil-works/pi-durable/storage/jsonl/node` 中的 `openNodeJsonlStorage(directory, context)` | 一个目录中的只追加文件。传入 `{ fsync: true }` 可在每个提交标记写入前刷盘。它还会把全部历史保存在内存里，内存占用随之增长；长期运行的智能体请改用 SQLite。 |
| Cloudflare Durable Object | `@earendil-works/pi-durable/storage/sqlite/cloudflare` 中的 `openDurableObjectSqliteStorage(ctx.storage)` | 一个 SQLite 支持的 Durable Object 的 SQLite 存储；每次提交就是它的一次存储事务。 |

在浏览器中，用 `await IndexedDbStorage.open(name)` 打开 IndexedDB 存储。同一时刻只能有一个持有者占有该数据库；请用一个 [Web Lock](https://developer.mozilla.org/docs/Web/API/Web_Locks_API) 包住它的生命周期，而不要在相互竞争的标签页或 worker 中各自打开它。当持久保留（durable retention）很重要时，请调用 `await navigator.storage.persist()`。

SQLite 存储在与宿主共用一个数据库时，可以为它的表和索引起名字空间（namespace）：向 `SqliteStorage.open(database, options)`、`openNodeSqliteStorage(path, options)` 或 `openDurableObjectSqliteStorage(ctx.storage, options)` 传入 `{ prefix: "pi_" }`。存储会把带前缀的名字渲染进它的 SQL，因此适配器无需额外支持。前缀必须是合法的 SQLite 标识符，且不能以 `sqlite_` 开头；宿主可以保留更多前缀，例如 Durable Objects 中的 `_cf_`。修改前缀不会迁移已有数据。

经 Cloudflare 适配器、以同一个存储对象打开的多个 Pi 存储会自动共享一个操作队列，因此多个 Pi 存储可以安全地共用一个 Durable Object 数据库。要把数据库与宿主表共用，请创建一个适配器，Pi 与所有宿主查询都用它；绕过队列的直接存储调用可能被某个 Pi 事务回滚：

```typescript
const database = new DurableObjectSqliteDatabase(ctx.storage);
const piStorage = await SqliteStorage.open(database, { prefix: "pi_" });
await database.exec("CREATE TABLE IF NOT EXISTS host_notes (text TEXT)");
await database.run("INSERT INTO host_notes (text) VALUES (?)", text);
```

同一时刻只有一个进程持有某个存储，没有跨进程加锁。可移植的 SQLite 与 JSONL 核心（`/storage/sqlite`、`/storage/jsonl`）不依赖 Node API 即可运行，例如在 Bun 或 Cloudflare Durable Objects 中，只要提供异步的 `SqliteDatabase` 门面（facade）或来自 `@earendil-works/pi-durable/env` 的 `FileSystem`。

SQLite 适配器需要实现基于 Promise 的 `exec`、`run`、`get`、`all`、`transaction` 与 `close`。`run`、`get` 与 `all` 接收 SQL 文本加位置参数绑定；适配器可以按 SQL 文本缓存预编译语句。事务回调会收到一个事务句柄；事务中的所有操作都必须经由它，回调结束时句柄即失效。适配器必须把无关操作与其他事务排队，直到当前事务结束，因此在回调内部直接调用 `database` 自身永远不会返回：

```typescript
await database.transaction(async (transaction) => {
	await transaction.exec("CREATE TABLE example (value TEXT)");
	await transaction.run("INSERT INTO example (value) VALUES (?)", "stored atomically");
});
```

自定义后端可以用任何兼容 Vitest 或 Jest 的测试运行器运行共享的一致性测试套件：

```typescript
import { registerStorageConformance } from "@earendil-works/pi-durable/testing";
import { describe, expect, it } from "vitest";

registerStorageConformance({ describe, expect, it }, "My Storage", async (use) => {
	const storage = await openMyStorage();
	try {
		await use(storage);
	} finally {
		await closeMyStorage(storage);
	}
});
```

包根入口会加载 TypeBox，因为工具任务要用 pi-ai 的 `validateToolArguments()` 校验参数。不打包时这约占 23 MB 的峰值 RSS，经 tree-shaking 打包后约 4 MB。

## 错误

三条规则决定一个错误的后果：

1. **存储错误会终结运行框架。** 命中它的那个调用以该错误拒绝。它之后的一切调用、以及每一个挂起的等待，都以 `SessionFailed` 拒绝（其 `cause` 即该错误）；监听与事件流以 `session_failed` 结束；运行中的任务收到中止信号；`onReport` 恰好收到该错误一次。随后运行框架自行关闭。没有任何东西会被重试；自定义存储要自行重试其瞬时故障。重新打开即可恢复：提交是原子的，存储因此保持一致；以相同 `requestId` 重新提交，会找到那笔已被受理的提交。
2. **无效的读取只让该次调用失败：** 存储的读取操作会为坏游标、未知对话、或文档未保留的历史抛出 `StorageRequestError`。被你取消的读取同样只让读取自身失败。这一豁免只覆盖读取：来自 `commit()` 或 `mintId()` 的任何错误——包括 `StorageRequestError`——都会像第 1 条规则那样终结运行框架。
3. **你的代码只让它所在的单元失败：** 抛异常的任务阶段使该任务进入故障（fault）状态，抛异常的工具得到一个错误结果，抛异常的钩子被上报并跳过（`beforeTool` 会阻止该调用），抛异常的提交回调回滚该次提交。抛异常或返回被拒 Promise 的监听器会被上报，其余监听器照常运行。例外是宿主的 `RegistryReader`：它的 `snapshot()` 若抛出异常，运行框架便无从调度，因此会像存储错误那样使运行框架失败。

`harness.closed` 在运行框架关闭后落定，无论是经由 `close()` 还是存储错误所致，宿主因此可以这样在失败后重启：

```typescript
harness.closed.then((end) => {
	if (end.reason === "failed") reopen(end.error);
});
```

失败会让运行框架自行关闭；`closed` 在这次关闭完成后落定，即便存储未能干净地关闭。关闭会等待正在运行的任务代码返回，因此无视中止信号的代码会拖延 `closed`。
